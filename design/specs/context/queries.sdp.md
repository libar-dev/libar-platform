# The context queries

Layer 1 · Detail: full · Traces: D2, D5, D8, D11, D19, Law 5, Law 11, F11, F13, F15, Probe 5, S4, E-6, E-24.

A context exposes queries that return DTOs. The parent authenticates and authorizes, then calls a context query through the component API with the tenant as its one scope argument; the context reads its own tables by index and maps state to the DTO its registration declares, so its private schema stays private. The queries serve the first two rows of the read-need table, one entity's detail and an essential list, plus journal inspection and the rebuild check. A list inside the component pages through `paginator` from `convex-helpers`, because the built-in `.paginate()` throws inside a component; the parent relays the page, and a client pages by an explicit pair of cursors with no hook.

## Intent

- outcome: Pin the query surface of a context, its arguments, its DTO mapping and how pagination crosses the boundary (D8, E-24)
- value: One entity's detail and an essential list are served by an authorized indexed query with no projection job, and a client subscribed to the parent's query sees committed state or later (D8, F7)
- risk: `paginator` keeps no pagination journal, so a context list page is pinned to its range only when the client passes the `endCursor` its first read returned; a client that subscribes with a start cursor alone sees gaps or repeats between pages under live writes (F15, Probe 5, S4)
- risk: A page subscribed with an end cursor is read to that cursor whatever `numItems` says, so its bound on a re-run is the row cap and the byte cap the list passes; a page that reaches either comes back `SplitRequired` with a `splitCursor` and holds only the rows up to its `continueCursor`, and the client must replace it with two pages, which costs one more query per split (S4, F13, E-24, Probe 5)
- risk: A fold reads every event since the latest baseline and deep-compares the result inside one query, so the 1 second query timeout binds before the 16 MiB read ceiling; the fold bound is provisional until the first experiment and the L2-7 example measure it (F13, E-25)
- assumption: A parent query calling a component query stays reactive (F15)
- assumption: The built-in `.paginate()` throws inside a component, as the components page states and Probe 5 showed, and `paginator` from `convex-helpers/server/pagination` is the documented replacement (S4, Probe 5)
- assumption: The documentation says a component has no `ctx.auth`; the queries do not rest on it, because by this design's rule no component function reads `ctx.auth`, and they trust the tenant the parent passes (F11, D11)

### Open questions

- [non-blocking] Probe 5 showed on the pinned backend with `convex-helpers` 0.1.124 that the parent query stays reactive, that pages pinned by their end cursors stay contiguous, that a capped page crosses the boundary as `SplitRequired` with its `splitCursor`, and that the `usePaginatedQuery` hook of `convex-helpers/react` then shows 40 of 45 rows; this design uses no hook across the boundary, and the examples are rerun when either pin moves (Probe 5, F15, S4, D8, E-24)
- [non-blocking] Extension E-24: the doc says component queries are authorized and return DTOs; this Spec fixes one definer per query, the one `tenantId` argument with no separate scope, the `toDto` mapping with the stream version on every DTO, pagination through `paginator`, the item cap with a row cap of twice the item cap and a byte cap passed on every run, the relay of `pageStatus` and `splitCursor` unchanged, paging by an explicit cursor pair with no client hook, the parent query's one `authorizeQuery` call and its refusal as a rejection, the `maxEvents` argument of the `rebuild` query and its `budgetExhausted` refusal for a batching caller, and the fold refusal of the `rebuild` query; this is a provisional reading the owner has not ruled (D8, S4, E-24, E-42)
- [non-blocking] A parent query's refusal carries the query's name in the field `commandType` of the rejection data, a field whose name says command; the wire shape stays `RejectionData` of `spec:command.outcome-boundary` unchanged, and whether the field is renamed or the language gains a word for both is the owner's ruling, which has not been made (D7, E-24)

## Contract

- One entity's detail is an authorized component query returning a DTO (D8)
- An essential list is an indexed query over the stream rows, paginated, or a read model updated in the command (D8)
- A context query returns a deliberate DTO and its private schema stays private; a document ID never leaves the component (D8, D2)
- Every query names its tenant: the tenant scope of a context query is its `tenantId` argument alone, as it is for an operation, and an absent tenant is never a wildcard (Law 11, D11, E-6)
- Authorization comes before disclosure; a context query is called only after the parent authorized the actor for that tenant, and the query reads only rows of the tenant it was given (Law 5, D11)
- No query reads `ctx.auth` (F11)
- After a successful command, an authorized query sees the committed state or a later one (D8)
- A history query returns a stream's events in stream-version order, including the events before a baseline (D5, Sc L2-7)
- An operation query returns the events one operation produced in this context, for diagnosis by operation ID (D19)
- A rebuild query folds the stream from its journal and returns the folded state and version for the equality test; an audit-only context registers none (D3, D5)
- A component query cannot be called by a client; the parent's query calls it and returns what the client may see (S4, Law 5)
- A list is one query over one `paginate` call with a bounded page; inside a component the call is `paginator` from `convex-helpers/server/pagination`, because the built-in `.paginate()` throws there; the parent passes the client's `cursor`, `endCursor` and `numItems` through and relays the page with `isDone`, `continueCursor`, `pageStatus` and `splitCursor` as the call returned them (S4, E-24, Probe 5)
- [extension] A list caps `numItems` at its item cap and passes a row cap of twice the item cap and a byte cap on every run, so a full page never comes back `SplitRequired` on its own, and a page read to an end cursor is still bounded; the caller's own `maximumRowsRead` and `maximumBytesRead` are not relayed (E-24, S4, F13, Probe 5)
- [extension] A client pages by an explicit cursor pair and no hook crosses the component boundary: it reads a page with `cursor` and `numItems`, then subscribes to the same page with `endCursor` set to the `continueCursor` that read returned, and each page is a reactive query of its own (E-24, F15, Probe 5)
- [extension] A client that receives `pageStatus: "SplitRequired"` replaces the page with two, one from the page's `cursor` to the `splitCursor` and one from the `splitCursor` to the `endCursor` the page was subscribed with, never to the capped page's own `continueCursor`; `SplitRecommended` marks a complete page that the client may split the same way (E-24, Probe 5)
- [extension] `get` answers `null` for a subject that is absent or deleted, and `list` leaves deleted subjects out after the page is read unless its `includeDeleted` argument is `true`, so a page may hold fewer rows than `numItems` while `isDone` is false; `includeDeleted` is for a trusted caller inside the deployment, the rebuild and the restore, which need deleted subjects, and a parent query or parent list never relays it from a client (E-24, D8)
- [extension] A list is ordered by `streamId` within a stream type; a context that needs another order adds an index and a query for it (E-24, D2)
- [extension] Every DTO a registration's `toDto` returns carries the stream's `StreamVersion` as `version`, so the parent, the projection and the backfill read one shape on the live path and on the enumeration (E-24, D8, D9)
- [extension] A `rebuild` query refuses, with a structured result rather than a read-limit error, a stream whose tail since its latest baseline exceeds the fold bound, and likewise a stream whose saved `stateSchemaVersion` is behind the registration's and so still awaits its baseline; the caller counts either refusal as a journal finding (E-24, E-25, F13)
- [extension] The parent query that relays a context query takes `tenantId` in its own `args`, establishes and authorizes its actor through `authorizeQuery` of `spec:command.actor-and-scope` before the component call, never reads `ctx.auth` itself and never infers the tenant from the identity; a refusal is the rejection of `spec:command.outcome-boundary` with the code `unauthenticated` or `forbidden` and the query's name in `commandType`, and it writes nothing, no receipt included (E-24, Law 11, Law 5, D11, D7)
- [extension] A cursor the pagination call cannot read is a technical failure, the plain error the call throws, and never a rejection (E-24, D4)

## Design

Each query is built by its own definer from the journal and a stream registration, so its `returns` validator is the registration's DTO validator, code generation sees a static export, and a context registers only the queries it serves. The tenant scope is the `tenantId` argument; no query takes a second scope argument. `paginator` reads its index fields from a schema the library builds from `contextTables`, the same fragment the component's schema spreads.

- fnDefineGet: `defineGet<S, C, E extends DomainEvent, R>(journal: Journal, registration: StreamRegistration<S, C, E, R>): RegisteredQuery<"public", GetArgs, Promise<Value | null>>` registering `{ args: { tenantId: v.string(), streamId: v.string() }, returns: v.union(registration.dto, v.null()), handler }` (D8, E-24)
- fnDefineList: `defineList<S, C, E extends DomainEvent, R>(journal: Journal, registration: StreamRegistration<S, C, E, R>): RegisteredQuery<"public", ListArgs, Promise<PaginationResult<Value>>>` registering `{ args: { tenantId: v.string(), paginationOpts: paginationOptsValidator, includeDeleted: v.optional(v.boolean()) }, returns: paginationResultValidator(registration.dto), handler }` (D8, E-24)
- typeQueryArgs: `type GetArgs = { tenantId: string; streamId: string }` and `type ListArgs = { tenantId: string; paginationOpts: PaginationOptions; includeDeleted?: boolean }` where `PaginationOptions` is the type of `convex/server` (E-24, Law 11)
- fnDefineOthers: `defineHistory(journal, registration)`, `defineRebuild(journal, registration)` and `defineByOperation(journal)` register the `history`, `rebuild` and `byOperation` queries below in the same way, one definer each (D5, D19, E-24)
- fnGet: the handler of `defineGet` reads the stream through the journal's `load`, which reads the row by `by_identity` and assembles a derived state from its parts, returns `null` when the stream does not exist or its row carries `deletedAt`, and otherwise returns `registration.toDto(state, meta)` (D8, Law 11, E-2, E-24)
- fnList: the handler of `defineList` runs `paginator(ctx.db, contextSchema).query("streams").withIndex("by_identity", (q) => q.eq("tenantId", tenantId).eq("streamType", streamType)).paginate(boundedPage(paginationOpts, { items: limitListPage(registration.mapping.budgetBytes), bytes: limitListBytes }))`, leaves out rows whose `deletedAt` is set unless `includeDeleted` is `true`, reads each remaining row's parts by `by_stream_part` under a derived mapping, maps the rows through `toDto` with a `StreamMeta` built from the row, and returns the helper's result with that `page` in place of the rows; a row saved under a newer `stateSchemaVersion` than the registration's makes `list` throw the plain Error that `load` throws (D8, S4, E-2, E-24, F13)
- typePageLimit: `type PageLimit = { items: number; bytes: number }` (E-24, F13)
- fnBoundedPage: `boundedPage(opts: PaginationOptions, limit: PageLimit): PaginationOptions` returns `{ cursor: opts.cursor, numItems, endCursor: opts.endCursor when set, maximumRowsRead: 2 * limit.items, maximumBytesRead: limit.bytes }` and nothing else of `opts`, where `numItems` is `opts.numItems` floored, raised to 1 when it is not at least 1, a value that is not a number included, and capped at `limit.items`, so `Infinity` asks for the item cap; the context library exports it beside the definers, a parent list imports it from there, and every list, in a context and in the parent, passes its one `paginate` call these options (E-24, F13, Probe 5)
- fnHistory: `export const history = query({ args: { tenantId: v.string(), streamId: v.string(), fromVersion: v.optional(v.number()), paginationOpts: paginationOptsValidator }, returns: paginationResultValidator(eventEnvelopeValidator), handler })` runs `paginator(ctx.db, contextSchema).query("events").withIndex("by_stream", ...)` with `.eq` on the identity fields and `.gte("streamVersion", fromVersion ?? 1)` in ascending order and paginates with `boundedPage(paginationOpts, { items: limitHistoryPage, bytes: limitHistoryBytes })`; events before a baseline are returned like any other (D5, S4, Sc L2-7, E-24, F13)
- componentPagination: `paginator` is imported from `convex-helpers/server/pagination` and called with the component's `ctx.db` and `contextSchema`; it takes the same options as the built-in `.paginate` and returns `{ page, isDone, continueCursor }` with `pageStatus` and `splitCursor` present only when it marks a split; it keeps no journal, so a page is pinned only by an `endCursor`; with an `endCursor` it reads to that cursor and `numItems` no longer bounds it; it counts a row before it tests either cap, so the byte cap is a stopping point that the last row read may pass by its own size; it answers `SplitRequired` when a cap is reached and `SplitRecommended` when a complete page holds more than `numItems + 1` rows (S4, E-24, F13, Probe 5)
- pagingByCursor: a client holds one subscription per page, each with `{ cursor, numItems, endCursor }`; the first page starts at `cursor: null`, the next at the previous page's `endCursor`, and the last page is the one whose first read answered `isDone: true`, subscribed with no `endCursor` so that it follows rows added after it (E-24, F15, Probe 5)
- fnRebuild: `export const rebuild = query({ args: { tenantId: v.string(), streamId: v.string(), maxEvents: v.optional(v.number()) }, returns: rebuildResultValidator, handler })` calls `rebuildStream` with `maxEvents` and, on a fold, compares with the saved row by deep equality; `maxEvents` is the events the caller may still read in its own transaction, which the restore's stream check passes per stream, and it is lowered to `maxFoldEvents` when larger (D3, D5, Sc L2-7, E-24, E-42)
- typeRebuildResult: `type RebuildResult = { kind: "folded"; state: Value; version: number; fromBaseline: number | null; eventsApplied: number; savedVersion: number; equal: boolean } | { kind: "refused"; reason: "tailTooLong" | "awaitingBaseline" | "budgetExhausted"; tailLength: number; maxFoldEvents: number; savedVersion: number; savedSchemaVersion: number; currentSchemaVersion: number }` where every refusal comes from `rebuildStream` before any event is read; `tailTooLong` and `awaitingBaseline` are what the restore's journal check records as findings, `awaitingBaseline` naming a stream saved under an older meaning that no command or sweep batch has migrated yet, and `budgetExhausted`, returned when the tail exceeds the caller's `maxEvents` but not `maxFoldEvents`, is the point where a batching caller stops and resumes next time, never a finding (E-24, E-25, E-42, F13)
- validatorRebuildResult: `const rebuildResultValidator = v.union(v.object({ kind: v.literal("folded"), state: v.any(), version: v.number(), fromBaseline: v.union(v.number(), v.null()), eventsApplied: v.number(), savedVersion: v.number(), equal: v.boolean() }), v.object({ kind: v.literal("refused"), reason: v.union(v.literal("tailTooLong"), v.literal("awaitingBaseline"), v.literal("budgetExhausted")), tailLength: v.number(), maxFoldEvents: v.number(), savedVersion: v.number(), savedSchemaVersion: v.number(), currentSchemaVersion: v.number() }))` (E-24, E-25, E-42)
- fnByOperation: `export const byOperation = query({ args: { tenantId: v.string(), operationId: v.string() }, returns: v.array(eventEnvelopeValidator), handler })` ranges `by_operation` and collects, for diagnosis and for a receipt's stream versions (D2, D19)
- paginationShape: `paginationOptsValidator` from `convex/server` in `args` and `paginationResultValidator(item)` from the same module in `returns`, for every list of the platform, in a context and in the parent; the validator requires `page`, `isDone` and `continueCursor` and admits `pageStatus` and `splitCursor` absent, `null` or set, which covers the helper's result and the built-in's (S4, E-24, Probe 5)
- ordersExample: `export const get = defineGet(journal, orderStream)` and `export const list = defineList(journal, orderStream)` in the Orders context's `queries/order.ts`, where `orderStream.dto` is `orderDtoValidator`, so `get` returns `v.union(orderDtoValidator, v.null())` and `list` returns `paginationResultValidator(orderDtoValidator)` (D8, E-24)
- parentPassThrough: `export const listOrders = query({ args: { tenantId: v.string(), paginationOpts: paginationOptsValidator }, returns: paginationResultValidator(orderDtoValidator), handler: async (ctx, args): Promise<PaginationResult<OrderDto>> => { await authorizeQuery(ctx, { name: "listOrders", tenantId: args.tenantId, permission: "orders.read" }); return (await ctx.runQuery(components.orders.queries.order.list, args)) as PaginationResult<OrderDto>; } })` where `OrderDto` is the type of `orderDtoValidator`, the tenant is the `tenantId` argument, never inferred from the identity, `authorizeQuery` is the one call that establishes and authorizes the actor, the production composition names no service issuer and so passes none, a composition that names some passes the set it gives `publicCommand`, and the handler states its return type, the DTO type, because it calls a function reference of its own deployment, casting the component's answer to it once because the context's query is typed as returning a `Value` (D11, Law 11, Law 5, F15, S4, E-6, E-24)
- parentGet: `export const getOrder = query({ args: { tenantId: v.string(), orderId: v.string() }, returns: v.union(orderDtoValidator, v.null()), handler: async (ctx, { tenantId, orderId }): Promise<OrderDto | null> => { await authorizeQuery(ctx, { name: "getOrder", tenantId, permission: "orders.read" }); return (await ctx.runQuery(components.orders.queries.order.get, { tenantId, streamId: orderId })) as OrderDto | null; } })` with the component's answer cast once to the DTO type, as `parentPassThrough` does (D8, D11, Law 5, F15)
- dtoMapping: `registration.toDto(state, meta)` is the only path from state to a DTO, so the private schema stays private; the DTO validator is the registration's and pins the shape, and every DTO carries `version: StreamVersion` built from `meta`, which the adapter's `streams` entries, the projection's version compare and the backfill all read (D8, D12, E-24)
- tenantNarrowing: every index read of a query leads with the `tenantId` argument, and no query reads a row of another tenant; a DTO policy that hides fields from some actors is not designed here (Law 5, Law 11, D11, F11)
- reactivityAssumption: a client subscription to the parent query re-runs when the component's tables change; this is F15, which the docs state and Probe 5 showed (F15, Probe 5)
- limitListPage: `limitListPage(budgetBytes) = max(1, min(100, floor(4 MiB / budgetBytes)))` items per page, where `budgetBytes` is the whole stream's budget: 16 at the default 256 KiB, 8 at the 512 KiB cap and 100 at 40 KiB or less; it is the cap on `numItems`, and the row cap is twice it, so a page reads at most 8 MiB and one row at whole budgets on the first run and on a run to an end cursor alike, because the size the paginator adds is the stored row's, `_id` and `_creationTime` beside the budgeted fields, and it checks the bound after the row that reaches it, and a full first page is never marked `SplitRequired` (F13, F20, E-2, E-24, S4, Probe 5)
- limitListBytes: 8 MiB, passed as `maximumBytesRead` on every `list` page; the helper stops at the row that reaches it, so one page reads at most 8 MiB and one row, half the 16 MiB read ceiling with room to spare (F13, E-2, E-24)
- limitHistoryPage: 250 events per page as the cap on `numItems`, with a row cap of 500, twice the item cap, which at the 16 KiB payload bound plus the envelope reads under 9 MiB, plus the baseline events the page spans at up to the stream's `budgetBytes` each, of which a stream carries one per change of meaning; a run to an end cursor is bounded by the row cap the same way (F13, E-2, E-12, E-24)
- limitHistoryBytes: 9 MiB, passed as `maximumBytesRead` on every `history` page, under the 16 MiB ceiling with room for the stream row a parent reads beside it (F13, E-12, E-24)
- limitRebuildRead: [extension] the rebuild query reads the stream row first, refuses with `awaitingBaseline` when its `stateSchemaVersion` is behind the registration's, and refuses with `tailTooLong` when the events after the latest baseline exceed the journal's `maxFoldEvents` of 500; a fold that runs reads at most 500 events of at most `limitEventBytes` of `spec:context.event-envelope` each, 20,480 bytes and the 61 bytes of a stored document's system fields, with the stored row of at most `budgetBytes + 61` bytes for a single mapping, where a derived mapping adds 61 bytes for each of its documents, and the stored baseline event of at most `budgetBytes + 4,096 + 61` bytes, at most 11,323,294 bytes in all for a single mapping at the 512 KiB cap on `budgetBytes`, under 10.9 MiB, and the 1 second query timeout, not the read ceiling, is the limit that binds first, which the first experiment measures (F13, E-2, E-12, E-25, D5)
- observedFullLastPage: [extension] on the pinned backend with `convex-helpers` 0.1.124, a full last page reports `isDone` false and the page after it is empty with `isDone` true: 30 rows read in pages of 10 come back as three full pages and a fourth empty one (E-24, Probe 5)
- registeredFunctions: one query per definer a context calls: `get` and `list` per stream type it serves, `history` and `rebuild` where it inspects its journal, and one `byOperation` per context (Decision method rule 2, E-22)

## Verification — reviewed

- A reviewer confirms that every context query's `args` include `tenantId` and no second scope argument, that none reads `ctx.auth`, and that every DTO is produced by the registration's `toDto`.
- A reviewer confirms that every parent query on tenant data takes `tenantId` in its `args` and calls `authorizeQuery` before its first read or component call, and that none calls `ctx.auth` or builds an actor.
- A reviewer confirms that every list makes one `paginate` call with the options of `boundedPage`, returns through `paginationResultValidator`, that a context list calls `paginator` and never the built-in `.paginate()`, and that no client code of the repository uses a pagination hook across the component boundary, the Probe 5 example that records the hook's behavior aside.
- A reviewer confirms that the `rebuild` query's `maxEvents` argument is read before any event and that `budgetExhausted` is never recorded as a finding by any caller.
