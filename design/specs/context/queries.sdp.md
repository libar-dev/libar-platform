# The context queries

Layer 1 · Detail: full · Traces: D2, D5, D8, D11, D19, Law 5, Law 11, F11, F13, F15, Probe 5, S4, E-6, E-24.

A context exposes authorized queries that return DTOs. The parent authenticates and authorizes, then calls a context query through the component API with the tenant and the scope as arguments; the context reads its own tables by index and maps state to the DTO its registration declares, so its private schema stays private. The queries serve the first two rows of the read-need table, one entity's detail and an essential list, plus journal inspection and the rebuild check the first experiment needs. Pagination inside the component uses `paginator` from `convex-helpers`, because the components page states that the built-in `.paginate()` does not work in a component; the parent relays the helper's page, and Probe 5 showed reactivity and the helper's end-cursor behavior across the boundary on the pinned backend.

## Intent

- outcome: Pin the query surface of a context, its arguments, its DTO mapping and how pagination crosses the boundary (D8, E-24)
- value: One entity's detail and an essential list are served by an authorized indexed query with no projection job, and a client subscribed to the parent's query sees committed state or later (D8, F7)
- risk: The helper's page does not subscribe to its end cursor; Probe 5 showed pinned pages contiguous under live writes across the boundary, and showed the `convex-helpers/react` hook leaving out the rows between a capped page's continue cursor and its end cursor after a split, so a list capped by `maximumRowsRead` can lose rows on the client without a sign (F15, Probe 5, S4)
- risk: A reactive re-run of a page carries the page's end cursor, and the helper then reads to that cursor whatever `numItems` says, so a page whose index range fills with live inserts is bounded only by the `maximumRowsRead` and `maximumBytesRead` the query passes; a capped page comes back as `SplitRequired` with a split cursor, which costs the client one more query per split (S4, F13, E-24)
- risk: A fold reads every event since the latest baseline and deep-compares the result inside one query, so the 1 second query timeout binds before the 16 MiB read ceiling; the fold bound is provisional until the first experiment and the L2-7 example measure it (F13, E-25)
- assumption: A parent query calling a component query stays reactive (F15)
- assumption: The built-in `.paginate()` does not work inside a component and `paginator` from `convex-helpers/server/pagination` is the documented replacement, as the components page states (S4)
- assumption: The documentation says a component has no `ctx.auth`; the queries do not rest on it, because by this design's rule no component function reads `ctx.auth`, and they trust the scope the parent passes (F11, D11)

### Open questions

- [non-blocking] Probe 5 ran on 2026-10-01 on the pinned backend with `convex-helpers` 0.1.124: the parent query stays reactive, pinned pages stay contiguous, and a `SplitRequired` page crosses the boundary with its `splitCursor`; the `convex-helpers/react` hook then showed 40 of 45 rows, because it ends the second half at the capped page's `continueCursor`; slice S2 decides before it builds a list whether a context list sets `maximumRowsRead`, who closes the range to the page's end cursor, or which hook the client uses (Probe 5, F15, S4, D8, E-24)
- [non-blocking] Extension E-24: the doc says component queries are authorized and return DTOs; this Spec fixes the four queries per stream type, the operation query, the `scope` argument, the `toDto` mapping with the stream version on every DTO, pagination through `paginator`, the byte-derived page bound passed as `maximumRowsRead` and `maximumBytesRead` so that it holds on a reactive re-run with an end cursor, which the helper's source shows ignores `numItems`, the relay of `pageStatus` and `splitCursor` unchanged, the `maxEvents` argument of the `rebuild` query and its `budgetExhausted` refusal for a batching caller, and the fold refusal of the `rebuild` query; the owner confirms (D8, S4, E-24, E-42)

## Contract

- One entity's detail is an authorized component query returning a DTO (D8)
- An essential list is an indexed query over the stream rows, paginated, or a read model updated in the command (D8)
- A context query returns a deliberate DTO and its private schema stays private; a document ID never leaves the component (D8, D2)
- Every query names its tenant and takes the scope the parent established; an absent tenant is never a wildcard (Law 11, D11)
- Authorization comes before disclosure; a context query is called only after the parent authorized the caller for that tenant and scope, and the query narrows rows to the scope it was given (Law 5, D11)
- No query reads `ctx.auth` (F11)
- After a successful command, an authorized query sees the committed state or a later one (D8)
- A history query returns a stream's events in stream-version order, including the events before a baseline (D5, Sc L2-7)
- An operation query returns the events one operation produced in this context, for diagnosis by operation ID (D19)
- A rebuild query folds the stream from its journal and returns the folded state and version for the equality test; an audit-only context registers none (D3, D5)
- A component query cannot be called by a client; the parent's query calls it and returns what the client may see (S4, Law 5)
- Pagination inside a component uses `paginator` from `convex-helpers/server/pagination`, because the built-in `.paginate()` does not work in a component; the parent passes the client's `paginationOpts` through and relays the helper's page unchanged, `pageStatus` and `splitCursor` included, and a reactive client uses `usePaginatedQuery` from `convex-helpers/react`, which passes the end cursor the helper needs and splits a page the helper marks `SplitRequired` (S4, E-24, Probe 5)
- [extension] A paginated component query bounds every page in rows and bytes through the helper's `maximumRowsRead` and `maximumBytesRead`, never through `numItems` alone, because a reactive re-run that carries an end cursor reads to that cursor whatever `numItems` says; a page that hits the bound comes back with `pageStatus: "SplitRequired"` and a `splitCursor`, and the client hook fetches the two halves, so the byte-derived page bound holds on the first run and on every re-run (E-24, S4, F13)
- [extension] A list is ordered by `streamId` within a stream type; a context that needs another order adds an index and a query for it (E-24, D2)
- [extension] Every DTO a registration's `toDto` returns carries the stream's `StreamVersion` as `version`, so the parent, the projection and the backfill read one shape on the live path and on the enumeration (E-24, D8, D9)
- [extension] A `rebuild` query refuses, with a structured result rather than a read-limit error, a stream whose tail since its latest baseline exceeds the fold bound, and likewise a stream whose saved `stateSchemaVersion` is behind the registration's and so still awaits its baseline; the caller counts either refusal as a journal finding (E-24, E-25, F13)
- [extension] The parent query that relays a context query takes `tenantId` in its own `args`, reads `ctx.auth` for the actor only, authorizes that actor for that tenant through `authorize` before the component call, and never infers the tenant from the identity (E-24, Law 11, Law 5, D11)

## Design

The four stream queries are built once per stream type by `defineStreamQueries`, so their `returns` validators are the registration's DTO validator and code generation sees static exports. `scope` is the `TenantScope` of `spec:command.actor-and-scope`; the context reads `scope.tenantId` and any narrowing it carries and never widens it.

- fnDefineStreamQueries: `defineStreamQueries<S, C, E extends DomainEvent, R>(journal: Journal, registration: StreamRegistration<S, C, E, R>): { get: RegisteredQuery<"public", GetArgs, Value | null>; list: RegisteredQuery<"public", ListArgs, PaginationResult<Value>>; history: RegisteredQuery<"public", HistoryArgs, PaginationResult<EventEnvelope>>; rebuild: RegisteredQuery<"public", GetArgs, RebuildResult> }` takes every DTO validator from `registration.dto` (D8, E-24)
- fnGet: `export const get = query({ args: { tenantId: v.string(), scope: tenantScopeValidator, streamId: v.string() }, returns: v.union(registration.dto, v.null()), handler })` reads the stream through the journal's `load`, which reads the row by `by_identity` and assembles a derived state from its parts, returns `null` when absent or when `deletedAt` is set unless the DTO policy shows deleted subjects, and returns `registration.toDto(state, meta)` (D8, Law 11, E-2, E-24)
- fnList: `export const list = query({ args: { tenantId: v.string(), scope: tenantScopeValidator, includeDeleted: v.optional(v.boolean()), paginationOpts: paginationOptsValidator }, returns: paginationResultValidator(registration.dto), handler })` runs `paginator(ctx.db, schema).query("streams").withIndex("by_identity", (q) => q.eq("tenantId", tenantId).eq("streamType", streamType)).paginate({ ...paginationOpts, numItems: min(paginationOpts.numItems, limitListPage), maximumRowsRead: min(paginationOpts.maximumRowsRead ?? limitListPage, limitListPage), maximumBytesRead: min(paginationOpts.maximumBytesRead ?? limitListBytes, limitListBytes) })` and maps `page` through `toDto`, reading each row's parts by `by_stream_part` first under a derived mapping, so a page reads at most its rows' whole budgets on the first run and on a reactive re-run alike; a client-supplied limit is honoured only when smaller (D8, S4, E-2, E-24, F13)
- fnHistory: `export const history = query({ args: { tenantId: v.string(), scope: tenantScopeValidator, streamId: v.string(), fromVersion: v.optional(v.number()), paginationOpts: paginationOptsValidator }, returns: paginationResultValidator(eventEnvelopeValidator), handler })` runs `paginator(ctx.db, schema).query("events").withIndex("by_stream", ...)` with `.eq` on the identity fields and `.gte("streamVersion", fromVersion ?? 1)` in ascending order and paginates with `numItems` capped at `limitHistoryPage`, `maximumRowsRead: limitHistoryPage` and `maximumBytesRead: limitHistoryBytes`, each lowered to a smaller client value when one is supplied; events before a baseline are returned like any other (D5, S4, Sc L2-7, E-24, F13)
- componentPagination: `paginator` is imported from `convex-helpers/server/pagination` and called with the component's `ctx.db` and its `schema`; it takes the same `paginationOpts` and returns the same `{ page, isDone, continueCursor }` as `.paginate` plus the optional `pageStatus` and `splitCursor` that `paginationResultValidator` already admits; it does not subscribe the query to its end cursor, which is why a reactive client passes the end cursor through `usePaginatedQuery` from `convex-helpers/react` rather than the hook in `convex/react`; and when an `endCursor` is present the helper's `paginate` sets its row target to undefined and reads to that cursor, so `numItems` bounds only the first run and the two `maximum` options bound every run, returning `pageStatus: "SplitRequired"` with a `splitCursor` at the middle of the rows read when either is hit, which the hook resolves by fetching the page in two halves (S4, E-24, F13, Probe 5)
- fnRebuild: `export const rebuild = query({ args: { tenantId: v.string(), scope: tenantScopeValidator, streamId: v.string(), maxEvents: v.optional(v.number()) }, returns: rebuildResultValidator, handler })` calls `rebuildStream` with `maxEvents` and, on a fold, compares with the saved row by deep equality; `maxEvents` is the events the caller may still read in its own transaction, which the restore's stream check passes per stream, and it is lowered to `maxFoldEvents` when larger (D3, D5, Sc L2-7, E-24, E-42)
- typeRebuildResult: `type RebuildResult = { kind: "folded"; state: Value; version: number; fromBaseline: number | null; eventsApplied: number; savedVersion: number; equal: boolean } | { kind: "refused"; reason: "tailTooLong" | "awaitingBaseline" | "budgetExhausted"; tailLength: number; maxFoldEvents: number; savedVersion: number; savedSchemaVersion: number; currentSchemaVersion: number }` where every refusal comes from `rebuildStream` before any event is read; `tailTooLong` and `awaitingBaseline` are what the restore's journal check records as findings, `awaitingBaseline` naming a stream saved under an older meaning that no command or sweep batch has migrated yet, and `budgetExhausted`, returned when the tail exceeds the caller's `maxEvents` but not `maxFoldEvents`, is the point where a batching caller stops and resumes next time, never a finding (E-24, E-25, E-42, F13)
- validatorRebuildResult: `const rebuildResultValidator = v.union(v.object({ kind: v.literal("folded"), state: v.any(), version: v.number(), fromBaseline: v.union(v.number(), v.null()), eventsApplied: v.number(), savedVersion: v.number(), equal: v.boolean() }), v.object({ kind: v.literal("refused"), reason: v.union(v.literal("tailTooLong"), v.literal("awaitingBaseline"), v.literal("budgetExhausted")), tailLength: v.number(), maxFoldEvents: v.number(), savedVersion: v.number(), savedSchemaVersion: v.number(), currentSchemaVersion: v.number() }))` (E-24, E-25, E-42)
- fnByOperation: `export const byOperation = query({ args: { tenantId: v.string(), scope: tenantScopeValidator, operationId: v.string() }, returns: v.array(eventEnvelopeValidator), handler })` ranges `by_operation` and collects, for diagnosis and for a receipt's stream versions (D2, D19)
- paginationShape: `paginationOptsValidator` from `convex/server` in `args`, which admits `endCursor`, `maximumRowsRead` and `maximumBytesRead` beside `numItems` and `cursor`, and `paginationResultValidator(item)` from the same module in `returns`, which admits the optional `pageStatus` and `splitCursor`; the result is the helper's `{ page, isDone, continueCursor, pageStatus?, splitCursor? }`, and the parent's query relays it to the client unchanged, because the hook needs `splitCursor` to split a capped page (S4, E-24, Probe 5)
- ordersExample: `export const { get, list, history, rebuild } = defineStreamQueries(journal, orderStream)` in the Orders context, where `orderStream.dto` is `orderDtoValidator`, so `get` returns `v.union(orderDtoValidator, v.null())` and `list` returns `paginationResultValidator(orderDtoValidator)` (D8, E-24)
- parentPassThrough: `export const listOrders = query({ args: { tenantId: v.string(), paginationOpts: paginationOptsValidator }, returns: paginationResultValidator(orderDtoValidator), handler: async (ctx, args) => { const identity = await ctx.auth.getUserIdentity(); if (identity === null) throw new ConvexError({ code: "unauthenticated", message: "sign in" }); const actor: Actor = { kind: "human", id: identity.tokenIdentifier }; const decision = await authorize(ctx, { actor, tenantId: args.tenantId, permission: "orders.read" }); if (!decision.allowed) throw new ConvexError({ code: "forbidden", message: decision.reason }); const scope: TenantScope = { tenantId: args.tenantId }; return ctx.runQuery(components.orders.queries.order.list, { tenantId: args.tenantId, scope, paginationOpts: args.paginationOpts }); } })` where the tenant is the `tenantId` argument, never inferred from the identity, `ctx.auth` is read once for the actor only as the pipeline's public entry does, `authorize` is the helper of `spec:command.actor-and-scope` reading the grants in the same transaction, and the `scope` is derived from the authorized tenant; the client subscribes through `usePaginatedQuery` from `convex-helpers/react`, because the built-in hook cannot maintain the pagination journal across the component boundary (D11, Law 11, Law 5, F15, S4, E-6, E-24)
- dtoMapping: `registration.toDto(state, meta)` is the only path from state to a DTO, so the private schema stays private; the DTO validator is the registration's and pins the shape, and every DTO carries `version: StreamVersion` built from `meta`, which the adapter's `streams` entries, the projection's version compare and the backfill all read (D8, D12, E-24)
- scopeNarrowing: the query narrows rows to `scope` and never widens it; a DTO policy that hides fields from some actors is the context's, decided from `scope`, never from `ctx.auth` (Law 5, D11, F11)
- reactivityAssumption: a client subscription to the parent query re-runs when the component's tables change; this is F15, which the docs state and Probe 5 showed (F15, Probe 5)
- limitListPage: `min(200, floor(8 MiB / registration.mapping.budgetBytes))` rows per page, where `budgetBytes` is the whole stream, row and parts together, which is 32 rows at the default 256 KiB budget, 16 rows for a derived stream type at the 512 KiB cap and 200 rows for a stream type whose budget is 40 KiB or less, passed as the cap on `numItems` for the first run and as `maximumRowsRead` for every run, because a reactive re-run with an end cursor ignores `numItems`, so one page reads at most 8 MiB of stream documents, half the 16 MiB read ceiling, whatever the budget and however the range has filled; the query caps a larger `numItems` rather than refusing it, and a capped re-run returns `SplitRequired` (F13, E-2, E-24, S4)
- limitListBytes: 8 MiB, passed as `maximumBytesRead` on every `list` page as the byte form of the same bound, so that the helper's own byte count stops a page that `maximumRowsRead` would not, such as rows that grew after the page bound was computed (F13, E-2, E-24)
- limitHistoryPage: 500 events per page, which at the 16 KiB payload bound plus the envelope reads under 9 MiB, plus the baseline events the page spans at up to the stream's `budgetBytes` each, of which a stream carries one per change of meaning; passed as the cap on `numItems` and as `maximumRowsRead`, so a reactive re-run with an end cursor is bounded the same way (F13, E-2, E-12, E-24)
- limitHistoryBytes: 9 MiB, passed as `maximumBytesRead` on every `history` page, under the 16 MiB ceiling with room for the stream row a parent reads beside it (F13, E-12, E-24)
- limitRebuildRead: the rebuild query reads the stream row first, refuses with `awaitingBaseline` when its `stateSchemaVersion` is behind the registration's, and refuses with `tailTooLong` when the events after the latest baseline exceed the journal's `maxFoldEvents` of 600; a fold that runs reads at most 600 events of at most 17 KiB each with the row and the baseline event of at most `budgetBytes`, about 10 MiB, and the 1 second query timeout, not the read ceiling, is the limit that binds first, which the first experiment measures (F13, E-2, E-12, E-25, D5)
- registeredFunctions: four queries per stream type and one `byOperation` per context (Decision method rule 2, E-22)
- builtInS1: slice S1 built none of these queries; `get`, `list`, `history`, `rebuild` and `byOperation` wait for the slices that build queries, lists and rebuild (E-24, D8)

## Verification — reviewed

- A reviewer confirms that every query's `args` include `tenantId` and `scope`, that none reads `ctx.auth`, and that every DTO is produced by the registration's `toDto`.
- A reviewer confirms that every parent query relaying a context query takes `tenantId` in its `args` and calls `authorize` for that tenant before the component call.
- A reviewer confirms that `list` and `history` paginate through `paginator` and never through the built-in `.paginate()`, that each passes `maximumRowsRead` and `maximumBytesRead` at its own bound and never trusts a larger client value, that the parent's paginated query passes `paginationOpts` through and returns the component's result unchanged with `pageStatus` and `splitCursor`, and that the client hook is the one from `convex-helpers/react`.
- A reviewer confirms that the `rebuild` query's `maxEvents` argument is read before any event and that `budgetExhausted` is never recorded as a finding by any caller.
