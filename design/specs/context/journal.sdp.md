# The journal

Layer 1 · Detail: full · Traces: D2, D3, D5, D18, D19, Law 2, Law 3, Law 6, Law 10, Law 11, F1, F2, F8, F9, F13, S4, Existing systems, Sc L1-10, Sc L2-7, E-2, E-3, E-12, E-25.

The journal is a context's store of its events and the shared library that writes and reads it. An append names the stream version it expects and checks it by an indexed read in the same transaction. Order exists only within a stream; no deployment-wide token exists, and events in different streams relate through the operation and the cause they carry. Domain streams are rebuildable from their events by default, and the tool that keeps rebuild true through a change of meaning is the baseline event, which a migration writes and from which rebuild starts. Old events are never rewritten, and old reducer versions are not kept forever: a migration that changes meaning is registered on its stream type with the function that maps the saved state to the new meaning, and it retires once every stream has its baseline. The baseline is written by one journal helper with two callers: the persistence adapter, on the first command that loads a stream saved under an older meaning, and the parent's driver, which sweeps the streams no command reaches. No decision is therefore taken against a state of the wrong meaning, and nothing pauses writes.

The journal's boundary is the library API the persistence adapter and the queries call. The library exports `append`, `load`, `rebuild` and `defineMaintenance`, which builds the baseline writer, and nothing that patches or deletes an event. It is included by every context as code; no context shares a table with another. The baseline writer is a public function of the component, because a component's internal functions are not exposed to the parent, and the parent drives it in bounded batches from a scheduled internal mutation of its own.

## Intent

- actor: The persistence adapter, which appends and migrates a stream on load; the context queries and the rebuild test, which read; the parent's migration driver, which calls the baseline writer (D2, D5)
- problem: Without an expected-version check two appends can interleave on one stream; a global position puts a counter in every write's path; and a change of meaning in `evolve` silently breaks rebuild for every old stream (D2, D5, Sc L2-7)
- outcome: Every append is ordered within its stream by an indexed check in the same transaction, events in different streams relate through operation and cause, and a rebuild from the latest baseline gives the saved state while earlier events stay readable (D2, D5, Sc L2-7)
- value: Rebuild stays a test rather than a hope, without rewriting history or keeping every reducer, and without any global order (D5, D2)
- risk: A change of meaning costs a migration that writes a baseline per affected stream; a live stream pays it on its first command after the deploy, and a cold stream waits for the driver's sweep, during which its rebuild is refused as awaiting its baseline rather than folded under the wrong meaning (D5, E-25)
- risk: A migration that reads history makes the first command on each of its streams read that stream's tail, at most `maxFoldEvents`; an operation that plans many such streams in that window can exceed the read ceiling and fails as a technical failure until the sweep reaches them, so a history-reading migration is the exception (E-25, F13, Law 6)
- risk: A rebuild reads the events after the latest baseline in one transaction; a stream whose tail exceeds the fold bound is refused rather than folded and needs a baseline or the snapshot tier trigger, and the 1 second query timeout binds before the read ceiling, so the bound is provisional until the first experiment measures a fold (F13, D18, E-25)
- risk: A baseline is an event at the next stream version, so a migration advances every migrated stream by one; a caller holding a reviewed version across the sweep is answered `staleVersion` on its next command and re-reviews from the `current` the details carry, every read-model row whose source the sweep touched has `sourceVersions` one behind its stream until the next command or verify pass rewrites it, and a client comparing the versions its last command returned with a subscription sees a version it never wrote; a meaning change is therefore rolled out in a maintenance window or under the tenant's write pause, and the driver reads the gate before every batch (D2, D5, Sc L1-10, E-25, E-8)
- assumption: Mutations are serializable under optimistic concurrency, so the indexed read that checks the version puts the stream in the read set and the engine serializes concurrent appends (F1)

### Open questions

- [non-blocking] Extension E-25: the doc says a migration writes a baseline event holding the migrated state and that rebuild starts from the latest baseline, and it does not say who computes that state, who drives the migration, or what a live command does on a stream the migration has not reached; this Spec fixes the representation, an event of the reserved type `baseline` whose payload holds the state and its schema version and is bounded by the stream's `budgetBytes` instead of the payload bound, a `baselineVersion` on the stream row, a `BaselineMigration` registered on the stream type whose `migrate` function computes the migrated state from the saved state and optionally the events since the last baseline, the rule that `stateSchemaVersion` counts meaning only and lives on the registration, one helper `migrateToSchemaVersion` that writes the baseline chain, called by the adapter on load for a live stream and by the `writeBaseline` maintenance mutation for the sweep, the code-older-than-data error, the `writeBaseline` mutation built by `defineMaintenance` and declared with the component's public `mutation` builder, the parent-side scheduled chain that drives it by cursor, the batch bound derived from `budgetBytes`, the upcasting rule for old event schema versions, the fold bound of 500 events with the refusals `rebuildStream` returns above it and for a stream awaiting its baseline, the retirement rule for a migration, and the payload byte check in `append`; the option of refusing commands on unmigrated streams with a transient code until the sweep arrives was not taken because it turns a deploy into a partial write pause the doc reserves for history-dependent views; a consequence the owner should weigh is that every baseline bumps its stream's version, so a reviewed version held across the sweep is answered `staleVersion` and re-reviewed rather than silently accepted, because Sc L1-10 forbids reinterpreting a reviewed version against fresh state and the baseline is a real event of the stream, while a live stream migrated on load never trips it because its expected-version check runs before the chain; and the driver reads the write pause's gate before every batch and reschedules itself when refused, so a sweep never changes a source under a paused rebuild's cut; the owner confirms (D5, D9, S4, Sc L1-10, E-2, E-8, E-12, E-25)

## Behavior

- rule: An append names the stream version it expects; the check is an indexed read in the same transaction, and an index alone is not a unique constraint (D2, F1)
- rule: Order exists only within a stream; no deployment-wide order token exists (D2)
- rule: Timestamps, `_creationTime` and UUID order never prove that a consumer has seen every committed event (D2)
- rule: Events in different streams relate through `operationId` and `causedBy`, and a receipt may list the stream versions one operation touched (D2)
- rule: The starting indexes are stream replay, event identity and stream enumeration; others are added when a real query needs them (D2)
- rule: [extension] The operation index `by_operation` starts with the three, because two real queries need it from Layer 1: the restore's receipt check and diagnosis by operation ID, both of which D19 names; the doc's three-index start is extended under E-3 (E-3, D2, D19)
- rule: Domain streams are rebuildable from their events by default (D5)
- rule: When a change in meaning leaves old events unable to reproduce current state, the migration writes a baseline event holding the migrated state, and rebuild starts from the latest baseline (D5)
- rule: Earlier events stay as readable history; old events are never rewritten; old reducer versions are not kept forever (D5)
- rule: A change of representation without a change of meaning is a schema migration, not an event, and a `schemaVersion` field alone is not schema evolution (D5)
- rule: Replay and rebuild never run original commands or repeat external effects (Law 10)
- rule: In a rebuildable domain, events are the only source of the next state (Law 3)
- rule: Incomplete history in an existing system stays audit-only or gets a baseline event that starts a rebuildable epoch; past business events are never invented (Existing systems, D5)
- rule: Rebuilding a stream that has a baseline event equals the saved state, and the earlier events are still readable (Sc L2-7)
- rule: [extension] The journal library exports no function that patches or deletes an event; the events table is append-only by construction of its only writer (E-25, D5)
- rule: [extension] A baseline is an event of the reserved type `baseline` at the next stream version, whose payload holds the migrated state and its schema version; `evolve` never sees it, because rebuild takes its payload as the start (E-25, D5)
- rule: [extension] A payload whose `eventSchemaVersion` is older than the current one is upcast in `evolve` until a baseline retires it; the stored event is never touched (E-25, D5)
- rule: [extension] A command that loads a stream whose saved `stateSchemaVersion` is behind the registration's runs the registered baseline chain on that stream first, inside its own sub-transaction and before `decide`, so no decision is taken against a state of the wrong meaning; the driver's sweep migrates the streams no command reaches, and nothing pauses writes (E-25, D3, D5, Law 2)
- rule: [extension] A stream row whose `stateSchemaVersion` is ahead of the registration's, or a chain with a gap between the row's version and the registration's, is a plain error and a technical failure, never a rejection, because the code is older than the data or a migration was not registered (E-25, Law 6)
- rule: [extension] `stateSchemaVersion` counts meaning: it is declared once on the stream type's registration, every bump of it is one registered `BaselineMigration`, and a change of representation rewrites rows through the mapping and moves nothing (E-25, D5)
- rule: [extension] A `BaselineMigration` leaves its registry only after the sweep has reported no stream below its `toSchemaVersion` in every tenant; until then a cold stream may still need it, and removing it earlier is the gap the rule above names (E-25, D5)
- flow: The adapter loads the stream row by the identity index and takes its version as the expected version; when the command names a reviewed version, the adapter compares it with the row's version and rejects a mismatch as `staleVersion` before `decide` runs, which is step 3 of `spec:context.persistence-adapter` (D2, Sc L1-10)
- flow: When the loaded row's `stateSchemaVersion` is behind the registration's, the adapter calls `migrateToSchemaVersion`, which appends one baseline event per registered step at the next versions, carrying the command's operation and actor and `causedBy` of kind `migration`, and hands back the migrated state at the advanced version; the command's events follow the baselines and the row is saved once, which is step 3a of `spec:context.persistence-adapter` (D5, D3, Law 2, E-25)
- flow: Before writing, `append` reads the events index from the expected version up, which puts the stream's range in the transaction's read set so the engine serializes concurrent appends; an event above the expected version, or no event at a nonzero expected version, means the stream row and the events index disagree, which is a defect that throws a plain error, never a rejection, because the caller-named case was already answered from the row (D2, F1, Law 6)
- flow: The adapter inserts the new events at consecutive versions through `append` and then saves the stream row once with the last version, at its step 9, in the same transaction (D2, Law 2)
- flow: A rebuild reads the baseline event at the row's `baselineVersion` when there is one, folds `evolve` over the events with a greater version from the baseline's state or from `initial()`, and compares state and version with the saved row (D3, D5, Sc L2-7)
- flow: A migration that changes meaning is registered on its stream type as a `BaselineMigration` with a name, the state schema versions it goes from and to, and a `migrate` function, and the registration's `stateSchemaVersion` is raised to its target in the same deploy; from that deploy on, live streams migrate on their first command and the parent's driver calls `maintenance.writeBaseline` through `ctx.runMutation` once per bounded batch and schedules itself with the returned cursor until the enumeration is done (D5, D19, F2, F8, E-25)
- flow: Each `writeBaseline` batch enumerates the tenant's streams of that type after the cursor, skips every stream already at or past the target version, which a live command or an earlier batch brought there by writing its baseline, and for every other stream calls the same `migrateToSchemaVersion` helper, which computes the migrated state with `migrate` from the loaded state and, when the migration asks for it, the events since the last baseline, and inserts one baseline event per step at the next versions; the batch then saves the row, all in one sub-transaction, and never rewrites an earlier event (D5, D19, Law 2, E-25)

## Design

The library is generic over the component's data model and is instantiated once per context with its `contextId` and its history mode. It owns the two tables of `spec:context.tables` and the envelope of `spec:context.event-envelope`. Every read it makes is an index range that leads with `tenantId`; every write is an insert of an event or an insert or replace of a stream row.

- transactionBoundary: the same component sub-transaction as the operation that appends; the journal opens no transaction of its own (D2, F2)
- fnCreateJournal: `createJournal(config: { contextId: string; history: "rebuildable" | "auditOnly" }): Journal` returns the configuration frozen (D2, D5, E-25)
- typeJournal: `type Journal = { readonly contextId: string; readonly history: "rebuildable" | "auditOnly" }` (D2, D5)
- typeStreamRegistration: `type StreamRegistration<S, C, E extends DomainEvent, R> = { decider: Decider<S, C, E, R>; mapping: StateDocumentMapping<S>; stateSchemaVersion: number; eventValidators: Record<string, Validator<unknown, "required", string>>; dto: Validator<Value, "required", string>; toDto: (state: S, meta: StreamMeta) => Value; baselineMigrations: readonly BaselineMigration<S>[] }` declared once per stream type, where `stateSchemaVersion` is the version the current `evolve` produces, `mapping.budgetBytes` is the stream document budget every byte-derived bound reads, `dto` is the validator of what `toDto` returns, `toDto` carries `meta`'s stream version on the DTO as `version: StreamVersion` as `spec:context.queries` pins, and `baselineMigrations` is the static registry of the migrations that may write a baseline for this stream type (D2, D3, D5, D8, E-2, E-24, E-25)
- typeBaselineMigration: `type BaselineMigration<S> = { name: string; fromSchemaVersion: number; toSchemaVersion: number; readsHistory: boolean; migrate: (saved: unknown, history: readonly EventEnvelope[]) => S }` where `saved` is the stream's state as `load` assembles it under the old meaning and `history` is the events after the stream's latest baseline when `readsHistory` is true, otherwise an empty array; the registered migrations form one chain, each step's `fromSchemaVersion` equal to the previous step's `toSchemaVersion` and the last step's `toSchemaVersion` equal to the registration's `stateSchemaVersion` (D5, E-25)
- migratedStateSource: the migrated state is `migrate(saved, history)`; the saved state is the input because it is the old reducer's fold, kept current by every command, so the migration needs no old reducer and reads events only when it declares `readsHistory` to derive something the old state never held (D3, D5, E-25)
- typeStreamMeta: `type StreamMeta = { tenantId: string; contextId: string; streamType: string; streamId: string; streamVersion: number; stateSchemaVersion: number; deletedAt?: number; baselineVersion?: number }` where `stateSchemaVersion` is the meaning version the row was saved under, which the adapter compares with the registration's on load (D2, E-25)
- typeLoadedStream: `type LoadedStream<S> = { state: S; version: number; exists: boolean; meta: StreamMeta; rowId?: GenericId<"streams">; parts?: Record<string, unknown> }` where `rowId` is the stream row's document ID, set when the row exists, by which the adapter's step 9 replaces the row (D3, E-2, E-23)
- fnLoad: `load<S, C, E extends DomainEvent, R>(ctx: QueryCtx | MutationCtx, journal: Journal, registration: StreamRegistration<S, C, E, R>, tenantId: string, streamId: string): Promise<LoadedStream<S>>` reads the stream row by `by_identity` and, for a derived mapping, its parts by `by_stream_part`, and returns `initial()` at version 0 with the registration's `stateSchemaVersion` on `meta` when no row exists, so a new stream never needs a baseline (D3, E-1, E-2, E-25)
- fnAppend: `append<S, E extends DomainEvent>(ctx: MutationCtx, journal: Journal, loaded: LoadedStream<S>, envelope: EnvelopeInput, events: readonly E[], expectedVersion: number): Promise<AppendResult>` where `AppendResult = { firstVersion: number; lastVersion: number; envelopes: EventEnvelope[] }` holds the envelopes `append` inserted, in version order; `append` reads `loaded` to throw a plain error when the envelope names a tenant, stream type or stream ID other than `loaded.meta`'s or a context other than the journal's (D2, E-23, E-25)
- appendCheck: `append` reads `by_stream` with `.eq` on tenant, stream type and stream ID and `.gte("streamVersion", expectedVersion)`, takes two, and throws a plain error when either is above `expectedVersion`, or when `expectedVersion` is not zero and no event is at it, because the stream row then names a version the journal does not hold; the read puts the stream's range in the transaction's read set (D2, F1)
- appendWrites: one `ctx.db.insert("events", envelope)` per event at versions `expectedVersion + 1` to `expectedVersion + n`, and no stream row, which its caller saves once, the adapter at its step 9 or `writeBaseline` after the chain; an append of zero events throws a plain error (D2, Law 2)
- limitPayloadBytes: `append` measures each validated payload with `getConvexSize` of `convex/values` before the insert and throws a plain error, a developer error and a technical failure, when it exceeds 16,384 bytes, so the bound of `spec:constraints.events-stay-small` has one producer and is never a rejection; the one exception is an event of the reserved type `baseline`, whose payload holds the whole migrated state and is bounded instead by the stream type's `budgetBytes`, at most 512 KiB, so that it stays inside one document with its envelope (E-12, E-2, D19, Law 6)
- limitEnvelopeCheck: [extension] `append` measures, for every event it inserts, the envelope beside the payload, `getConvexSize(event) - getConvexSize(event.payload)`, against `limitEnvelopeBytes`, 4,096 bytes, of `spec:context.event-envelope`, after the payload check and before the insert, and throws a plain error above it whose message names the event type, the measured bytes and the bound, each number in decimal digits with no separator; an envelope of exactly 4,096 bytes is inserted, so no stored event other than a `baseline` measures above `limitEventBytes`, 20,480 bytes (F13, D19, Law 6, E-12)
- fnRebuild: `rebuildStream<S, C, E extends DomainEvent, R>(ctx: QueryCtx, journal: Journal, registration: StreamRegistration<S, C, E, R>, tenantId: string, streamId: string, maxEvents?: number): Promise<{ kind: "folded"; state: S; version: number; fromBaseline: number | null; eventsApplied: number } | { kind: "refused"; reason: "tailTooLong" | "awaitingBaseline" | "budgetExhausted"; tailLength: number; maxFoldEvents: number; savedSchemaVersion: number; currentSchemaVersion: number }>` where `maxEvents` is the caller's remaining event budget for this transaction, at most `maxFoldEvents`, which the restore's stream check passes so that its batch never folds past the bound (D3, D5, Sc L2-7, E-25, E-42)
- rebuildReads: the stream row first, by `by_identity`; when its `stateSchemaVersion` is behind the registration's the function returns the refusal `awaitingBaseline` without reading an event, because the current `evolve` cannot fold the old meaning and the stream's baseline is still to come from a command or the sweep; when `streamVersion - (baselineVersion ?? 0)` exceeds `maxFoldEvents` it returns `tailTooLong` without reading an event; when it exceeds `maxEvents` but not `maxFoldEvents` it returns `budgetExhausted` without reading an event, which is a resume point for a batching caller and never a finding about the stream; otherwise `by_stream` with `.eq` on the three identity fields and `.gte("streamVersion", baselineVersion ?? 1)` in ascending order, collected in one transaction, the baseline event first when there is one (D5, F13, E-25, E-42)
- limitFoldEvents: [extension] `maxFoldEvents` is 500 events since the latest baseline, provisional; at `limitEventBytes` of `spec:context.event-envelope`, 20,480 bytes and the 61 bytes of a stored document's system fields, a fold reads at most 10,270,500 bytes of events, under 9.8 MiB, and at most 11,323,294 bytes, under 10.9 MiB, with the stored stream row of at most `budgetBytes + 61` bytes for a single mapping, where a derived mapping adds 61 bytes for each of its documents, and the stored baseline event of at most `budgetBytes + 4,096 + 61` bytes, at the 512 KiB cap on `budgetBytes`, which leaves more than 5 MiB of headroom under the 16 MiB ceiling, and the 1 second query timeout for folding and deep-comparing that much binds first, so the first experiment and the L2-7 example measure it; the same bound applies to the tail a history-reading migration step reads, and a longer tail is a plain error there (F13, E-2, E-12, E-25)
- baselineEvent: `eventType: "baseline"`, `eventSchemaVersion: step.toSchemaVersion`, `payload: { state, stateSchemaVersion: step.toSchemaVersion }` where `state` is what the step's `migrate` returned, `causedBy: { kind: "migration", migrationName: step.name }`, `operationId` and actor those of the driver's run or of the command that migrated the stream on load, at the stream's next version; `evolve` never sees it (D5, E-25, E-26)
- fnMigrateToSchemaVersion: `migrateToSchemaVersion<S, C, E extends DomainEvent, R>(ctx: MutationCtx, journal: Journal, registration: StreamRegistration<S, C, E, R>, loaded: LoadedStream<S>, envelope: EnvelopeInput, toSchemaVersion: number): Promise<LoadedStream<S>>` is the one writer of baseline events; it throws a plain error when `loaded.meta.stateSchemaVersion` is above `toSchemaVersion` or when the registered chain from that version to `toSchemaVersion` has a gap, and otherwise runs the chain step by step: read the tail by `by_stream` above `baselineVersion ?? 0` when the step reads history, a tail above `maxFoldEvents` being a plain error, compute `step.migrate(saved, history)`, `append` one baseline event at `loaded.version + 1`, and continue from the migrated state; it returns the loaded stream at the advanced version with `baselineVersion` and `stateSchemaVersion` updated on `meta`, and saves no row, which its caller does once (D5, D3, Law 2, Law 6, E-25)
- migrateToSchemaVersionCallers: the persistence adapter calls it at step 3a with `registration.stateSchemaVersion` for a stream whose row is behind, before `decide` and after the expected-version check, so the caller's reviewed version is compared with what the caller could have seen; `writeBaseline` calls it with the named migration's `toSchemaVersion` for every stream of its batch that is behind; both paths write the same events and the same row fields, so state and history agree whichever path a stream took (D3, D5, Sc L1-10, E-25)
- baselineRow: the caller of `migrateToSchemaVersion` saves the stream row with `baselineVersion` and `streamVersion` from the returned `meta`, `stateSchemaVersion: toSchemaVersion`, `lastOperationId` and the migrated state written through the registration's `mapping`, so a derived mapping writes its parts too, in the same transaction as the baseline inserts; the adapter saves it at step 9 after the command's own events, `writeBaseline` right after the chain (D5, E-2, E-25)
- fnDefineMaintenance: `defineMaintenance(journal: Journal, registrations: readonly StreamRegistration<any, any, any, any>[]): { writeBaseline: RegisteredMutation<"public", WriteBaselineArgs, WriteBaselineResult> }`, whose args and result are the validators pinned on `fnWriteBaseline`, resolves the stream type and the migration name against the registrations' `baselineMigrations` at call time, and the component exports its result as `export const { writeBaseline } = defineMaintenance(journal, [orderStream])` in its `maintenance` module (D5, D12, E-25)
- fnWriteBaseline: `export const writeBaseline = mutation({ args: { tenantId: v.string(), streamType: v.string(), migrationName: v.string(), actor: actorValidator, operationId: v.string(), correlationId: v.optional(v.string()), afterStreamId: v.optional(v.string()), maxStreams: v.optional(v.number()) }, returns: v.object({ written: v.number(), skipped: v.number(), eventsRead: v.number(), nextAfterStreamId: v.union(v.string(), v.null()) }), handler })` is what `defineMaintenance` builds, with the component's own `mutation` builder (D5, D19, S4, E-25)
- writeBaselineBuilder: `writeBaseline` is declared with `mutation`, not `internalMutation`, because only a component's public functions are exposed to the parent and they become internal references there, callable with `ctx.runMutation` and unreachable from clients; an `internalMutation` in the component would be invisible to the driver (S4)
- writeBaselineSequence: resolve the registration by `streamType` and the migration by `migrationName`, a miss being a plain throw, and let `streamBound` be `min(maxStreams ?? limitBaselineBatch, limitBaselineBatch)`; read `by_identity` with `.eq` on `tenantId` and `streamType` and `.gt("streamId", afterStreamId)` when a cursor is given, taking `streamBound` rows; for each row in order skip it when its `stateSchemaVersion` is at or past `toSchemaVersion`, which a live command or an earlier batch reached by writing its baseline, throw a plain error when it is above the registration's `stateSchemaVersion`, and otherwise, when the byte estimate below allows one more stream, load it, call `migrateToSchemaVersion` with `toSchemaVersion` and save the row; return the counts, `written` counting baseline events, and, as the cursor, the last `streamId` processed, or `null` when the page was shorter than `streamBound` and every row of it was processed (D5, D19, E-25)
- writeBaselineOperationRef: every baseline event of one migration run carries the driver's `operationId`, the optional `correlationId`, `causedBy: { kind: "migration", migrationName }` built by the handler, and the operator or service actor the driver passes, so the run is diagnosable by operation ID like any other write (D2, D19, E-26)
- writeBaselineIdempotence: a stream already at the target schema version is skipped, so a driver restarted without a cursor after a failed batch rewrites nothing and writes no second baseline for the same migration; a stream a live command migrated first is skipped the same way, by its stamp, which the adapter writes only after the chain wrote the baseline (D19, E-25)
- limitBaselineBatch: [extension] `limitBaselineBatch` is `min(100, floor(4 MiB / registration.mapping.budgetBytes))` baseline events per `writeBaseline` call, a row several steps behind counting once per step; that is 16 at the default 256 KiB budget, 8 for a derived stream type at the 512 KiB cap and 100 for a budget of 40 KiB or less; each stream is read once at its budget and written twice, the row with its parts and the baseline event holding the state, so a call reads at most 4 MiB of stream documents and writes at most 8 MiB of state and under 0.4 MiB of baseline envelopes and system fields at `limitEnvelopeBytes + 61` bytes each, in at most 100 rows, their parts and 100 baseline events; when the migration reads history the call also keeps a running byte count of the tails it read and, before each further stream, adds that stream's tail length times 20,541 bytes, `limitEventBytes` of `spec:context.event-envelope` plus the 61 bytes of a stored document's system fields, ending the batch before the stream that would take the sum past 4 MiB, 204 events at the bound, while the first stream of a batch is always processed with a tail of at most `maxFoldEvents`; one call therefore reads under 4 MiB of stream documents plus the larger of 4 MiB of tail events and one tail of under 9.8 MiB, and under 32,000 documents because the smallest envelope is several hundred bytes, against the 16 MiB read, 16 MiB written, 32,000 scanned and 16,000 written ceilings (D19, F13, E-2, E-12, E-25)
- baselineDriver: the driver is a parent-side scheduled internal mutation chain with the same batch contract as the parent's read-model backfill; each batch first reads the write pause's gate through `gateAllows(ctx, ["all", "tenant:" + tenantId, "source:" + contextId + ":" + streamType])` of `spec:application.write-pause`, because a baseline is a write to a source stream, and when the answer is not allowed it reschedules itself after `limitDriverDeferral` with the same cursor and writes nothing; otherwise it makes one call of `ctx.runMutation(components.orders.maintenance.writeBaseline, { tenantId, streamType, migrationName, actor, operationId, afterStreamId })` and `ctx.scheduler.runAfter(0, internal.maintenance.migrateBaselines, { ..., afterStreamId: result.nextAfterStreamId })` until the cursor is `null`; scheduling from a mutation commits with it, a scheduled mutation retries internal errors and runs once, and a developer error ends the chain for the operator to restart, which is safe by idempotence; the driver is a sweep of the streams no command has reached since the deploy, and it races nothing, because a live command that reaches a stream first writes the same baseline and the sweep then skips that stream by its stamp (F2, F8, F9, D9, D19, E-8, E-25)
- limitDriverDeferral: 60 seconds between gate reads while a batch is refused, so a closed tenant, `all` or source scope delays the sweep and never ends it, and the outstanding deferred batch is one per chain (E-25, E-8, F13)
- sweepVersionBump: the adapter's step 3 compares a reviewed version with the row as loaded and before any baseline of step 3a, so a command that reaches a stream before the sweep never sees `staleVersion` from the migration; a command that reaches it after the sweep does, with `details.current` one higher than it reviewed, and re-reviews, because treating a reviewed version equal to `baselineVersion - 1` as current would reinterpret a reviewed version against a stream that changed, which Sc L1-10 forbids even when the change is a baseline (Sc L1-10, D2, D5, E-25)
- migrationWindow: between the deploy that raises a registration's `stateSchemaVersion` and the end of the sweep, a live stream is migrated by its first command, a cold stream waits for the sweep, the `rebuild` query answers `awaitingBaseline` for a stream not yet migrated instead of folding it under the wrong meaning, and no writer is paused; the window is the sweep's duration, and a migration that reads history is the one case where the first command on a stream costs a tail read (D5, D9, E-25)
- codeOlderThanData: a stream row whose `stateSchemaVersion` is above the registration's is data saved by newer code, which happens after a rollback of a deploy whose sweep or live commands already wrote baselines; `load` and `writeBaseline` throw a plain error for it, the command is a technical failure under Law 6, and the remedy is to redeploy the newer code, never to run the old `evolve` against the newer state (E-25, Law 6, D5)
- driverTenancy: the driver runs one tenant and one stream type per chain, because the enumeration index leads with `tenantId` and the parent, not the component, knows the tenants; a meaning change is rolled out by one chain per tenant (Law 11, E-25)
- driverNotMigrationsComponent: `@convex-dev/migrations` iterates a table of the deployment that defines the migration and cannot page a component's `streams` table from the parent, so the baseline migration uses the scheduled chain and not that component (S4, E-25)
- limitRebuildRead: a rebuild reads the events after the latest baseline in one transaction, at most `maxFoldEvents` of them; a stream whose tail exceeds the bound is refused and needs a baseline, and one that keeps growing past that is the snapshot tier trigger (F13, D5, D18, E-25)
- noGlobalOrder: the library exposes no query across streams ordered by anything but `streamVersion` within one stream; `by_operation` returns an operation's events in no promised order (D2)
- crossStreamRelation: `operationId` and `causedBy` on every envelope; a receipt may list the affected stream versions the operation returned (D2)
- schemaMigration: a change of representation without a change of meaning, such as a renamed field of the saved state or a switch from the single to the derived mapping, rewrites stream rows and parts through the new mapping in bounded batches, with a mapping that reads the old shape until the rewrite is done; it touches no event, writes no baseline and does not move `stateSchemaVersion`, which counts meaning only, so the adapter's on-load comparison never mistakes a representation change for a change of meaning (D5, E-2, E-25)
