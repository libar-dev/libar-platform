# Projection contract

Story · Detail: full · Traces: D8, D9, Law 6, Law 10, Law 11, F1, F13, E-8, E-9.

A projection is the named, versioned, deterministic function that turns a context's DTO at a stream version into a read-model row, and `applyProjection` is the one helper that writes that row, shared by the use case's live update and the rebuild's backfill. The contract pins the projection's shape, the declaration of a per-entity read model, which names its table and row budget and holds its projection, the row conventions every read model follows, the write rule that decides between insert, update and skip, the aggregate form with its per-entity marker, and the history form that folds the events of several streams into one row. Everything here is an extension of D8 and D9: the doc fixes the properties, this contract fixes the signature.

## Intent

- outcome: Pin the projection signature shared by live update and rebuild, and the row conventions (tenant, generation, key, source versions) every read model follows (D8, D9, E-9)
- value: One function per read model serves both the command path and the backfill, so a rebuild cannot disagree with a live update, and one row shape lets the registry, the queries and the rebuild treat every read model the same way (D8, D9)
- risk: A projection that reads anything but its input is not deterministic and breaks rebuild equality; the reviewed check below is the only guard until a test folds a sample (D8)
- assumption: Mutations are serializable under optimistic concurrency, so the write rule's read-then-write is atomic per row (F1)

### Open questions

- [non-blocking] Extension E-9: the doc says a projection is named, versioned and deterministic and that live update and rebuild share its logic; it does not give the signature or the row shape, for counts and sums it names the marker but not the aggregate row, and for the read models that depend on history across several streams, the ones the write pause exists for, it names no input. The option taken here: a per-entity read model declared as a `ReadModel<D, Row>` with `name`, `table`, `rowBudgetBytes` and its `projections`, a list of `Projection<D, Row>` with the latest first, each holding `version`, `keyOf` and `project` alone, rows with `tenantId`, `generation`, `key`, `projectionVersion` and `sourceVersions`, one `applyProjection` helper with a mode per caller that writes each generation by its role, active, building or verifying, with the projection whose version the generation records, for an `AggregateProjection<D>` an aggregate row with `value` and `entityCount` and no `sourceVersions`, because the markers carry them, written by `applyAggregate` under the marker's version compare with the mode ignored, and for a history-dependent view a `HistoryProjection<Row>` that folds events into the prior row, fed on the live path by the events the operation appended, which the adapter's `streams` entry carries, and on the backfill by the context's `history` pages under the write pause, with `sourceVersions` recording the highest version folded per stream so that an event is never folded twice; a row that derives from more than one source stream type is a history row, its projection bound once per source stream type, and a small cross-context view of current state is D8's parent query over bounded component reads; the owner confirms the three forms and has not ruled on the split of a per-entity read model into `ReadModel` and `Projection`, on the write by generation role or on the row measured against its budget at every write (E-9, E-23, E-24, D8, D9)
- [non-blocking] Extension E-9, two projection versions: the doc says live update and rebuild share one projection and does not say how a command writes two generations built by two versions; the option taken here is that a read model declares its projection versions as a list, the latest first, and `applyProjection` writes each generation with the projection whose version the generation row records, failing as a technical failure when the read model declares none of that version, so the rows of one generation are one truth of one version; the cost is that an earlier version stays in the code while a generation that records it is written or can be rolled back to, and a projection changed without a version change is still undetected (E-9, D8, D9)
- [non-blocking] The rule that a row with a newer version is never overwritten is read as the backfill path's rule only, so a live write to the active generation always lands, as `step3` has it; the owner has not confirmed that reading (D9, E-9)
- [non-blocking] Extension E-9, the history fold: D2 orders events only within a stream, and the two paths feed one history row in different orders, the live path command by command and the backfill stream by stream; the option taken here is a fold that gives one row whatever the order across streams and however its events are split between calls, a row no fold deletes, which keeps its subject's ended state, and baselines dropped before `keyOf`, so a view whose meaning needs the order across streams waits for the ordered consumer of D18 (E-9, D2, D9, D18, E-25)
- [non-blocking] Extension E-9, a composite row of current state: D8 lets a small cross-context view be a read model updated in the command, and no form here writes one row from the DTOs of two sources, because `project` builds a whole row from one DTO and a backfill enumerates one source; the option taken here is D8's other default, a parent query over bounded component reads, until a view needs such a row, which then needs a form whose `project` takes the DTO of every matching entry of one command and whose backfill reads the other context in the same mutation, online (E-9, D8, E-45)
- [non-blocking] Extension E-9, the history form's one version: a `HistoryProjection` declares one version, so a deploy that changes it leaves the active generation, which records the earlier version, unwritable, and every command whose events feed the view fails as a technical failure until a generation of the new version is switched; the option taken here is that one version, because a view rebuilt under the pause is never written by two versions at once, and a list of versions like the `projections` of a `ReadModel` is the form a view takes when its sources must stay writable across such a deploy (E-9, D8, D9, Law 6)

## Contract

- A projection has a version and a pure `project` function from a DTO at its stream version to a row or `null`, and is named by the read model it maintains; the same read model and version always give the same row for the same input (D8)
- A projection reads only its input; it never queries the database, the network, the scheduler, the environment or `ctx.auth`, and it never issues commands or causes effects (D8, Law 10)
- Live update and rebuild call the same `applyProjection` with the same read model, and each generation is written by the projection of the version it records; only the mode differs (D8, D9)
- The pipeline's step 9 picks the live-created mode when the `created` flag on the operation outcome's `streams` entry for that stream is true, which the adapter sets from a load that found no row, and the live-updated mode otherwise; no use case derives the flag (D9, E-9, E-23)
- The DTO a projection receives is the same `toDto(state, meta)` on both paths, the adapter's `streams` entry on the live path and the context's `list` page on the backfill, and it carries the stream's `StreamVersion` as `version`, so no adapter between two DTO shapes exists (D8, D9, E-9, E-24)
- Every read-model row carries `tenantId`, `generation`, `key` and `projectionVersion`, a per-entity or history row carries `sourceVersions` as well, and every read-model table has the `by_key` index leading with the tenant (E-9, Law 11, D9)
- `sourceVersions` holds one `StreamVersion` per source stream the row derives from; a per-entity row holds one, and a history row one per stream whose events it folded (E-9, D2, D8)
- [extension] An aggregate row derives from every entity under its key, so it carries no `sourceVersions`; it carries `value`, the sum of the recorded contributions, and `entityCount`, the number of markers, and the per-entity marker carries the `sourceVersions` the row conventions would otherwise hold (E-9, D9)
- [extension] A read model declares its name, the parent table that holds its rows, `rowBudgetBytes`, the largest row it writes, 16 KiB by default and at most `limitRowSize`, and its projections, one per version it can still write, the latest first, with distinct versions and at least one; every version writes rows the one table's validator accepts, and a change of shape the table cannot hold beside the earlier one is a new read model; a projection is the versioned rules alone, so they are tested without a table; the rebuild derives its batch bound from the declared budget the way the context derives its page from the stream budget (E-9, E-40, F13)
- On the backfill path a row is written only if it is missing or its `sourceVersions` are older than the input's for the same stream, and a row with a newer version is never overwritten; the rule is the backfill path's only, and a live write to the active generation always lands (D9)
- In the active generation a live write always lands: a missing row is inserted and an existing row is replaced, in the live-created mode and the live-updated mode alike, because `project` sees the whole DTO and cannot build a partial row, so a subject whose row was deleted gets its row back from the next command that writes it (D9, E-9)
- In a generation in `building`, the role `building`, the live-created mode inserts or replaces the row, and the live-updated mode replaces a row the backfill has already written and skips a missing one; in a generation in `verifying` or `verified`, the role `verifying`, the backfill has ended, a missing row is a subject that projected to none, and a live write lands as it does in the active generation (D9, E-8, E-9)
- [extension] Every write of a read-model row measures the whole row, the conventions included, with `getConvexSize` and throws a plain error, a technical failure that rolls the command back, when it measures above the read model's `rowBudgetBytes`; a declared budget above the ceiling of `limitRowSize` throws the same way (E-9, F13, Law 6)
- In the backfill mode the one generation the batch names is written whatever its role: the row is inserted if missing, updated if older, and, when the DTO projects to `null`, deleted if its `sourceVersions` are older than the input's and left as `skipped-newer` otherwise, which is how a verify pass makes absence right as well as presence (D9, E-8, E-9)
- A projection may return `null` for a DTO that has no row, such as a deleted subject; `applyProjection` then deletes the row if present, in the backfill mode only when the row is older than the input, and does nothing when it is absent, and nothing records the deletion, because a backfill batch reads the source in the same mutation that writes the row, so a batch that read the subject before its deletion committed re-runs under optimistic concurrency and reads the deleted subject, as the rebuild's `occRace` states (E-9, D2, F1)
- An aggregate projection contributes a number per entity to an aggregate row and keeps a per-entity marker so live commands and backfill never count one entity twice (D9)
- [extension] `applyAggregate` ignores the mode: the marker's `sourceVersions` decide, a marker that is not older than the input makes the write `skipped-newer`, and otherwise the marker's recorded contribution leaves the row of the marker's `aggregateKey` and the new contribution joins the row of `aggregateKeyOf`, one row moved by the difference when the key is the same and two rows when it changed, a row whose `entityCount` reaches 0 being deleted, and a `null` contribution joins no row and removes the marker; a live update on an entity backfill has not reached is therefore not partial, because `contribute` sees the whole DTO, which is why the missing-row rule of the per-entity path does not apply (E-9, D9, F1)
- [extension] An aggregate's entity is its source stream: `applyAggregate` derives the marker's `entityKey` from the input's one `StreamVersion` as `JSON.stringify([contextId, streamType, streamId])`, so the live path and the backfill, which pass `entry.version` and `dto.version`, name one marker, and equal stream IDs in two contexts or two stream types name two (E-9, D9, D2)
- [extension] A history projection folds events into a row: `keyOf` maps each event to the row it belongs to or to none, and `project` folds the events of one key, each stream's in stream-version order and the streams interleaved in any order, into the prior row; it is deterministic in the prior row and the events, reads nothing else, and is the one form a read model that depends on history across several streams may take, which is why such a read model rebuilds only under the write pause (E-9, D8, D9, Law 10)
- [extension] A history projection's fold gives the same row whatever the order in which the events of different streams arrive and however they are split between calls: from one prior row, the events of one key folded in one call or in several, with the streams interleaved in any way that keeps each stream's events in version order, give equal rows; D2 orders events only within a stream, and the live path feeds a row command by command while the backfill feeds it stream by stream, so a view whose meaning depends on the order across streams is not a history projection and waits for the ordered consumer of D18 (E-9, D2, D8, D18)
- [extension] `project` never answers `null`: a history row, once written, keeps its subject's ended state, such as a cancelled order, and leaves its table only when its generation is purged, so its `sourceVersions`, the fold's one memory, outlive the subject's end, and an event that arrives after it, such as `AllocationReleased` after `OrderCancelled`, folds into the row and never makes a new one (E-9, D9)
- [extension] `applyHistoryProjection` drops every event of the reserved type `baseline` before `keyOf`, on both paths: a baseline holds a stream's migrated state and no fact a view folds, and a migration that changes what a source's earlier events mean to the view is a new projection version and so a new generation, never a rewrite of rows in place (E-9, E-25, D9)
- [extension] A history row's `sourceVersions` hold, per source stream, the highest event version folded into it; `applyHistoryProjection` drops every event whose version is not above the recorded version for its stream and skips the write when none remain, so a live update and a backfill page never fold one event twice, and the live path never meets a non-active generation of a history view, because its generation in flight exists only while its source scopes are closed and `rollbackGeneration` of `spec:application.rebuild` refuses to reopen a retired one (E-9, D9, F1)
- [extension] A history projection is bound once per source stream type on the command declaration; the pipeline's step 9 feeds it, once per command, the events of every `streams` entry its bindings match, and the backfill feeds it each source's history, so a history row has one projection and several bindings; a `Projection` or an `AggregateProjection` takes one entry's DTO, so a read model of those forms derives each row from one source stream (E-9, E-7, D8)
- A projection's version changes whenever its output for any input changes; a new version is added at the head of the read model's `projections` and is a new generation, never an in-place rewrite, and an earlier version leaves the list only when no generation in `building`, `verifying`, `verified` or `active` records it and none in `retired` is to be rolled back to (D8, D9)
- The write rule reads and writes inside one mutation, so two writers of the same row serialize under optimistic concurrency and neither overwrites newer data (F1, D9)

## Design

The shapes are TypeScript in the parent. `StreamVersion` is the kernel's shape with its `version` field, and `streamVersionValidator` is the kernel's validator; `D` is the context's DTO type; `Row` is the read-model document without the row conventions, which `applyProjection` adds. Validators use `convex/values`; the row conventions are a validator the read-model tables spread into their `defineTable`. In the write rule a row is older than the input when the entry of its `sourceVersions` whose `tenantId`, `contextId`, `streamType` and `streamId` equal the input's has a `version` below the input's; an equal version is not older, and a row that records no entry for the input's stream is older.

- typeProjection: `type Projection<D, Row extends Record<string, Value>> = { version: number; keyOf(tenantId: string, dto: D): string; project(tenantId: string, dto: D, versions: StreamVersion[]): Row | null }` (E-9, D8)
- typeReadModel: `type ReadModel<D, Row extends Record<string, Value>> = { name: string; table: string; rowBudgetBytes: number; projections: readonly [Projection<D, Row>, ...Projection<D, Row>[]] }` where `name` is the read model's key in the generation registry, `table` is the parent table that holds its rows, `rowBudgetBytes` is at most 65,536 with `defaultRowBudgetBytes` 16,384, and `projections` lists the versions the deployment can write, the latest first (E-9, D8, F13)
- fnProjectionOf: `projectionOf<D, Row extends Record<string, Value>>(readModel: ReadModel<D, Row>, version: number): Projection<D, Row>` returning the declared projection of that version and throwing the plain `Error` `"Read model " + readModel.name + " declares no projection of version " + version` when there is none, a technical failure on the command path and a refusal of `startGeneration` and `rollbackGeneration` (E-9, D8, Law 6)
- typeWritableGeneration: `type WritableGeneration = { role: "active" | "building" | "verifying"; generation: number; projectionVersion: number }`, one generation a command writes, as the registry's `generationsToWrite` returns it; the role `verifying` covers the states `verifying` and `verified` (E-8, E-9, D9)
- typeRowWriter: `type RowWriter<DataModel extends GenericDataModel = RowDataModel> = { db: GenericDatabaseWriter<DataModel> }`, the part of a ctx `applyProjection` uses, generic over the composition's data model because a database writer is not covariant in its data model; `RowDataModel` is the data model of one table that spreads `rowConventions` and has `by_key`, and the library reads and writes the read model's own table, named by its `table`, under that table's type (E-9)
- typeAggregateProjection: `interface AggregateProjection<D> { name: string; version: number; table: string; rowBudgetBytes?: number; aggregateKeyOf(tenantId: string, dto: D): string; contribute(tenantId: string, dto: D): number | null }` where `null` means the entity no longer contributes, such as a deleted subject, and `rowBudgetBytes` bounds the aggregate row and the marker alike (E-9, D9, F13)
- typeHistoryProjection: `interface HistoryProjection<Row> { name: string; version: number; table: string; rowBudgetBytes?: number; keyOf(tenantId: string, event: EventEnvelope): string | null; project(tenantId: string, prior: Row | null, events: EventEnvelope[]): Row }` where `EventEnvelope` is the envelope of `spec:context.event-envelope`, `null` from `keyOf` means the event is not this view's, `prior` is `null` before the key's first event, `events` are the events of one key not yet folded into `prior`, each stream's in version order and the streams interleaved in any order, `project` answers a row and never `null`, and `rowBudgetBytes` is 16 KiB when absent; a history row is a bounded summary of history, never a list that grows with it, so `rowBudgetBytes` binds it like any row (E-9, D8, D9, F13)
- fnApplyHistoryProjection: `applyHistoryProjection<Row>(ctx: MutationCtx, projection: HistoryProjection<Row>, input: { tenantId: string; events: EventEnvelope[]; mode: ApplyMode; generations: readonly WritableGeneration[] }): Promise<{ key: string; results: ApplyResult[] }[]>` dropping the events of type `baseline`, grouping the rest by `keyOf` in the order given and leaving out those whose key is `null`, and per key and generation reading the row by `by_key`, dropping every event whose `streamVersion` is not above the row's recorded version for the event's stream, named by the envelope's `tenantId`, `contextId`, `streamType` and `streamId`, answering `skipped-newer` when none remain, and otherwise writing `project(tenantId, prior, remaining)` with `sourceVersions` raised to the highest version folded per stream and sorted by `contextId`, then `streamType`, then `streamId`, strings compared by UTF-16 code units, so the row is one value whatever the order the streams arrived in, and answering `inserted` or `updated`, never `deleted`, in the same mutation; `mode` is read by nothing, and a generation given whose `projectionVersion` is not the projection's `version` makes it throw the plain `Error` of `projectionOf` before it reads a row, a technical failure (E-9, D8, D9, F1, Law 6)
- typeApplyMode: `type ApplyMode = "live-created" | "live-updated" | "backfill"` (E-9, D9)
- typeApplyResult: `type ApplyResult = "inserted" | "updated" | "deleted" | "skipped-missing" | "skipped-newer" | "unchanged"` (E-9, D9)
- fnApplyProjection: `applyProjection<DataModel extends GenericDataModel, D, Row extends Record<string, Value>>(ctx: RowWriter<DataModel>, readModel: ReadModel<D, Row>, input: { tenantId: string; dto: D; versions: StreamVersion[]; mode: ApplyMode; generations: readonly WritableGeneration[] }): Promise<ApplyResult[]>` writing one result per generation in the order given; the pipeline's step 9 calls it with `versions: [entry.version]` for a per-entity row and the rebuild's batch with `versions: [dto.version]` (E-9, D8, D9)
- callers: the two callers are the command pipeline's step 9, with the mode from the `streams` entry's `created` flag and the list `generationsToWrite` returned, passed unchanged, and the rebuild's backfill and verify batches in `backfill` mode for the one generation they build or verify; a use case body never calls it, and the same two callers are the only callers of `applyAggregate` and `applyHistoryProjection`; step 9 calls `applyHistoryProjection` once per history read model per command, in the live-updated mode, with the events of every `streams` entry any of its bindings matches in the order of the entries, and a history batch calls it once with its one `history` page (E-9, D8, D9, E-7)
- tableOrderAllocationHistory: `orderAllocationHistory: defineTable({ ...rowConventions, orderId: v.string(), placedAt: v.optional(v.number()), cancelledAt: v.optional(v.number()), allocations: v.array(v.object({ stockItemId: v.string(), quantity: v.number(), allocatedAt: v.number(), releasedAt: v.optional(v.number()) })) }).index("by_key", ["tenantId", "generation", "key"])` the history-dependent cross-stream view of the example domain, the `HistoryProjection` named `orderAllocationHistory` over the table of that name, keyed by order ID and folded from `OrderPlaced` and `OrderCancelled` in Orders and `StockAllocated` and `AllocationReleased` in Inventory, with one entry of `allocations` per stock item the order allocated on and `sourceVersions` holding the order stream and every stock stream folded, so a row holds at most 100 entries and 101 versions; `getConvexSize` measures the largest such row, at 256-byte tenant and order IDs and 100 stock item IDs of 64 bytes, every allocation released, at 55,803 bytes, so the view declares `rowBudgetBytes` 65,536, the ceiling; it is bound once per source stream type, rebuilds only under the write pause, and Sc L2-6 builds it (E-9, E-46, D9, F13, Sc L2-6)
- typeOrderAllocationHistoryFields: `type OrderAllocationHistoryFields = { orderId: string; placedAt?: number; cancelledAt?: number; allocations: OrderAllocation[] }` where `type OrderAllocation = { stockItemId: string; quantity: number; allocatedAt: number; releasedAt?: number }`, the projected fields of the order allocation history, in `example/domain/orderAllocationHistory.ts` (E-9, E-46, Sc L2-6)
- fnOrderAllocationHistoryKeyOf: `orderAllocationHistoryKeyOf(tenantId: string, event: HistoryEvent): string | null` in `example/domain/orderAllocationHistory.ts`, answering the stream ID of an `OrderPlaced` or an `OrderCancelled`, the payload's `orderId` of a `StockAllocated` or an `AllocationReleased`, and `null` for every other event, where `type HistoryEvent = { streamId: string; eventType: string; recordedAt: number; occurredAt?: number; payload: unknown }` is the part of `EventEnvelope` the rules read, so the example's pure domain code imports no context library (E-9, E-46, Sc L2-6)
- fnProjectOrderAllocationHistory: `projectOrderAllocationHistory(tenantId: string, prior: OrderAllocationHistoryFields | null, events: readonly HistoryEvent[]): OrderAllocationHistoryFields` in the same file, folding the events one by one into `prior`, or, when `prior` is `null`, into `{ orderId, allocations: [] }` with the key of the first event that has one, and throwing the plain `Error` `"The order allocation history needs a prior row or an event of an order"` when there is neither; the view's `HistoryProjection` holds this function and `orderAllocationHistoryKeyOf` as its `project` and `keyOf` (E-9, E-46, Sc L2-6)
- orderAllocationHistoryFold: each field is written by the events of one stream, each event's time being its `occurredAt`, or its `recordedAt` when absent: `OrderPlaced` sets `placedAt` and `OrderCancelled` sets `cancelledAt`; `StockAllocated` on a stock item sets that stock item's entry of `allocations` to the payload's `quantity` and the time as `allocatedAt`, with no `releasedAt`; `AllocationReleased` sets `releasedAt` on that entry and changes nothing when the order has none on that stock item; every other event changes nothing; `allocations` is kept sorted by stock item ID, compared by UTF-16 code units; so the fold gives one row whatever the order across streams, a stock event before `OrderPlaced` included, and a pure test folds one order's events in every interleaving of its three streams and every split into calls and finds one row (E-9, D2, Sc L2-6)
- fnApplyAggregate: `applyAggregate<D>(ctx: MutationCtx, projection: AggregateProjection<D>, input: { tenantId: string; dto: D; versions: StreamVersion[]; mode: ApplyMode; generations: readonly WritableGeneration[] }): Promise<ApplyResult[]>` answering, per generation in order, one result for each aggregate row it writes, the old key's row before the new key's on a key change, `inserted` for a row it created, `updated` for a row whose `value` or `entityCount` changed and `deleted` for a row whose `entityCount` reached 0, or one `skipped-newer` when the marker was not older and one `unchanged` when no row moved; `input.versions` holds the one `StreamVersion` of the entity's source stream, and another length throws a plain error; `mode` is accepted for symmetry with `applyProjection` and read by nothing (E-9, D9)
- aggregateStep1: for each generation it derives `entityKey` from `input.versions[0]` as the contract states, reads the marker by `by_entity` with the tenant, read model, generation and `entityKey`, and computes `contribution` as `contribute(tenantId, dto)` and, when that is not `null`, `aggregateKey` as `aggregateKeyOf(tenantId, dto)` (E-9, D9)
- aggregateStep2: when a marker exists and its `sourceVersions` are not older than `input.versions` for the same stream, the result is `skipped-newer` and nothing is written (E-9, D9, F1)
- aggregateStep3: when a marker exists and `contribution` is `null` or `aggregateKey` differs from the marker's, it reads the row of the marker's `aggregateKey` by `by_key`, throwing a plain error when it is missing, a defect, subtracts the marker's contribution from `value` and 1 from `entityCount`, and deletes the row when `entityCount` reaches 0 and replaces it otherwise; when `contribution` is not `null` and the marker is missing or its key differs, it reads the row of `aggregateKey`, inserts it with `value` equal to `contribution` and `entityCount` 1 when missing, and otherwise adds `contribution` to `value` and 1 to `entityCount`; when the marker exists with the same key and `contribution` is not `null`, it adds `contribution` minus the marker's to that row's `value`, leaves `entityCount`, and writes no row when the difference is 0; when the marker is missing and `contribution` is `null`, it reads and writes no row (E-9, D9)
- aggregateStep4: then it inserts or replaces the marker with `entityKey`, `contribution`, `aggregateKey` and `input.versions`, or deletes it when `contribution` is `null`, all in the same mutation; a key change reads and writes two aggregate rows and the marker in each generation, and its two rows count against `limitReadModelWritesPerCommand` of `spec:application.read-models` (E-9, D9, E-8, E-45)
- validatorRowConventions: `const rowConventions = { tenantId: v.string(), generation: v.number(), key: v.string(), projectionVersion: v.number(), sourceVersions: v.array(streamVersionValidator) }` spread into every per-entity and history read-model `defineTable` (E-9, Law 11)
- validatorAggregateRowConventions: `const aggregateRowConventions = { tenantId: v.string(), generation: v.number(), key: v.string(), projectionVersion: v.number(), value: v.number(), entityCount: v.number() }` spread into every aggregate read-model `defineTable`, with the same `by_key` index, where `key` is `aggregateKeyOf(tenantId, dto)` (E-9, Law 11, D9)
- tableOrderTotals: `orderTotals: defineTable({ ...aggregateRowConventions }).index("by_key", ["tenantId", "generation", "key"])` an aggregate of order totals per status, where `key` is the status, `value` the sum of the orders' totals and `entityCount` the number of orders in it, given as the shape of an aggregate table and not as a read model the first experiment builds (E-9, D9)
