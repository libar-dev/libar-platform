# Projection contract

Story · Detail: full · Traces: D8, D9, Law 6, Law 10, Law 11, F1, F13, E-8, E-9.

A projection is the named, versioned, deterministic function that turns a context's DTO at a stream version into a read-model row, and `applyProjection` is the one helper that writes that row, shared by the use case's live update and the rebuild's backfill. The contract pins the projection's shape, the declaration of a per-entity read model, which names its table and row budget and holds its projection, the row conventions every read model follows, the write rule that decides between insert, update and skip, and the aggregate form with its per-entity marker. Everything here is an extension of D8 and D9: the doc fixes the properties, this contract fixes the signature.

## Intent

- outcome: Pin the projection signature shared by live update and rebuild, and the row conventions (tenant, generation, key, source versions) every read model follows (D8, D9, E-9)
- value: One function per read model serves both the command path and the backfill, so a rebuild cannot disagree with a live update, and one row shape lets the registry, the queries and the rebuild treat every read model the same way (D8, D9)
- risk: A projection that reads anything but its input is not deterministic and breaks rebuild equality; the reviewed check below is the only guard until a test folds a sample (D8)
- assumption: Mutations are serializable under optimistic concurrency, so the write rule's read-then-write is atomic per row (F1)

### Open questions

- [non-blocking] Extension E-9: the doc says a projection is named, versioned and deterministic and that live update and rebuild share its logic; it does not give the signature or the row shape, for counts and sums it names the marker but not the aggregate row, and for the read models that depend on history across several streams, the ones the write pause exists for, it names no input. The option taken here: a per-entity read model declared as a `ReadModel<D, Row>` with `name`, `table`, `rowBudgetBytes` and its `Projection<D, Row>`, which holds `version`, `keyOf` and `project` alone, rows with `tenantId`, `generation`, `key`, `projectionVersion` and `sourceVersions`, one `applyProjection` helper with a mode per caller that writes each generation by its role, active or building, for an `AggregateProjection<D>` an aggregate row with `value` and `entityCount` and no `sourceVersions`, because the markers carry them, written by `applyAggregate` under the marker's version compare with the mode ignored, and for a history-dependent view a `HistoryProjection<Row>` that folds events into the prior row, fed on the live path by the events the operation appended, which the adapter's `streams` entry now carries, and on the backfill by the context's `history` pages under the write pause, with `sourceVersions` recording the highest version folded per stream so that an event is never folded twice; a cross-context or cross-stream row is built by one projection bound once per source stream type; the owner confirms the three forms and has not ruled on the split of a per-entity read model into `ReadModel` and `Projection`, on the write by generation role, on the row measured against its budget at every write or on the check that a generation is written only by the projection version it records (E-9, E-23, E-24, D8, D9)
- [non-blocking] Extension E-9, two projection versions: a read model holds one projection, so `applyProjection` writes every generation it is given with that projection, whatever `projectionVersion` the generation records; after a projection version change the active generation was built by the earlier version, and the owner has not ruled how a command writes two projection versions at once, the active generation's and a building generation's (E-9, D8, D9)

## Contract

- A projection has a version and a pure `project` function from a DTO at its stream version to a row or `null`, and is named by the read model it maintains; the same read model and version always give the same row for the same input (D8)
- A projection reads only its input; it never queries the database, the network, the scheduler, the environment or `ctx.auth`, and it never issues commands or causes effects (D8, Law 10)
- Live update and rebuild call the same `applyProjection` with the same projection; only the mode differs (D8, D9)
- The pipeline's step 9 picks the live-created mode when the `created` flag on the operation outcome's `streams` entry for that stream is true, which the adapter sets from a load that found no row, and the live-updated mode otherwise; no use case derives the flag (D9, E-9, E-23)
- The DTO a projection receives is the same `toDto(state, meta)` on both paths, the adapter's `streams` entry on the live path and the context's `list` page on the backfill, and it carries the stream's `StreamVersion` as `version`, so no adapter between two DTO shapes exists (D8, D9, E-9, E-24)
- Every read-model row carries `tenantId`, `generation`, `key` and `projectionVersion`, a per-entity or cross-context row carries `sourceVersions` as well, and every read-model table has the `by_key` index leading with the tenant (E-9, Law 11, D9)
- `sourceVersions` holds one `StreamVersion` per source stream the row derives from; a per-entity row holds one, a cross-context row holds one per context (E-9, D2, D8)
- [extension] An aggregate row derives from every entity under its key, so it carries no `sourceVersions`; it carries `value`, the sum of the recorded contributions, and `entityCount`, the number of markers, and the per-entity marker carries the `sourceVersions` the row conventions would otherwise hold (E-9, D9)
- [extension] A read model declares its name, the parent table that holds its rows, `rowBudgetBytes`, the largest row it writes, 16 KiB by default and at most `limitRowSize`, and its projection; the projection is the versioned rules alone, so they are tested without a table; the rebuild derives its batch bound from the declared budget the way the context derives its page from the stream budget (E-9, E-40, F13)
- A row is written only if it is missing or its `sourceVersions` are older than the input's for the same stream; a row with a newer version is never overwritten (D9)
- In the active generation a live write always lands: a missing row is inserted and an existing row is replaced, in the live-created mode and the live-updated mode alike, because `project` sees the whole DTO and cannot build a partial row, so a subject whose row was deleted gets its row back from the next command that writes it (D9, E-9)
- In a building generation the live-created mode inserts or replaces the row, and the live-updated mode replaces a row the backfill has already written and skips a missing one (D9)
- [extension] Every write of a read-model row measures the whole row, the conventions included, with `getConvexSize` and throws a plain error, a technical failure that rolls the command back, when it measures above the read model's `rowBudgetBytes`; a declared budget above the ceiling of `limitRowSize` throws the same way (E-9, F13, Law 6)
- In the backfill mode the row is inserted or updated in the building generation only, if missing or older (D9)
- A projection may return `null` for a DTO that has no row, such as a deleted subject; `applyProjection` then deletes the row if present and does nothing when it is absent, and nothing records the deletion, because a backfill batch reads the source in the same mutation that writes the row, so a batch that read the subject before its deletion committed re-runs under optimistic concurrency and reads the deleted subject, as the rebuild's `occRace` states (E-9, D2, F1)
- An aggregate projection contributes a number per entity to an aggregate row and keeps a per-entity marker so live commands and backfill never count one entity twice (D9)
- [extension] `applyAggregate` ignores the mode: the marker's `sourceVersions` decide, a marker that is not older than the input makes the write `skipped-newer`, an older or missing marker is written with the new contribution and versions and the difference goes to `value`, and a `null` contribution removes the marker and its recorded contribution; a live update on an entity backfill has not reached is therefore not partial, because `contribute` sees the whole DTO, which is why the missing-row rule of the per-entity path does not apply (E-9, D9, F1)
- [extension] A history projection folds events into a row: `keyOf` maps each event to the row it belongs to or to none, and `project` folds the events of one key, in stream-version order within each stream, into the prior row; it is deterministic in the prior row and the events, reads nothing else, and is the one form a read model that depends on history across several streams may take, which is why such a read model rebuilds only under the write pause (E-9, D8, D9, Law 10)
- [extension] A history row's `sourceVersions` hold, per source stream, the highest event version folded into it; `applyHistoryProjection` drops every event whose version is not above the recorded version for its stream and skips the write when none remain, so a live update and a backfill page never fold one event twice, and the live path never meets a non-active generation of a history view because its building generation exists only while its source scopes are closed (E-9, D9, F1)
- [extension] The same projection is bound once per source stream type on the command declaration; the pipeline's step 9 feeds it each matching entry's events, and the backfill feeds it each source's history, so a cross-stream row has one projection and several bindings (E-9, E-7, D8)
- A projection's version changes whenever its output for any input changes; a new version is a new generation, never an in-place rewrite (D8, D9)
- The write rule reads and writes inside one mutation, so two writers of the same row serialize under optimistic concurrency and neither overwrites newer data (F1, D9)

## Design

The shapes are TypeScript in the parent. `StreamVersion` is the kernel's shape with its `version` field, and `streamVersionValidator` is the kernel's validator; `D` is the context's DTO type; `Row` is the read-model document without the row conventions, which `applyProjection` adds. Validators use `convex/values`; the row conventions are a validator the read-model tables spread into their `defineTable`.

- typeProjection: `type Projection<D, Row extends Record<string, Value>> = { version: number; keyOf(tenantId: string, dto: D): string; project(tenantId: string, dto: D, versions: StreamVersion[]): Row | null }` (E-9, D8)
- typeReadModel: `type ReadModel<D, Row extends Record<string, Value>> = { name: string; table: string; rowBudgetBytes: number; projection: Projection<D, Row> }` where `name` is the read model's key in the generation registry, `table` is the parent table that holds its rows, and `rowBudgetBytes` is at most 65,536 with `defaultRowBudgetBytes` 16,384 (E-9, D8, F13)
- typeWritableGeneration: `type WritableGeneration = { role: "active" | "building"; generation: number; projectionVersion: number }`, one generation a command writes, as the registry's `generationsToWrite` returns it (E-8, E-9, D9)
- typeRowWriter: `type RowWriter<DataModel extends GenericDataModel = RowDataModel> = { db: GenericDatabaseWriter<DataModel> }`, the part of a ctx `applyProjection` uses, generic over the composition's data model because a database writer is not covariant in its data model; `RowDataModel` is the data model of one table that spreads `rowConventions` and has `by_key`, and the library reads and writes the read model's own table, named by its `table`, under that table's type (E-9)
- typeAggregateProjection: `interface AggregateProjection<D> { name: string; version: number; table: string; rowBudgetBytes?: number; aggregateKeyOf(tenantId: string, dto: D): string; contribute(tenantId: string, dto: D): number | null }` where `null` means the entity no longer contributes, such as a deleted subject, and `rowBudgetBytes` bounds the aggregate row and the marker alike (E-9, D9, F13)
- typeHistoryProjection: `interface HistoryProjection<Row> { name: string; version: number; table: string; rowBudgetBytes?: number; keyOf(tenantId: string, event: EventEnvelope): string | null; project(tenantId: string, prior: Row | null, events: EventEnvelope[]): Row | null }` where `EventEnvelope` is the envelope of `spec:context.event-envelope`, `null` from `keyOf` means the event is not this view's, `events` are the events of one key not yet folded into `prior`, in version order within each stream, and `null` from `project` deletes the row; a history row is a bounded summary of history, never a list that grows with it, so `rowBudgetBytes` binds it like any row (E-9, D8, D9, F13)
- fnApplyHistoryProjection: `applyHistoryProjection<Row>(ctx: MutationCtx, projection: HistoryProjection<Row>, input: { tenantId: string; events: EventEnvelope[]; mode: ApplyMode; generations: readonly WritableGeneration[] }): Promise<{ key: string; results: ApplyResult[] }[]>` grouping the events by `keyOf`, and per key and generation reading the row by `by_key`, dropping every event whose `streamVersion` is not above the row's recorded version for that stream, returning `skipped-newer` when none remain, otherwise writing `project(tenantId, prior, remaining)` with `sourceVersions` raised to the highest version folded per stream, in the same mutation; the pipeline's step 9 calls it with one `streams` entry's `events` and the rebuild's history batch with one `history` page (E-9, D8, D9, F1)
- typeApplyMode: `type ApplyMode = "live-created" | "live-updated" | "backfill"` (E-9, D9)
- typeApplyResult: `type ApplyResult = "inserted" | "updated" | "deleted" | "skipped-missing" | "skipped-newer" | "unchanged"` (E-9, D9)
- fnApplyProjection: `applyProjection<DataModel extends GenericDataModel, D, Row extends Record<string, Value>>(ctx: RowWriter<DataModel>, readModel: ReadModel<D, Row>, input: { tenantId: string; dto: D; versions: StreamVersion[]; mode: ApplyMode; generations: readonly WritableGeneration[] }): Promise<ApplyResult[]>` writing one result per generation in the order given; the pipeline's step 9 calls it with `versions: [entry.version]` for a per-entity row and the rebuild's batch with `versions: [dto.version]` (E-9, D8, D9)
- callers: the two callers are the command pipeline's step 9, with the mode from the `streams` entry's `created` flag and the list `generationsToWrite` returned, passed unchanged, and the rebuild's backfill and verify batches in `backfill` mode for the building generation; a use case body never calls it, and the same two callers are the only callers of `applyAggregate` and `applyHistoryProjection` (E-9, D8, D9, E-7)
- tableOrderAllocationHistory: `orderAllocationHistory: defineTable({ ...rowConventions, orderId: v.string(), lines: v.array(v.object({ stockItemId: v.string(), quantity: v.number(), allocatedAt: v.optional(v.number()), releasedAt: v.optional(v.number()) })) }).index("by_key", ["tenantId", "generation", "key"])` the history-dependent cross-stream view of the example domain, keyed by order ID and folded from `OrderPlaced` in Orders and `StockAllocated` and `AllocationReleased` in Inventory, whose row is bounded by the order's line count and whose `sourceVersions` hold the order stream and every stock stream folded; it is bound once per source stream type and rebuilds only under the write pause, and Sc L2-6 builds it (E-9, E-46, D9, Sc L2-6)
- fnApplyAggregate: `applyAggregate<D>(ctx: MutationCtx, projection: AggregateProjection<D>, input: { tenantId: string; entityKey: string; dto: D; versions: StreamVersion[]; mode: ApplyMode; generations: readonly WritableGeneration[] }): Promise<ApplyResult[]>` writing one result per generation, `inserted` when the aggregate row was created, `updated` when `value` or `entityCount` changed, `skipped-newer` when the marker was not older, and `unchanged` when nothing moved; `mode` is accepted for symmetry with `applyProjection` and read by nothing (E-9, D9)
- aggregateStep1: for each generation it reads the marker by `by_entity` with the tenant, read model, generation and `entityKey`, and computes `contribution` as `contribute(tenantId, dto)` (E-9, D9)
- aggregateStep2: when a marker exists and its `sourceVersions` are not older than `input.versions` for the same stream, the result is `skipped-newer` and nothing is written; otherwise the difference is `contribution` minus the marker's recorded contribution, or minus zero when the marker is missing (E-9, D9, F1)
- aggregateStep3: it reads the aggregate row by `by_key` with `aggregateKeyOf(tenantId, dto)`, inserts it with `value` equal to the difference and `entityCount` 1 when missing, else adds the difference to `value` and adjusts `entityCount` by one for a new marker and by minus one for a removed one; then it inserts or replaces the marker with `contribution`, `aggregateKey` and `input.versions`, or deletes it when `contribution` is `null`, all in the same mutation (E-9, D9, E-8)
- validatorRowConventions: `const rowConventions = { tenantId: v.string(), generation: v.number(), key: v.string(), projectionVersion: v.number(), sourceVersions: v.array(streamVersionValidator) }` spread into every per-entity and cross-context read-model `defineTable` (E-9, Law 11)
- validatorAggregateRowConventions: `const aggregateRowConventions = { tenantId: v.string(), generation: v.number(), key: v.string(), projectionVersion: v.number(), value: v.number(), entityCount: v.number() }` spread into every aggregate read-model `defineTable`, with the same `by_key` index, where `key` is `aggregateKeyOf(tenantId, dto)` (E-9, Law 11, D9)
- tableOrderTotals: `orderTotals: defineTable({ ...aggregateRowConventions }).index("by_key", ["tenantId", "generation", "key"])` an aggregate of order totals per status, where `key` is the status, `value` the sum of the orders' totals and `entityCount` the number of orders in it, given as the shape of an aggregate table and not as a read model the first experiment builds (E-9, D9)
- validatorOrderSummaryFields: `const orderSummaryFields = { orderId: v.string(), status: v.union(v.literal("placed"), v.literal("cancelled")), lineCount: v.number(), total: v.number(), placedAt: v.number() }` the projected fields of the order summary, which its table spreads and its query's view validator spreads (E-9, E-46, First experiment)
- tableOrderSummaries: `orderSummaries: defineTable({ ...rowConventions, ...orderSummaryFields }).index("by_key", ["tenantId", "generation", "key"]).index("by_status", ["tenantId", "generation", "status", "placedAt"])` (E-9, E-46, First experiment)
- indexByKeyUse: point read by `applyProjection` before every write and by the entity query; `key` is `keyOf(tenantId, dto)`, the application ID of the entity (E-9, D2)
- indexByStatusUse: the essential list query of the first experiment, paginated, within the active generation (E-9, First experiment)
- step1: `applyProjection` computes `key` and the candidate row with `project`; a `null` candidate means delete the row if present and `unchanged` when there is none (E-9)
- step2: for each generation in `generations` it reads the row by `by_key` (E-9, D9)
- step3: it decides by the generation's role and the mode: in the active generation it inserts a missing row and replaces an existing one in both live modes; in a building generation live-created inserts or replaces, live-updated replaces an existing row and answers `skipped-missing` for a missing one, and backfill inserts when missing and updates when the existing `sourceVersions` are older, else `skipped-newer` (D9, E-9)
- step4: before a write it throws a plain error when the row measures above `rowBudgetBytes` with `getConvexSize`; then it writes with `ctx.db.insert`, `ctx.db.replace` or `ctx.db.delete` in the same mutation and returns the results in generation order (E-9, F1, F13)
- limitRowSize: a read-model row stays under its read model's `rowBudgetBytes`, which `applyProjection` checks at every write, 16 KiB by default and at most 64 KiB, well under the 1 MiB document limit; the rebuild's batch bound is derived from the declared budget, and a row that would grow without bound with history is a wrong read model for this contract, a history projection included, whose row summarizes history within the same budget (F13, E-9, E-40)
- limitHistoryFold: on the live path `applyHistoryProjection` reads and writes at most one row per distinct key among one entry's events, each at most `rowBudgetBytes`, so a command that appends `n` events touches at most `n` history rows; on the backfill it takes one `history` page bounded by the rebuild's `limitHistoryBatch`, so one batch reads at most that many events plus as many rows (F13, E-9, E-40)
- limitGenerationsPerWrite: at most 2 generations are written per row per command, the active one and the one in building, verifying or verified if any; a retired generation is kept but never written, so one read model costs at most 2 point reads and 2 writes per command and exactly 1 of each outside a rebuild (E-9, E-8, F13)
- determinismCheck: the acceptance suite folds a sample of DTOs through `project` twice and compares, and compares a backfilled row with the live-written row for the same entity (D8, D9, Sc L2-5)

## Verification — reviewed

- A reviewer confirms that every read model in the corpus and the experiment is declared as a `ReadModel` with its `Projection`, an `AggregateProjection` or a `HistoryProjection` bound on a command declaration, and that the pipeline's step 9 and the rebuild's batches are the only callers of `applyProjection`, `applyAggregate` and `applyHistoryProjection`.
- A reviewer confirms that every `HistoryProjection` is bound with `pauseRequired` on its generations, that `applyHistoryProjection` drops already-folded events by the row's `sourceVersions` before it calls `project`, and that the L2-6 examples assert the fold against the journal.
- A reviewer confirms that no `project` function touches `ctx`, the database, the scheduler or the environment.
- A reviewer confirms that every per-entity or cross-context read-model table spreads `rowConventions`, that every aggregate table spreads `aggregateRowConventions`, and that each carries the `by_key` index.
- A reviewer confirms that `applyAggregate` compares the marker's `sourceVersions` before it touches `value`, that it reads no mode, and that a `null` contribution removes the marker and its recorded contribution.
