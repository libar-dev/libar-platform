# Restore

Layer 2 · Detail: full · Traces: D3, D5, D6, D8, D19, Law 3, Law 8, Law 10, F8, F12, F13, S8, Probe 7, Sc L2-8, E-42.

Restore is the procedure that puts a backup's data under matching code and configuration and proves, before any writer runs, that the domain, journal and read-model invariants hold. A backup is a consistent snapshot of table data; it excludes code, configuration, environment variables and pending scheduled functions, and restoring it wipes the deployment's data and replaces it. The procedure therefore starts by closing the door to writers through the environment, deploys the matching commit, restores, runs its checks as bounded batches, takes an inventory of the pending work the snapshot carries but the scheduler no longer drives, reconciles the gap since the backup, and reopens only when every check passes. Because the snapshot holds the maintenance gate and the generation rows as they were at backup time but not the scheduled batch that was driving a rebuild, a generation left in `building` or `verifying` is stranded by the restore, and a closed gate entry that names it would keep its writers out for ever; the inventory lists every such row and the accepted branch resumes each generation the operator did not abort. Restore is tested, not only backup: the drill is the acceptance scenario, run on a representative dataset in a disposable deployment.

The parts of restore that concern obligations, external dispatch and provider evidence belong to Layer 3 and to Package E. This workflow is the transactional profile's restore, which the durable profile extends: `spec:obligations.retention-and-restore` sets `OBLIGATIONS_DISPATCH` off before the snapshot is restored and runs its schedule rebuild and reconcile pass only after this workflow's accepted branch has cleared `MAINTENANCE_MODE`, so no rearmed wrapper runs into the closed door.

## Intent

- actor: The operator who runs a restore or the drill, and the release engineer who keeps the recovery plan current (D19)
- problem: A representative dataset is restored with matching code and configuration; if the procedure does not exist or its checks are missing, the restored deployment can serve a state whose events do not fold to its saved state, whose journal has gaps, or whose read models miss entities, and nobody knows until a customer does (Sc L2-8)
- outcome: A restore runs with the code and configuration the backup was taken under, keeps writers out until the domain, journal and read-model invariants are checked, records what it checked and found, and reopens only on a clean result (D19, Sc L2-8)
- value: The recovery plan is exercised, not assumed; a restore's result is a record the operator can read, and a failed check names its subject (D19)
- risk: The checks are batches over every stream and every read-model row, so a large dataset takes many batches; the drill sizes the representative dataset so the checks finish inside the release window (F13, D19)
- risk: Whether a backup and a restore cover component tables is not stated on the backup page; the contexts' data lives in components, so the drill proves it and Probe 7 records it (F12, S8, Probe 7)
- assumption: Backups exclude pending scheduled functions, environment variables, code and configuration, and a restore is a destructive replacement of table data (F12, S8)
- assumption: Environment variables survive a restore, because they are not part of the snapshot (F12, S8)
- assumption: Scheduling from a mutation commits with it, so the batches the accepted branch reschedules for stranded generations exist only if the run record's acceptance committed (F8)

### Open questions

- [non-blocking] Probe 7 pending: what a restore leaves of component state decides whether the contexts' tables come back with the parent's; the drill on the Orders and Inventory application shows it for Layer 2 and Probe 7 shows it for Workpool and Workflow before Layer 3 (Probe 7, F12, D19)
- [non-blocking] Extension E-42: the doc says restore runs with matching code and configuration, that domain, journal and read-model invariants hold, and that restore is tested; it does not list the checks or the record, and it does not say what a restore does to a rebuild that was in flight at the backup. The option taken here: four checks, journal, domain, read model and receipt, each a bounded checkpointed batch, the stream check bounded through the `rebuild` query's `maxEvents` argument so a batch folds at most 500 events in all, each folded stream also reading its own stored baseline event, a fifth step that inventories the closed gate entries, the generations in `building`, `verifying` or `verified` and the `imports` rows in `running` that the snapshot restored, a `restoreRuns` row as the record, an accepted branch that resumes every stranded generation the operator did not abort, and the `MAINTENANCE_MODE` environment variable as the door (E-42, D19, F12)
- [non-blocking] Extension E-42, the stream check's batch size: `limitCheckBatch` states the read of a batch that folds one stream, and each further stream the same batch folds reads its own stored baseline event of at most `budgetBytes + 4,096 + 61` bytes; the batch size that keeps a batch of several folded streams under the 16 MiB read ceiling is not pinned (E-42, F13)

## Workflow

- rule: Restore runs with the code and configuration the backup was taken under; the recovery plan names code, schemas, configuration, credentials, data and external outcome evidence (D19, Sc L2-8)
- rule: Restore is tested, not only backup; the drill runs this workflow on a representative dataset in a disposable deployment before every release (D19, Sc L2-8)
- rule: A backup is a consistent snapshot of table data and excludes code, configuration, environment variables and pending scheduled functions; a restore wipes existing data and replaces it (F12, S8)
- rule: Restore starts with dispatch off; in the transactional profile that is the writer door closed through the environment until the checks pass (D19, E-42)
- rule: The checks never run a command, never repeat an external effect and never rewrite an event (Law 10, D5)
- rule: Every check is a bounded, checkpointed batch below the transaction limits (D19, F13)
- rule: After a restore the receipts in the snapshot are the authority for what committed; anything committed after the backup time is outside the restored state, and the run record states the backup time so callers can re-send with their request keys (D19, D6)
- rule: A restore that fails a check stays closed, and the run record names the failed check and its subject; nobody reopens a deployment that failed a check (Sc L2-8, D19)
- rule: [extension] The four checks are journal, domain, read model and receipt, in that order, and each records what it examined and what it found on the run record (E-42, D19)
- rule: [extension] A restore drops every pending scheduled function with the snapshot, so a generation in `building` or `verifying` at backup time comes back with no batch driving it and a closed gate entry that names it stays closed; the fifth step inventories both, plus every `imports` row in `running`, on the run record, and the accepted branch resumes every inventoried generation the operator did not abort, so the gate never stays closed for a rebuild nobody is running (E-42, F12, D19)
- rule: [extension] A baseline-migration chain in flight at the backup leaves no row, only the baseline events it had written; the operator restarts it without a cursor after the accepted branch, which is safe because the journal's `writeBaseline` skips every stream already at the target schema version (E-42, F12, E-25, D5)
- The operator picks the backup and the recovery-plan entry recorded with it: commit, schema hash, configuration hash, credential locations and the location of external outcome evidence (D19, Sc L2-8)
- The operator sets `MAINTENANCE_MODE` to `restore` on the target deployment, so the writer check refuses every write with `writePaused` from now on (E-42, D19)
- The operator deploys the recorded commit and configuration and confirms that the deployed schema matches the backup's schema hash (D19, Sc L2-8)
- The operator restores the snapshot into the target from the dashboard or the CLI import; the restore is destructive and replaces the parent's table data and, as the drill must show, the components' (S8, F12, Probe 7)
- The operator starts the run record with `startRestoreRun`, which stores the backup ID, the backup time, the commit, the hashes and the operator (E-42, D19)
- The journal check runs in batches: for each stream of a `list` page taken with `includeDeleted`, the context's `rebuild` query, called with the events the batch may still fold as `maxEvents`, reports `version`, `savedVersion`, `fromBaseline` and `eventsApplied`, and the check asserts that `eventsApplied` equals `version` minus the baseline version and that `version` equals `savedVersion`, which shows the events since the latest baseline are contiguous and the stream row agrees; a `rebuild` answer refused with `tailTooLong` is recorded as a journal finding naming the stream and its tail length, never retried with a bigger batch, while one refused with `budgetExhausted` is not a finding but the point where this batch stops and the next one resumes; event identity is enforced by the append's indexed read and is not rescanned (E-42, E-24, E-25, D2, D5)
- The domain check runs in the same batches from the same `rebuild` call: its `equal` flag shows that folding the events since the latest baseline through `evolve` gives the saved state at the stream version (E-42, D3, Law 3, Sc L0-2)
- The read-model check runs in batches through the rebuild's verify logic in compare mode: for each read model's active generation, every enumerated stream has a row whose source versions equal the current versions and whose fields equal the projection of the current DTO (E-42, D8, D9)
- The receipt check runs in batches over receipts: for each receipt the context's `byOperation` query returns the events of its operation ID, and the check asserts that the stream versions the receipt lists are among them (E-42, D6, D19)
- Each check batch writes its cursor, its examined count and its findings on the run record in the same mutation, so an interrupted check resumes from its cursor (E-42, F13)
- The pending-work inventory runs after the four checks: it reads the restored gate document and records every closed entry, reads every generation in `building`, `verifying` or `verified` for each read model the parent declares and records it with its state and fence, and pages the `imports` table recording every row in `running`; nothing it records is a finding, because pending work is not a broken invariant (E-42, F12, D19)
- The operator reads the inventory and calls the rebuild's `abortGeneration` for every generation that should not continue, which also resumes the gate scope that generation closed; a generation in `verified` needs no batch and follows the ordinary switch, and an operator-closed tenant or `all` entry is resumed or kept deliberately with `resumeGate` (E-42, D9, Sc L2-6)
- When every check reports zero findings, the operator clears `MAINTENANCE_MODE` and calls `finishRestoreRun`, which resumes every inventoried generation still in `building` or `verifying` at its inventoried fence, bumping the fence and scheduling its next batch from the saved cursor in the same mutation, and marks the run accepted with the finish time; in the durable profile the operator then runs the obligation module's restore steps of `spec:obligations.retention-and-restore`, the schedule rebuild and the reconcile pass, and only after they finish turns `OBLIGATIONS_DISPATCH` on, so no wrapper is rearmed while the door is closed (E-42, E-56, F8, F12, Sc L2-8, Sc L3-7)
- When any check reports a finding, the run record is marked failed with the check and the subject, `MAINTENANCE_MODE` stays set, no generation is resumed, and the operator decides between another backup and a repair (Sc L2-8, D19)
- The drill restores a representative dataset into a disposable deployment on the same team, runs the steps above end to end, and records the run as acceptance evidence (D19, S8, Sc L2-8)

## Design

The restore itself is a platform operation outside any mutation. Everything the procedure adds is in the parent: a run record table, one internal mutation per check batch, one for the pending-work inventory, and the door in the writer check. Each check batch is one mutation. The journal and domain checks share one batch function, because both read the context's `rebuild` query, which folds a stream inside the context and compares it with the saved row; that query is per stream and runs in the batch's own transaction, so the batch hands it the events it may still fold and the query refuses before reading when the tail would not fit, which makes one 500-event fold the batch's worst case rather than a fold on top of a nearly full budget. The read-model check reuses the rebuild's verify logic, and the receipt check reads the parent's receipts and the context's `byOperation` query. The pending-work inventory reads the gate document, the registry and the `imports` table and writes what it finds on the run record. The procedure's six mutations are the only mutations in the parent that do not read the write pause's gate: they write only the `restoreRuns` record and, in the accepted branch, the generation rows they resume; they run only while a run is `running`; and the door they hold closed would otherwise refuse them.

- transactionBoundary: none for the snapshot restore; each check batch is one internal mutation that reads through one component query and writes only the run record; `finishRestoreRun` is one mutation that marks the run and reschedules the stranded generations together, so acceptance and the rescheduling commit or fail as one (D19, F8, F13)
- convexSurface: `startRestoreRun`, `streamCheckBatch`, `readModelCheckBatch`, `receiptCheckBatch`, `pendingWorkBatch`, `finishRestoreRun` as internal mutations and `getRestoreRun` as an internal query, all in the parent (E-42, D19)
- tableRestoreRuns: `restoreRuns: defineTable({ backupId: v.string(), backupTakenAt: v.number(), targetDeployment: v.string(), commit: v.string(), schemaHash: v.string(), configHash: v.string(), state: v.union(v.literal("running"), v.literal("accepted"), v.literal("failed")), checks: v.array(v.object({ name: v.string(), cursor: v.optional(v.string()), examined: v.number(), findings: v.array(v.object({ subject: v.string(), detail: v.string() })), state: v.union(v.literal("pending"), v.literal("running"), v.literal("passed"), v.literal("failed")) })), pendingWork: v.array(pendingWorkItemValidator), operator: actorValidator, startedAt: v.number(), finishedAt: v.optional(v.number()) })` where `checks` holds five entries, the four checks and the inventory under the name `pendingWork`, whose cursor and state are kept like a check's while its items go to `pendingWork` (E-42, D19)
- validatorPendingWorkItem: `const pendingWorkItemValidator = v.object({ kind: v.union(v.literal("generation"), v.literal("closedScope"), v.literal("import")), subject: v.string(), detail: v.string(), generationId: v.optional(v.id("generations")), fence: v.optional(v.number()), resolution: v.optional(v.union(v.literal("resumed"), v.literal("aborted"), v.literal("kept"), v.literal("recorded"))) })` where `subject` is the read model and generation number, the scope key, or the tenant and import ID, `fence` is the generation's fence at inventory time, and `resolution` is written by `finishRestoreRun` (E-42, D19)
- validatorCheckScope: `const checkScopeValidator = v.union(v.object({ kind: v.literal("tenant"), tenantId: v.string() }), v.object({ kind: v.literal("all") }))` naming which tenants a check covers; under `all` a check batch iterates the application's tenant list the way the rebuild's `tenantIteration` does, one tenant named on every context call, and never calls a context without a tenant (E-42, D11, Law 11)
- indexRestoreRunsByStarted: `.index("by_started", ["startedAt"])` (E-42)
- indexRestoreRunsByStartedUse: the operator's listing of runs, newest first (E-42, D19)
- fnStartRestoreRun: `export const startRestoreRun = internalMutation({ args: { backupId: v.string(), backupTakenAt: v.number(), targetDeployment: v.string(), commit: v.string(), schemaHash: v.string(), configHash: v.string(), operator: actorValidator }, returns: v.id("restoreRuns"), handler })` refusing when `MAINTENANCE_MODE` is not `restore` (E-42, D19)
- fnStreamCheckBatch: `export const streamCheckBatch = internalMutation({ args: { runId: v.id("restoreRuns"), contextId: v.string(), streamType: v.string(), scope: checkScopeValidator }, returns: v.boolean(), handler })` calling `ctx.runQuery(components.orders.queries.order.list, { tenantId, includeDeleted: true, paginationOpts: { numItems: streamsPerBatch, cursor } })` once, where `streamsPerBatch` is the stream bound of `limitCheckBatch`, and, per stream of the page in order, `ctx.runQuery(components.orders.queries.order.rebuild, { tenantId, streamId, maxEvents: maxFoldEvents - sum })` where `sum` is the running total of `eventsApplied` in this batch; the query reads the stream row first and refuses with `budgetExhausted` before reading an event when the tail exceeds `maxEvents`, on which the batch saves the cursor at that stream and returns, so the next batch starts with `sum` at zero and admits the same stream alone; a `tailTooLong` refusal is a journal finding, `equal` false a domain finding, and the batch returns whether the enumeration is done (E-42, E-24, E-25, D2, D3, D5, Sc L0-2)
- fnReadModelCheckBatch: `export const readModelCheckBatch = internalMutation({ args: { runId: v.id("restoreRuns"), readModel: v.string(), scope: checkScopeValidator }, returns: v.boolean(), handler })` reusing the rebuild's verify logic in compare mode against the active generation (E-42, D8, D9)
- fnReceiptCheckBatch: `export const receiptCheckBatch = internalMutation({ args: { runId: v.id("restoreRuns"), scope: checkScopeValidator }, returns: v.boolean(), handler })` reading 25 receipts by tenant from the receipt cursor and calling `ctx.runQuery(components.orders.queries.operations.byOperation, { tenantId, operationId })` per receipt for each context the receipt's versions name (E-42, D6, D19)
- fnPendingWorkBatch: `export const pendingWorkBatch = internalMutation({ args: { runId: v.id("restoreRuns") }, returns: v.boolean(), handler })` which on its first call, when the inventory's cursor is empty, reads the gate document and appends one `closedScope` item per closed entry, then reads `by_read_model_state` for each read model the parent's declarations name and each of `building`, `verifying` and `verified` and appends one `generation` item per row with its state and fence, and on every call pages the `imports` table with `.paginate` in creation order, `limitPendingWorkBatch` rows at a time, appending one `import` item per row in `running`; it saves the page cursor on its `checks` entry and returns whether the paging is done (E-42, F12, D19, E-41)
- fnFinishRestoreRun: `export const finishRestoreRun = internalMutation({ args: { runId: v.id("restoreRuns"), operator: actorValidator }, returns: v.null(), handler })` marking the run failed when any check has a finding; otherwise refusing with a plain error while `MAINTENANCE_MODE` is still `restore` or the inventory has not finished, and then, for every `generation` item whose row is still in `building` or `verifying` at the inventoried fence, calling the rebuild's `resumeChain` in this mutation, which bumps the fence and schedules the next batch from the saved cursor, writing `resumed` on the item, `aborted` on one whose row is `aborted`, `kept` on a `closedScope` item still closed, `recorded` on an `import` item, and marking the run accepted with the finish time (E-42, D19, F8, F12, Sc L2-8)
- doorExemption: `startRestoreRun`, `streamCheckBatch`, `readModelCheckBatch`, `receiptCheckBatch`, `pendingWorkBatch` and `finishRestoreRun` do not read the gate through `assertWritable` or `gateAllows` and write only `restoreRuns`, except that `finishRestoreRun`'s accepted branch also patches the generation rows it resumes; `startRestoreRun` refuses when `MAINTENANCE_MODE` is not `restore`, and each later mutation refuses when its run is not `running`, so no operational row is written outside a restore and no business table is written by them at all (E-42, D19)
- checkOrder: journal, domain, read model, receipt, then the inventory; a later check does not start while an earlier one has findings, because a broken journal makes the fold check meaningless, and the inventory runs last because it is not a check and its items never fail the run (E-42, D3)
- gapRecord: the run record's `backupTakenAt` is the gap start; the procedure writes no synthetic receipt and invents no event for the gap (D19, Existing systems)
- limitCheckBatch: [extension] at most `min(25, floor(2 MiB / budgetBytes))` streams per stream-check batch, which is 8 at the default 256 KiB stream budget and 25 for a stream type whose budget is 80 KiB or less, and at most the journal's `maxFoldEvents` of 500 events folded per batch, enforced through `maxEvents` rather than by a stop after the fold that crossed a bound; a batch that folds one stream reads one fold of at most 500 events of at most `limitEventBytes` of `spec:context.event-envelope` per event, 20,480 bytes and the 61 bytes of a stored document's system fields, under 9.8 MiB, with its stored baseline event of at most `budgetBytes + 4,096 + 61` bytes, plus the `list` page of at most 2 MiB of stream rows, plus the same rows read again when each `rebuild` re-reads its row before folding, at most 2 MiB, where each stored row of a single mapping reads 61 bytes of system fields beyond its `budgetBytes`, 488 bytes for the four rows read twice at the cap, and a derived mapping adds 61 bytes for each of its documents, plus the run record of at most the 1 MiB document limit, at most 16,042,313 bytes in all for a single mapping at the 512 KiB cap on `budgetBytes`, under 15.3 MiB against the one budget that nested queries share, as Probe 4 showed, below the 16 MiB read ceiling; each further stream the batch folds reads its own stored baseline event of at most `budgetBytes + 4,096 + 61` bytes beside the events it shares the 500-event bound with, so this total does not bound a batch that folds several streams; a typical batch folds far less, and the 1 second timeout binds first for a batch that folds one full tail, which is why the check is a resumable batch; 25 receipts per receipt batch, each one component call plus one `list` call; 100 rows per read-model batch with one `list` call capped by the context's byte-derived page; the per-stream calls are the cost Probe 3 measures (E-42, E-24, E-25, F13, S3, S9, Probe 3, Probe 4)
- limitFoldPerStream: [extension] a fold check reads the events since the latest baseline, at most the journal's `maxFoldEvents` of 500 and never more than the batch's remaining `maxEvents`; the `rebuild` query reads the stream row and refuses before reading an event, with `tailTooLong` above the fold bound, which is a finding of the journal check and not a bigger batch, and with `budgetExhausted` above the batch's remaining budget, which is the resume point of the next batch and never a finding (E-42, E-25, F13, D5)
- limitPendingWorkBatch: 100 `imports` rows per inventory call, one gate document and at most three registry index ranges per declared read model on the first call, all far below the ceilings; a generation in `building`, `verifying` or `verified` is at most one per read model, so the registry part is bounded by the number of declared read models (E-42, F13)
- limitFindingsKept: at most 100 findings per check on the run record; further findings are counted, so the record stays under the document limit, and at most 200 pending-work items are kept the same way (E-42, F13)
- drillCadence: once per release on a disposable deployment, with the representative dataset the acceptance contract names (D19, Sc L2-8)

## Verification — reviewed

- A reviewer confirms that no check batch calls a context operation, schedules anything or writes anything but the run record, and that the only scheduling in the procedure is `finishRestoreRun`'s rescheduling of inventoried generations in its accepted branch.
- A reviewer confirms that the six restore mutations are the only functions in the parent that skip the gate read, that each writes only `restoreRuns` apart from the generation rows `finishRestoreRun` resumes, and that each refuses outside a running restore.
- A reviewer confirms that the door is read by the writer check before the gate document and that the procedure clears it only in the accepted branch, before `finishRestoreRun` reschedules anything.
- A reviewer confirms that `streamCheckBatch` passes `maxEvents` on every `rebuild` call, that a `budgetExhausted` refusal is never recorded as a finding, and that the read of a batch that folds one stream, one full fold with its stored baseline event plus the page read twice, is stated below the ceiling, with each further folded stream's own stored baseline event named beside it.
- A reviewer confirms that every generation the inventory lists is `resumed` or `aborted` on an accepted run record and that no closed gate entry on an accepted run names a generation that is not `building`, `verifying` or `verified` again.
- A reviewer confirms that the recovery plan entry named in the first flow exists for every backup the drill uses.
