# Rebuild: generations, backfill and the write pause

Layer 2 · Detail: full · Traces: D8, D9, D11, D19, Law 10, Law 11, F1, F7, F8, F9, F12, F13, F17, Probe 6, Sc L2-5, Sc L2-6, E-8, E-40, E-42.

A rebuild builds a new numbered generation of a read model while the old one stays active. For a per-entity or current-state read model it runs online: the generation is registered as building, live commands write it as well as the active one, backfill batches fill it from each source at its current stream version writing only where the target is missing or older, and one write switches the active generation after coverage is verified. Optimistic concurrency orders each batch against live commands, so neither side overwrites newer data. The old generation is kept for a rollback period and no longer written; a rollback reopens it and one verify pass repairs it before it is active again. For a read model that depends on history across several streams the rebuild runs under a write pause, because it needs a consistent cut; the scope closed is the view's sources, the context and stream type pairs its bindings name, so every use case that writes one of them and the journal's baseline driver read the gate and are refused, background writers are fenced by that read and by the generation's fence, and an operator can resume or abort. Such a view is a `HistoryProjection` and its backfill pages each source stream's history under the pause. Rebuild never runs commands or external effects.

The registry, the per-entity marker and the gate document are pinned by `spec:application.generation-registry` and `spec:application.write-pause`. The projection and the write rule are `spec:application.projection-contract`. Sources are read through the context's queries, never its tables; a rebuild of a stream from its own events is the journal's concern and not this one.

## Intent

- actor: The operator who starts, verifies, switches, rolls back or aborts a generation, and the use cases whose live writes keep the building generation current (D9, D19)
- problem: A per-entity read model is rebuilt while commands run and the rebuild is interrupted and resumed; a live command's incremental update on a row backfill has not written builds a partial one, a backfill batch overwrites newer data, an entity is missed at cutover, or a side effect replays; a cross-stream history view is rebuilt without a consistent cut (Sc L2-5, Sc L2-6)
- outcome: A per-entity or current-state read model rebuilds online as a new generation with no stale overwrite, no missing entity and no side effect, with cutover and rollback in one write each; a history-dependent view rebuilds under a write pause with safe resume and abort, and writes reopen only after verification (D9, Sc L2-5, Sc L2-6)
- value: The common rebuild costs no downtime and no projection job; the write pause is paid only where a consistent cut is needed (D9)
- risk: The standing cost is a generation registry read in every command that maintains a read model, a generation on every row, a marker per entity for counts and sums, the batch runner, and for the write pause a gate every writer reads (D9)
- risk: The batch bound and the runner are design choices under the transaction limits until Probe 6 shows how a batch races a live command and whether the migrations component fits (F13, F17, Probe 6)
- assumption: Mutations are serializable under optimistic concurrency, so a backfill batch and a live command that touch the same row serialize and the loser retries (F1)
- assumption: `@convex-dev/migrations` fits a generation backfill; its product page states resumable batches with saved progress, resume from the last checkpoint and running over a subset, and states no batch size, so the batch bound below is this design's own under E-40 and F13, and whether a migration can iterate a table inside a component is what Probe 6 shows (F17, Probe 6)
- assumption: A parent query calling a component query stays reactive, so switching the active generation in the registry re-runs every subscription that reads it, and the enumeration's `paginator` page relayed by the parent stays contiguous under live writes; this is F15, and Probe 5 showed both on the pinned backend (F15, Probe 5, S4)
- assumption: Scheduling from a mutation commits with it, and a scheduled mutation retries internal errors and runs once (F8, F9)
- assumption: Backups exclude pending scheduled functions, so a restore drops the batch that was driving a generation and leaves its row at the checkpoint; the restore procedure's inventory and resume are the recovery (F12, E-42)

### Open questions

- [non-blocking] Probe 6 pending: a backfill batch racing a live command under optimistic concurrency, and whether the migrations component can drive a batch whose source is a context's enumeration rather than a parent table (Probe 6, F1, F17, D9)
- [non-blocking] Extension E-40: the doc binds resumable batching to `@convex-dev/migrations` and gives no batch size; the component iterates a parent table while the sources of a read model live in a context component. The option taken here: a batch is one mutation with one cursor and a bound of at most 100 entities, capped twice, by the read model's declared `rowBudgetBytes` so that the parent's point reads and writes stay under 4 MiB, and by the context's byte-derived `list` page bound, which is 16 items at the default 256 KiB stream budget, a design choice under F13 that is a field of the generation row and that `resumeGeneration` lowers down to 1 when a generation stalls on optimistic-concurrency conflicts over a hot key range, because a mutation that loses the race never commits and cannot count its own losses; the migrations component drives batches whose source is a parent table, and a self-scheduled internal mutation with the same batch contract drives batches whose source is a context's enumeration until Probe 6 shows the component can; Probe 6 also measures the contention and decides whether an automatic stall check earns its function (E-40, E-24, E-9, F17, F13, F1)
- [non-blocking] Extension E-8: the registry states, the rollback period, what a rollback does, the gate document, the scope a paused rebuild closes and the reach of a generation are design choices the doc does not make; they are pinned in the two contracts under this workflow, the registry's E-8 question records the two readings of rollback, kept-and-reverified against write-through, with the cheaper one taken, and it records the two readings of reach, one generation per read model spanning every tenant against one registry per read model and tenant, with the deployment-wide one taken because a generation is a build of the projection's code, which is the same for every tenant; the write pause's E-8 question records that a paused rebuild closes the view's source stream types rather than the read model, because a consistent cut must hold every writer of the sources, which the declaration's `writes` makes derivable; and this workflow adds that the backfill of a history view pages each source stream's history one page per batch, with the stream and the event cursor on the batch cursor, because a `HistoryProjection` takes events and the doc's write-pause rebuild has no other input (E-8, E-9, E-38, D9)

## Workflow

- rule: Rebuild never runs commands or external effects (D9, Law 10)
- rule: Rebuild reads a source only through the context's queries, with the tenant as the one argument that scopes them, never through the context's tables (D10, D11, F11)
- rule: Online rebuild is the default for per-entity and current-state read models; the write pause is the exception, for read models that depend on history across several streams (D9)
- rule: Live commands also write the building generation; a command that creates a stream writes its row, and a command on an existing stream updates the row only if backfill has already written it (D9)
- rule: A backfill batch reads or folds each source at its current stream version and writes the row only if the target is missing or older (D9)
- rule: Coverage is verified before the switch, the active generation switches in one write, and the old generation is kept for a rollback period (D9)
- rule: Counts and sums use a per-entity marker so live commands and backfill never count one entity twice, which is still transactional (D9)
- rule: Under the write pause every writer in the scope reads the maintenance gate, background writers are fenced or drained, and an operator can resume or abort (D9)
- rule: A refused write under the pause is a transient refusal, retryable and never a stored rejection (D4, D9)
- rule: Every batch has a stated bound below the transaction limits, tested against the pinned Convex version; the limits are ceilings, not batch sizes (D19, F13)
- rule: [extension] The rebuild runs under an operator actor, and a generation spans every tenant of the deployment: its batches iterate the application's tenant list and name the tenant on every context call, so no call runs with an absent tenant as a wildcard, and the one registry row per read model answers every tenant's queries, which is why a switch can never leave one tenant reading a generation that was built for another (D11, Law 11, E-8)
- rule: A backfill batch racing a live command is ordered by optimistic concurrency; the batch's read-then-write of a row is one mutation, so the batch never overwrites a row a command wrote after the batch read its source (D9, F1)
- rule: [extension] The batch runner is `@convex-dev/migrations` where the batch's source is a parent table, and a self-scheduled internal mutation with the same batch contract where the source is a context's enumeration (E-40, F17, F8)
- rule: [extension] A projection version change is a new generation, never an in-place rewrite of the active one (E-8, D8)
- rule: [extension] The batch bound is a field of the generation row, at most 100 entities, at most `floor(4 MiB / (2 * rowBudgetBytes))` for the read model's declared row budget, and never more than the context's `list` page admits at the stream type's document budget; only `resumeGeneration` changes it, lowering it down to 1 when a generation stalls on optimistic-concurrency conflicts; a batch that loses the race never commits, so it cannot record its own loss (E-40, E-24, E-9, F1, F13)
- An operator calls `startGeneration` for a read model; it inserts the generation row in state `building` with the next generation number, the projection version, the batch size and fence 1, and schedules the first backfill batch in the same transaction; with `pauseRequired` it also closes the maintenance gate for every source scope of the read model's bindings in that transaction, before the batch is scheduled (D9, F8, E-8, E-38)
- From that commit every use case that maintains the read model writes the active generation and the building one through `applyProjection`, in live-created mode for a stream it created and live-updated mode otherwise (D9, E-9)
- Each backfill batch runs as one mutation: it loads the generation row, stops if the state is not `building` or the fence differs, reads the gate, calls the context's `list` query once with `includeDeleted` and a page of the batch size from the saved cursor, applies the projection in backfill mode for each returned DTO at its current version, writes the new cursor and the counts on the generation row, and schedules the next batch or moves the state to `verifying` when the enumeration is done (D9, D10, F1, E-40)
- A batch that is interrupted, times out or throws leaves the generation at its last checkpoint; a backend interruption leaves the scheduled batch pending and it runs after the restart, an internal error is retried by Convex, a batch that keeps losing the optimistic-concurrency race fails after Convex's own retries with its documents-changed error, and a developer error, that failure or a timeout ends the batch, after which the operator's `resumeGeneration` bumps the fence, lowers the batch size when the failure was contention, and schedules a batch from the saved cursor; re-processing an entity is a no-op because its row is no longer older; a restore is the one interruption that leaves no batch pending, because the snapshot excludes scheduled functions while it brings the row back at its checkpoint, so `spec:application.restore` inventories every generation in `building` or `verifying` and its accepted branch resumes each one the operator did not abort through the same `resumeChain` (D9, F9, F1, F12, E-42, Sc L2-5)
- Each verify batch enumerates the sources again from the verify cursor and checks that every stream whose DTO projects to a row has one whose versions are at least the enumerated versions, while a stream whose DTO projects to `null` needs no row; a miss is backfilled in place and counted; the state moves to `verified` when the verify cursor is done and the last full pass counted zero misses (D9, Sc L2-5)
- `switchGeneration` sets the verified generation `active` and the active one `retired` with `retireAfter` in one write; every query reads the active generation from the registry, so every subscription on the read model re-runs (D9, F7)
- [extension] During the rollback period the retired generation's rows are kept and no longer written; `rollbackGeneration` reopens the retired generation as `verifying` with a bumped fence and a fresh verify cursor, live commands write it again from that commit, its verify pass backfills every row that is missing or older, and the ordinary `switchGeneration` makes it active again, so the current generation keeps serving until the rollback is verified (E-8, D9, Sc L2-5)
- After `retireAfter`, `purgeGenerationBatch` deletes the retired generation's rows and markers in bounded batches and marks it `purged` (D19, E-40)
- For a history-dependent read model the generation row records `pauseRequired`, and `startGeneration` closes the maintenance gate for every source scope of the read model's bindings in the mutation that inserts the row, recording its own generation on each closed entry, so the gate is closed before the first batch is scheduled and this generation's batches are the one background writer allowed through (D9, E-8, E-38)
- While the gate is closed for the sources, every use case whose declaration writes one of them and the journal's baseline driver refuse with `writePaused` before any write, whether or not they maintain the view; a batch scheduled before the close reads the closed gate when it starts and refuses, a batch running when the close commits loses the optimistic-concurrency race on the gate document and re-runs into the refusal, and a batch of a superseded chain refuses because its generation fence is stale; nothing needs to drain (D9, D4, E-8, E-38, F1)
- Backfill under the pause enumerates a consistent cut because no source changes: each history batch takes one stream from the enumeration, reads one `history` page of it from the saved event cursor, folds the page into the building generation through `applyHistoryProjection` in backfill mode, and saves the stream and the event cursor on the generation row, moving to the next stream when the page reports `isDone`; an interrupted batch resumes from its cursor with the gate still closed, and the gate never reopens by itself (D9, E-9, Sc L2-6)
- Verification runs under the pause: each verify batch enumerates the sources again and checks, per stream, that the row of its last event's key records the stream's current version in `sourceVersions`, backfilling the stream's history in place when it does not; the operator switches the generation and only then resumes the gate, so writes reopen only after verification (D9, Sc L2-6)
- `abortGeneration` marks a building, verifying or verified generation `aborted`, leaves the active generation untouched, and resumes every closed entry that names this generation; aborted rows are purged in bounded batches (D9, Sc L2-6)

## Design

Each batch is one scheduled internal mutation in the parent. The rebuild schedules from a mutation, so a batch is scheduled only if its predecessor committed, and a scheduled mutation retries internal errors and runs once. The rebuild is an operator operation on parent tables; it is not deferred business work and creates no obligation. All rebuild functions are `internalMutation` or `internalQuery` and reach the dashboard through operator functions that authorize an operator actor; no public function starts, switches or aborts a generation. `Actor` is the pipeline's actor type and `actorValidator` its validator; `rowBudgetBytes` is the projection contract's declared row budget.

The enumeration is the context's `list` query with `includeDeleted`, the one read of context data per batch: one call returns a page of up to `batchSize` DTOs and a continuation cursor, built inside the component by `paginator` from `convex-helpers` over the `by_identity` index that includes deleted subjects, and capped by the query at its byte-derived page bound. A DTO carries the stream version the projection compares, as the queries contract's `toDto(state, meta)` maps it onto `version`. Deleted subjects reach the projection as DTOs the projection maps to `null`, so their rows are deleted rather than left behind.

- transactionBoundary: each batch is one scheduled internal mutation that commits its rows, its cursor and the scheduling of the next batch together; the switch, rollback and abort are one mutation each (D9, F8, F9)
- convexSurface: `startGeneration`, `backfillBatch`, `resumeGeneration`, `verifyBatch`, `switchGeneration`, `rollbackGeneration`, `abortGeneration`, `purgeGenerationBatch` as internal mutations, `getGenerations` as an internal query, all in the parent; the gate functions are in the write-pause contract (D9, E-8)
- fnStartGeneration: `export const startGeneration = internalMutation({ args: { readModel: v.string(), projectionVersion: v.number(), batchSize: v.optional(v.number()), pauseRequired: v.boolean(), actor: actorValidator }, returns: v.id("generations"), handler })` computing the row's `batchSize` as `min(args.batchSize ?? 100, floor(4 MiB / (2 * rowBudgetBytes)))` from the projection's declared row budget, inserting the row with the cursor at the first tenant of the application's tenant list and, when `pauseRequired`, calling the write pause's `closeScope` once per distinct `source:` scope of the read model's bindings with the new row's ID before scheduling the first batch; `pauseRequired` is refused with a plain error for a read model whose projection is not a `HistoryProjection`, and required for one that is (D9, E-8, E-9, E-38, E-40)
- fnHistoryPageCall: `ctx.runQuery(components.orders.queries.order.history, { tenantId, streamId, paginationOpts: { numItems: limitHistoryBatch, cursor: eventCursor } })` the one read of context data a history batch makes beside the `list` call of `numItems` 1 that gives it its next stream, returning a `paginator` page of envelopes in version order that the batch folds through `applyHistoryProjection` (D2, D10, E-9, E-24)
- fnBackfillBatch: `export const backfillBatch = internalMutation({ args: { generationId: v.id("generations"), fence: v.number() }, returns: v.null(), handler })` (D9, E-40)
- fnEnumerateCall: `ctx.runQuery(components.orders.queries.order.list, { tenantId, includeDeleted: true, paginationOpts: { numItems: batchSize, cursor } })` returning the `paginator` page `{ page, isDone, continueCursor }` of DTOs with their stream versions, one call per batch; the query caps `numItems` at its byte-derived bound, so a batch never reads more than 8 MiB of stream rows however `batchSize` was set (D2, D10, F15, S4, E-24)
- tenantIteration: `[extension]` every generation spans all tenants, so the generation row's `cursor` and `verifyCursor` are the registry's `BatchCursor`, the current tenant and the page cursor within it; a batch moves to the next tenant of the application's tenant list, read in tenant-ID order, when `isDone`, and the enumeration is done when the last tenant's page is done; a batch never calls `list` without a tenant (E-40, E-8, D11, Law 11)
- fnResumeChain: `resumeChain(ctx: MutationCtx, generationId: Id<"generations">, actor: Actor, batchSize?: number): Promise<void>` bumping the fence, setting the row's `batchSize` when given, at least 1 and at most the bound `startGeneration` computed, clearing `lastError`, and scheduling `backfillBatch` from the saved cursor when the state is `building` or `verifyBatch` from the verify cursor when it is `verifying`, all in the caller's mutation; refused with a plain error in any other state; called by `resumeGeneration` and by the restore's `finishRestoreRun` for every generation the snapshot stranded (D9, F8, E-40, E-42)
- fnResumeGeneration: `export const resumeGeneration = internalMutation({ args: { generationId: v.id("generations"), batchSize: v.optional(v.number()), actor: actorValidator }, returns: v.null(), handler })` the operator's entry to `resumeChain` (D9, Sc L2-5, E-40)
- fnVerifyBatch: `export const verifyBatch = internalMutation({ args: { generationId: v.id("generations"), fence: v.number() }, returns: v.null(), handler })` (D9)
- fnSwitchGeneration: `export const switchGeneration = internalMutation({ args: { generationId: v.id("generations"), rollbackPeriodMs: v.optional(v.number()), actor: actorValidator }, returns: v.null(), handler })` (D9)
- fnRollbackGeneration: `export const rollbackGeneration = internalMutation({ args: { readModel: v.string(), actor: actorValidator }, returns: v.null(), handler })` setting the read model's retired generation to `verifying` with a bumped fence, a cleared verify cursor and zero misses, and scheduling `verifyBatch`; refused when `retireAfter` has passed or when another generation is building, verifying or verified; the switch that completes the rollback is `switchGeneration` (D9, E-8)
- fnAbortGeneration: `export const abortGeneration = internalMutation({ args: { generationId: v.id("generations"), reason: v.string(), actor: actorValidator }, returns: v.null(), handler })` marking the generation `aborted`, bumping its fence, and calling the write pause's `resumeScope` for every closed entry that names this generation (D9, Sc L2-6, E-8)
- fnPurgeGenerationBatch: `export const purgeGenerationBatch = internalMutation({ args: { generationId: v.id("generations"), fence: v.number() }, returns: v.null(), handler })` deleting at most `limitPurgeBatch` rows by the `by_key` index range for that generation (D19, E-40)
- step1: `backfillBatch` loads the generation row by ID and returns without writing when `state` is not `building` or `fence` differs from its argument (E-40, D9)
- step2: it calls the write pause's `gateAllows(ctx, scopes, generationId)` with the `all` scope, the scope of the tenant it iterates and the read-model scope, and returns without writing, apart from `writePaused` and the answer's scope in `lastError`, when the answer is not allowed, which it is while the restore door is set and while a closed entry covers one of those scopes and names a generation other than this one; the generation then waits for `resumeGeneration` after the gate reopens; `verifyBatch` and `purgeGenerationBatch` make the same read at the same point, and no batch calls `assertWritable`, because a batch parks its generation rather than failing its scheduled mutation with a thrown refusal (E-8, E-42, D9)
- step3: it calls `list` once with `includeDeleted` and `paginationOpts` of `batchSize` items from the saved cursor (D10, E-40)
- step4: for each item it calls `applyProjection` or `applyAggregate` in backfill mode for the building generation only, counting inserted, updated and skipped (D9, E-9)
- step5: it patches the generation row with the new cursor, the counts and `updatedAt`, and schedules `backfillBatch` with the same fence through `ctx.scheduler.runAfter(0, ...)`, or sets `state` to `verifying` and schedules `verifyBatch` when `isDone` (D9, F8)
- historyStep3: for a history view a batch replaces steps 3 and 4: when the cursor names no stream it calls `list` with `numItems` 1 from the page cursor to take the next stream and sets `eventCursor` to `null`; it then calls `history` for that stream with `limitHistoryBatch` events from `eventCursor`, calls `applyHistoryProjection` in backfill mode for the building generation with the page, and saves `eventCursor`, or clears `streamId` and advances the page cursor when the page reports `isDone` (D9, E-9, E-24, E-40)
- historyVerify: a verify batch of a history view enumerates the sources with `list` and, per stream, reads its last event through `history` with `fromVersion` at the stream's version and `numItems` 1, finds that event's row by `keyOf`, and counts a miss when the row is absent or its `sourceVersions` record a lower version for the stream; a miss is repaired by folding the stream's history in place through the same history batches from `eventCursor` null (D9, E-9, Sc L2-6)
- migrationsBinding: `[extension] const migrations = new Migrations<DataModel>(components.migrations, { internalMutation })` with `migrations.define({ table: "orderSummaries", batchSize: 100, customRange: (q) => q.withIndex("by_key", (i) => i.eq("tenantId", tenantId).eq("generation", generation)), migrateOne })` for batches whose source is a parent table, such as purging a generation or re-projecting an existing generation's rows; the component resumes from the failed batch (E-40, F17)
- rebuildClass: a read model declares its class at declaration time, per entity or bounded current state for the online path, as a `Projection` or `AggregateProjection`, and history across streams for the write pause, as a `HistoryProjection`; `pauseRequired` on the generation row records it, and a history view never rebuilds online because a live fold onto a row backfill has not reached cannot be told apart from a complete one (D9, D18, E-9)
- limitHistoryBatch: `min(500, floor(4 MiB / (2 * rowBudgetBytes)))` events per history batch, 128 at the default 16 KiB row budget and 32 at the 64 KiB ceiling, so one batch reads at most that many events of at most 17 KiB, about 2.2 MiB, one stream row through `list`, and at most one history row per event, at most 2 MiB, and writes at most 2 MiB, under the ceilings with the 1 second timeout in mind; the count is stored on the generation row as its `batchSize` and lowered by `resumeGeneration` like the online bound (E-40, E-9, E-24, F13)
- occRace: a live command that read a row before the batch wrote it, or the batch that read the source before a command changed it, is the loser of an optimistic-concurrency conflict and re-runs; the re-run reads the newer row or the newer source, and the version compare then skips the older write; the batch's read set is the index range of the page it enumerated, so a live write to any stream in that range re-runs the batch, and a batch that keeps losing fails after Convex's internal retries with its documents-changed error, which is the stall that `resumeGeneration` answers with a smaller bound (F1, D9, Probe 6, E-40)
- markerRule: an aggregate write reads the entity's marker for the generation in the same mutation and adds only the difference between the new and the recorded contribution, so a live command and a backfill batch that both see the entity never count it twice (D9, E-8)
- limitBatchSize: at most 100 entities per backfill or verify batch, this design's own bound under E-40 and F13 until Probe 6, and at most `floor(4 MiB / (2 * rowBudgetBytes))` for the read model's declared row budget, which is 128 and so 100 at the default 16 KiB and 32 at the 64 KiB ceiling of `limitRowSize`, computed by `startGeneration`, stored as `batchSize` and passed to a migrations-driven batch so that both runners carry the same number; the context's `list` caps the page further at `limitListPage(budgetBytes)`, `max(1, min(100, floor(4 MiB / budgetBytes)))` items, so a batch reads 16 stream rows at the default 256 KiB stream budget and the full 100 only for a stream type whose budget is 40 KiB or less; lowered per generation down to 1 by `resumeGeneration`; the worst case of one batch is one `list` call of at most 8 MiB of stream rows read inside the context, plus in the parent the gate document, the generation row and at most two point reads per entity, the building generation's row and, for an aggregate, its marker, each at most `rowBudgetBytes`, at most 4 MiB, and at most two writes per entity plus the generation row, at most 4 MiB written, so a batch reads under 12 MiB and writes under 4 MiB even if limits add up across the boundary, and runs under 1 second (E-40, E-24, E-9, F13, F17, Probe 4)
- limitPurgeBatch: 500 rows deleted per purge batch, one index range, under 1 second (E-40, F13, D19)
- limitOutstandingBatches: one scheduled batch per generation at a time, enforced by the fence; a stale batch returns without writing (E-40, F13)
- limitBuildingGenerations: at most one generation in `building`, `verifying` or `verified` per read model at a time, so a command writes at most two generations, the active one and that one (E-8, E-9)
- limitRollbackPeriod: `[extension]` 7 days by default, stored as `retireAfter` on the retired row; the retired generation is kept but not written, and a rollback after `retireAfter` is refused (E-8, D9)

## Example space

```gwt-vocabulary
Given a {viewKind:"per-entity"|"cross-stream history"} read model with an active generation
And a new generation registered as {mode:"building online"|"building under a write pause"}
And live commands {liveCommands:"keep running"|"are refused while paused"}
When the backfill is interrupted after {batches:number} batches and then {resumption:"resumed"|"aborted"}
Then no row of the new generation holds data older than its source stream version
And the new generation {coverage:"covers every stream enumerated at cutover"|"is discarded and read by no query"}
And no command or external effect ran during the rebuild
And the active generation {cutover:"switches in one write and can roll back"|"stays the old one"}
And writes {writes:"never stopped"|"reopen only after verification"|"reopen after the abort"}
```

## Verification — reviewed

- A reviewer confirms that every batch function states its bound and that the bounds sit below the F13 ceilings with the 1 second timeout in mind.
