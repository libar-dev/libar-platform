# Rebuild: generations, backfill and the write pause

Layer 2 · Detail: full · Traces: D8, D9, D11, D19, Law 10, Law 11, F1, F7, F8, F9, F12, F13, F17, Probe 6, Sc L2-5, Sc L2-6, E-8, E-9, E-40, E-42, E-48, E-49.

A rebuild builds a new numbered generation of a read model while the old one stays active, and it is also how a read model comes to exist: its first generation is built the same way. For a per-entity read model it runs online: the generation is registered as building, live commands write it as well as the active one, backfill batches fill it from each source at its current stream version writing only where the target is missing or older, one verify pass makes presence and absence right, and one write switches the active generation. Optimistic concurrency orders each batch against live commands, so neither side overwrites newer data. The old generation is kept for a rollback period and no longer written; a rollback reopens it, one verify pass repairs it, and the same switch makes it active again. For a read model that depends on history across several streams the rebuild runs under a write pause, because it needs a consistent cut; the scope closed is the view's sources, the context and stream type pairs its bindings name, so every use case that writes one of them and the journal's baseline driver read the gate and are refused, background writers are fenced by that read and by the generation's fence, and an operator can resume or abort. Such a view is a `HistoryProjection` and its backfill pages each source stream's history under the pause. Rebuild never runs commands or external effects.

The registry, the progress row, the per-entity marker and the gate document are pinned by `spec:application.generation-registry` and `spec:application.write-pause`. The projection and the write rule are `spec:application.projection-contract`. The operator entry and the tenant list are `spec:command.actor-and-scope`. Sources are read through the context's queries, never its tables; a rebuild of a stream from its own events is the journal's concern and not this one.

## Intent

- actor: The operator who starts, interrupts, resumes, switches, rolls back, aborts or purges a generation through the operator entries, and the use cases whose live writes keep the generation being built current (D9, D19)
- problem: A per-entity read model is rebuilt while commands run and the rebuild is interrupted and resumed; a live command's incremental update on a row backfill has not written builds a partial one, a backfill batch overwrites newer data, an entity is missed at cutover, a deleted subject keeps its row, or a side effect replays; a cross-stream history view is rebuilt without a consistent cut (Sc L2-5, Sc L2-6)
- outcome: A per-entity read model rebuilds online as a new generation with no stale overwrite, no missing entity, no row of a subject that projects to none and no side effect, with the cutover in one write and a rollback that is one verify pass and then that switch of one write; a history-dependent view rebuilds under a write pause with safe resume and abort, and writes reopen only after verification (D9, Sc L2-5, Sc L2-6)
- value: The common rebuild costs no downtime and no projection job; the write pause is paid only where a consistent cut is needed (D9)
- risk: The standing cost is a generation registry read in every command that maintains a read model, a generation on every row, the earlier projection version kept in the code while its generation can be rolled back to, the batch chain, and for the write pause a gate every writer reads (D9)
- risk: A pass costs at least one batch per tenant of the tenant list, because a batch names one tenant, so a deployment of many empty tenants pays one scheduled mutation for each (E-49, Law 11)
- risk: A paused rebuild closes its view's sources in every tenant until the switch or the abort; its backfill and its verify pass each take one batch per source stream, one more for each further `history` page of a stream longer than the batch size, and one per tenant and source to end that source's enumeration, so the pause lasts about twice that count times one batch; a batch that took streams until its event bound was spent, or a generation of one tenant, which the registry does not offer, would shorten it (D9, E-8, E-40, D18)
- risk: The batch bound is a design choice under the transaction limits and no question of correctness: a batch that races a live command on one row is ordered by optimistic concurrency and the row ends at the source's newest stream version in either commit order, and a batch that reads past the read limit fails as a whole and leaves its checkpoint as it was (F13, F1, F17, Probe 6)
- assumption: Mutations are serializable under optimistic concurrency, so a backfill batch and a live command that touch the same row serialize and the loser re-runs (F1)
- assumption: A scheduled mutation that loses an optimistic-concurrency race is run again by Convex until it commits; the pinned packages do not show a bound on those runs, the design needs none for correctness, and Probe 6 shows what a stalled batch looks like (F9, F1, Probe 6)
- assumption: A parent query calling a component query stays reactive, so switching the active generation in the registry re-runs every subscription that reads it, and the enumeration's `paginator` page relayed by the parent stays contiguous under live writes; this is F15, and Probe 5 showed both on the pinned backend (F15, Probe 5, S4)
- assumption: Scheduling from a mutation commits with it, and a scheduled mutation retries internal errors and runs once (F8, F9)
- assumption: Backups exclude pending scheduled functions, so a restore drops the batch that was driving a generation and leaves its rows at the checkpoint; the restore procedure's inventory and resume are the recovery (F12, E-42)

### Open questions

- [non-blocking] `@convex-dev/migrations` walks only the tables of the component it is defined in, reaches a context's rows only through a parent internal mutation written by hand against a contract its README does not document and the compiled tier needs a cast for, keeps a status apart from the generation's state, and leaves no error on its row when a batch fails past the read limit, so every batch is driven by the rebuild's own self-scheduled internal mutation and the progress row is the one checkpoint; a hosted deployment and sustained contention are not observed (Probe 6, F1, F17, D9)

- [non-blocking] Extension E-8: the registry states, the rollback period, what a rollback does, the gate document, the scope a paused rebuild closes and the reach of a generation are design choices the doc does not make; they are pinned in the two contracts under this workflow (E-8, E-9, E-38, D9)
- [non-blocking] Extension E-8, what this workflow does not offer: the online path is pinned for a per-entity read model with one source stream type and the paused path for a history view, a `HistoryRebuildTarget` with its sources; an `AggregateProjection` has no rebuild here and gets one when a view needs it, and a row made from the current state of more than one source has no form at all, as `spec:application.projection-contract` records; `rollbackGeneration` refuses a generation that needs a write pause, because nothing would hold its sources while live commands fold onto a row that missed the events since its retirement, so such a view returns to earlier rules only through a new generation under the pause (E-8, E-9, D9, D18)
- [non-blocking] Extension E-49, a deployment whose grants predate the tenant list: the tenant list is written by `insertGrant`, so on such a deployment it holds no row while `grants` holds many, and a pass over an empty list visits no tenant and still ends; the option taken here is that `startGeneration` refuses an empty list beside a grant with a message naming `fillTenants`, and `fillTenants`, an operator entry, walks the grants in bounded batches through a progress row of its own and inserts each missing tenant once; a list that holds a tenant whose first grant came after the table and misses an older one is not detected by that refusal, so the operator runs `fillTenants` on such a deployment before its first `startGeneration` (E-49, E-48, E-40, Law 11)
- [non-blocking] Extension E-40, the shape of a history batch: a batch takes one stream, so a pass costs at least one scheduled mutation per source stream and the pause lasts about twice the stream count times one batch; the alternative is a batch that takes streams from one `list` page until its event budget is spent, one `history` call per stream, with the byte bound counting one baseline per stream; the first paused rebuild on the native backend measures one batch, and the shape is chosen with that number (E-40, E-9, F13, F19, D9)
- [non-blocking] The verify pass under the write pause: a history view's generation is built while no source changes, so its verify pass repeats the backfill's batches and, by `spec:application.rebuild#design.historyVerify`, finds nothing over a covered generation, which doubles the pause; the option kept here is the pass, as D9's "Verify coverage, then switch" and Sc L2-6's "writes reopen only after verification" read, and whether a paused generation is `verified` when its backfill ends is the owner's (D9, Sc L2-6)
- [non-blocking] Whether a history view's batch chain, at up to 2 MiB of rows per batch scheduled with `runAfter(0)`, is held by the deployment class's write throughput limit, `spec:facts.f13-transactions-have-limits#design.limitWriteThroughput`, which the first paused rebuild on the native backend and one hosted run show (F13, E-40)

## Workflow

- rule: Rebuild never runs commands or external effects (D9, Law 10)
- rule: Rebuild reads a source only through the context's queries, with the tenant as the one argument that scopes them, never through the context's tables (D10, D11, F11)
- rule: Online rebuild is the default for per-entity and current-state read models; the write pause is the exception, for read models that depend on history across several streams (D9)
- rule: Live commands also write the generation being built; a command that creates a stream writes its row, and while the generation is `building` a command on an existing stream updates the row only if backfill has already written it (D9)
- rule: [extension] Once the backfill has ended, in `verifying` and `verified`, a live write always lands as it does in the active generation, because a missing row then means a subject that projected to none and never a row backfill has yet to write; this is what lets one verify pass be enough (E-8, E-9, D9)
- rule: A backfill batch reads each source at its current stream version and writes the row only if the target is missing or older (D9)
- rule: [extension] Coverage is verified before the switch by one verify pass over every tenant and every source, which inserts a missing row, updates an older one and deletes the row of a subject whose DTO projects to `null`; the generation is `verified` when that pass ends, whatever it repaired, and the count of repairs is kept for the operator (E-8, D9, Sc L2-5)
- rule: [extension] The active generation switches in one write: one mutation that patches two generation rows together, the verified one to `active` and the active one to `retired`, or one row when the read model had no active generation, so no command and no query sees one row changed without the other; the old generation is kept for a rollback period (D9, E-8, F1)
- rule: [extension] A retired generation is not written; a rollback reopens the retired generation the operator names as `verifying`, one verify pass repairs what the writes since its retirement changed, presence and absence alike, and the ordinary switch makes it active, so a rollback is a verify pass and then a switch of one write, never one write by itself, and the current generation serves until that switch; a generation that needs a write pause is never reopened, and its view returns to earlier rules through a new generation under the pause (E-8, D9, Sc L2-5)
- rule: [extension] Each generation is written with the projection whose version its row records, by its batches and by live commands alike, and `startGeneration` and `rollbackGeneration` refuse a version the read model does not declare (E-9, E-8, D8)
- rule: Under the write pause every writer in the scope reads the maintenance gate, background writers are fenced or drained, and an operator can resume or abort (D9)
- rule: A refused write under the pause is a transient refusal, retryable and never a stored rejection (D4, D9)
- rule: [extension] Under the pause a history row's recorded version for a stream means every event of that stream with the row's key up to that version is folded: a stream's events reach the fold in version order, from its first event on the backfill and the verify pass and after its last folded version on the live path, a generation in flight is written by its own batches alone while its sources are closed, and no retired generation is reopened; so a verify pass that repeats the backfill and folds no event finds the generation covering every source (E-8, E-9, D9, F1)
- rule: Every batch has a stated bound below the transaction limits, tested against the pinned Convex version; the limits are ceilings, not batch sizes (D19, F13)
- rule: [extension] Every function that starts or changes a generation is an operator entry of `spec:command.actor-and-scope`: an internal function that records the stated operator on the generation row and reads no grant (E-48, D11, D19)
- rule: [extension] A generation spans every tenant of the deployment: its batches take one tenant at a time from `nextTenant` of the tenant list, in tenant-ID order, and name that tenant on every context call, so no call runs with an absent tenant as a wildcard, and the one registry row per read model answers every tenant's queries (D11, Law 11, E-8, E-49)
- rule: [extension] A tenant whose row enters the tenant list behind a backfill's cursor is not visited by that pass and needs no visit, because every stream it owns was created after the generation was registered and so was written live; the verify pass starts again at the first tenant and visits it (E-49, E-8, D9)
- rule: [extension] `startGeneration` refuses when the tenant list holds no row while the `grants` table holds one, with a message that names `fillTenants`, because a generation started then would visit no tenant, end its passes and be switched with no row of any tenant (E-49, E-8, Law 11)
- rule: [extension] `fillTenants` is an operator entry of `spec:command.actor-and-scope` that fills the tenant list from the `grants` table: its batches walk the grants in tenant-ID order, one distinct tenant per read, at most `limitTenantFillBatch` tenants per batch, through the `tenantFill` progress row of their own, and insert a tenant's row only where none exists, so each tenant is inserted once however often the walk runs; it reads a grant row only as the record that its tenant exists and never to authorize, and it writes nothing but tenant rows and its progress row (E-49, E-48, E-40, D11, Law 11)
- rule: [extension] A tenant fill and a generation in flight exclude each other: `fillTenants` refuses while a read model of the deployment has a generation in `building`, `verifying` or `verified`, and `startGeneration` and `rollbackGeneration`, which reopens a generation, refuse while the fill's pass is `fill`, so no tenant whose streams predate a generation enters the list behind that generation's cursor (E-49, E-8, D9, F1)
- rule: A backfill batch racing a live command is ordered by optimistic concurrency; the batch's read-then-write of a row is one mutation, so the batch never overwrites a row a command wrote after the batch read its source (D9, F1)
- rule: [extension] Every batch, whether its source is a context's enumeration or a parent table, is driven by a self-scheduled internal mutation under one batch contract, and the rebuild uses `@convex-dev/migrations` for nothing (E-40, F17, F8)
- rule: [extension] A projection version change is a new generation, never an in-place rewrite of the active one (E-8, D8)
- rule: [extension] The batch bound is a field of the progress row, the read model's by `batchSizeFor`, a whole number of at least 1 and at most `rebuildBatchCeiling(readModel)`; the context's `list` page bounds the bytes a batch reads, so a batch may take fewer entities than its size, and does not change the size; `startGeneration` sets it and nothing changes it after, so every pass and every resumed pass runs at the size on the row, and a purge batch deletes at most that many rows, capped by `limitPurgeBatch(readModel)` (E-40, E-24, E-9, F1, F13)
- rule: [extension] A generation has at most one live batch chain, the one whose batches carry the row's current fence; `interruptGeneration`, `resumeGeneration`, `rollbackGeneration`, `abortGeneration` and `purgeGeneration` each add one to the fence, so a batch scheduled before any of them checkpoints nothing and schedules nothing; `interruptGeneration` alone also sets `interruptedFence` to the new fence, and while it equals `fence` the stale batch writes only the interruption, on the progress row (E-40, E-8, F8)
- An operator calls `startGeneration` for a read model; it inserts the generation row in state `building` with the next generation number, the projection version and fence 1, inserts the progress row in the pass `backfill` with the batch size and a `null` cursor, and schedules the first backfill batch, all in one mutation; a read model with no generation gets generation 1 this way (D9, F8, E-8)
- [extension] On a deployment whose grants predate the tenant list an operator calls `fillTenants` before the first `startGeneration`; it inserts the `tenantFill` row, or reopens it, in the pass `fill` with a new fence and schedules the first fill batch; each fill batch reads the gate, takes up to `limitTenantFillBatch` further tenants from the grants after the row's cursor, inserts the tenant row of each that has none, saves the last tenant ID as the cursor and schedules the next fill batch, and the batch that finds no further tenant sets the pass to `idle` and schedules nothing (E-49, E-48, E-40, F8)
- From that commit every use case that maintains the read model writes the active generation, when there is one, and the one being built through `applyProjection`, in live-created mode for a stream it created and live-updated mode otherwise (D9, E-9)
- Each backfill batch runs as one mutation: it loads the generation row and the progress row, returns without writing if the state is not `building` or the pass is not `backfill`, returns when the fence differs, after recording the interruption as step 1 states while `interruptedFence` equals the fence, takes its tenant from the cursor, reads the gate, calls the source's `list` query once with `includeDeleted` and a page of the batch size from the saved cursor, applies the projection in backfill mode for each returned DTO at its current version, writes the new cursor and the counts on the progress row, and schedules the next batch, or, when the last tenant's last page is done, moves the generation to `verifying` and schedules the first verify batch (D9, D10, F1, E-40, E-49)
- A batch that throws leaves the generation at its last checkpoint; a backend interruption leaves the scheduled batch pending and it runs after the restart, an internal error is retried by Convex, and a developer error or a timeout ends the chain; the operator's `interruptGeneration` ends a chain on purpose, and `resumeGeneration` schedules a batch from the saved cursor with a new fence, at the batch size on the progress row; re-processing an entity is a no-op because its row is no longer older; a restore is the one interruption that leaves no batch pending, so `spec:application.restore` inventories every generation in `building` or `verifying` and its accepted branch resumes each one the operator did not abort through the same `resumeChain` (D9, F9, F1, F12, E-42, Sc L2-5)
- Each verify batch enumerates the sources again from the progress row's cursor, which the end of the backfill reset to `null`, the first tenant, and calls `applyProjection` in backfill mode for every DTO, so a missing row is inserted, an older one updated, and the row of a DTO that projects to `null` deleted; each such repair is counted as a miss; when the last tenant's last page is done the generation moves to `verified` and no batch is scheduled (D9, E-8, Sc L2-5)
- `switchGeneration` sets the verified generation `active` and, when the read model has an active generation, sets that one `retired` with `retiredAt` and `retireAfter`, in one mutation; every query reads the active generation from the registry, so every subscription on the read model re-runs (D9, F7, F1)
- [extension] During the rollback period the retired generation's rows are kept and not written; `rollbackGeneration` reopens the retired generation it is given, one without `pauseRequired`, as `verifying` with a new fence and a `null` cursor and schedules a verify batch, live commands write it again from that commit, its one verify pass repairs every row that is missing, older or left behind by a deleted subject, and the ordinary `switchGeneration` makes it active and retires the generation that served meanwhile (E-8, D9, Sc L2-5)
- `abortGeneration` marks a building, verifying or verified generation `aborted`, leaves the active generation untouched, and resumes every closed gate entry that names this generation; an aborted rollback leaves the reopened generation `aborted`, never `retired` again (D9, Sc L2-6, E-8)
- `purgeGeneration` starts the purge of an aborted generation, or of a retired one once `retireAfter` has passed; each purge batch deletes at most the progress row's batch size, capped by `limitPurgeBatch`, of rows of the generation for one tenant by the `by_key` range, stays on that tenant while a full batch came back, moves to the next tenant of the tenant list otherwise, and marks the generation `purged` after the last tenant; nothing starts a purge by itself, and a purge whose chain ended, a restore among the causes, is continued by `resumeGeneration` from its progress row (D19, E-40, E-49)
- For a history-dependent read model the generation row records `pauseRequired`, and `startGeneration` closes the maintenance gate for every source scope of the read model's bindings in the mutation that inserts the row, recording its own generation on each closed entry, so the gate is closed before the first batch is scheduled and this generation's batches are the one background writer allowed through (D9, E-8, E-38)
- While the gate is closed for the sources, every use case whose declaration writes one of them and the journal's baseline driver refuse with `writePaused` before any write, whether or not they maintain the view; a batch scheduled before the close reads the closed gate when it starts and refuses, a batch running when the close commits loses the optimistic-concurrency race on the gate document and re-runs into the refusal, and a batch of a superseded chain refuses because its generation fence is stale; nothing needs to drain (D9, D4, E-8, E-38, F1)
- Backfill under the pause enumerates a consistent cut because no source changes: each history batch takes the next stream of its cursor's source in its tenant, reads one `history` page of it from the saved event cursor, folds the page into the building generation through `applyHistoryProjection` in backfill mode, and saves the source, the stream and the event cursor on the progress row, moving to the next stream when the page reports `isDone`, to the next source when that source's enumeration in the tenant ends, and to the next tenant after the last source; an interrupted batch resumes from its cursor with the gate still closed, and the gate never reopens by itself (D9, E-9, Sc L2-6)
- Verification runs under the pause: the verify pass repeats the backfill's batches from the first tenant and source and counts as a miss every row they insert or update, which over a covered generation is none, so a miss is repaired by the batch that found it and the generation is `verified` when the pass ends; `switchGeneration` resumes every closed entry that names the generation in the mutation that makes it active, so writes reopen only after verification (D9, E-9, Sc L2-6)

## Design

Each batch is one scheduled internal mutation in the parent. The rebuild schedules from a mutation, so a batch is scheduled only if its predecessor committed. The rebuild is an operator's work on parent tables; it is not deferred business work and creates no obligation. The library exports one plain helper per entry below, of the same name, taking `(ctx, config: RebuildConfig, args)` and returning the entry's value; a composition's `rebuild` module registers each entry over its helper with its own `internalMutation` and `internalQuery`, so the entries are reached as `internal.rebuild.startGeneration` and so on, and no public function starts or changes a generation. Every refusal is a plain `Error` with the message given; in a message, `name` is the read model's name, `n` the generation number and `state` the generation's state. Beside the helpers the library exports `batchSizeFor`, `rebuildBatchCeiling`, `limitPurgeBatch`, `resumeChain`, the constants `limitTenantFillBatch` and `limitGenerationsListed`, and the types `RebuildConfig`, `RebuildTarget`, `BatchRef` and `FillBatchRef`. Every patch of a progress row or of the `tenantFill` row sets `updatedAt` to the writing mutation's `Date.now()`; a field written as absent, `lastError`, `retiredAt` or `retireAfter`, is removed from the document, which a patch with `undefined` does; a batch never writes `changedAt` or `changedBy`, which only an operator entry sets, and when it ends a pass it patches the generation row's `state`, and at the end of a purge also removes `retiredAt` and `retireAfter`, and nothing else on that row. A batch, and an operator entry that reads the progress row, over a generation that has no progress row throws `"No progress for generation " + generationId`.

The enumeration is the context's `list` query with `includeDeleted`, the one read of context data per batch: one call returns a page of up to `batchSize` DTOs and a continuation cursor, built inside the component by `paginator` from `convex-helpers` over the `by_identity` index that includes deleted subjects, and capped by the query at its byte-derived page bound. A batch reads `page`, `isDone` and `continueCursor` and ignores any split status, because the rows up to `continueCursor` are complete. A DTO carries the stream version the projection compares, as the queries contract's `toDto(state, meta)` maps it onto `version`. Deleted subjects reach the projection as DTOs the projection maps to `null`, so their rows are deleted rather than left behind.

- transactionBoundary: each batch is one scheduled internal mutation that commits its rows, its checkpoint and the scheduling of the next batch together; every operator entry that changes anything is one mutation, and `getGenerations` is one query (D9, F8, F9)
- convexSurface: `startGeneration`, `interruptGeneration`, `resumeGeneration`, `switchGeneration`, `rollbackGeneration`, `abortGeneration`, `purgeGeneration` and `fillTenants` as the operator entries, `backfillBatch`, `verifyBatch`, `purgeBatch` and `fillTenantsBatch` as the scheduled batches, all internal mutations, and `getGenerations` as an internal query, in the composition's `rebuild` module; the gate entries are in the write-pause contract (D9, E-8, E-48)
- typeRebuildTarget: `type RebuildTarget<D = any> = { readModel: ReadModel<D, any>; source: SourceRef; list: FunctionReference<"query", "internal", ListArgs, PaginationResult<D>> }` one per-entity read model the deployment can rebuild, its one source stream type, and the reference to that stream type's `list` query in its context component, such as `components.orders.queries.order.list` (E-8, E-9, D10)
- typeHistorySource: `type HistorySource = { source: SourceRef; list: FunctionReference<"query", "internal", ListArgs, PaginationResult<{ version: StreamVersion }>>; history: FunctionReference<"query", "internal", { tenantId: string; streamId: string; fromVersion?: number; paginationOpts: PaginationOptions }, PaginationResult<EventEnvelope>> }` one source stream type of a history view, with the references to its `list` and `history` queries of `spec:context.queries` in its context component, such as `components.inventory.queries.stockItem.list` and `components.inventory.queries.stockItem.history` (E-8, E-9, D10)

```gwt-vocabulary
Given a {viewKind:"per-entity"|"cross-stream history"} read model with an active generation
And a new generation registered as {mode:"building online"|"building under a write pause"}
And live commands {liveCommands:"keep running"|"are refused while paused"}
When the backfill is interrupted after {batches:number} batches and then {resumption:"resumed"|"aborted"}
Then no row of the new generation holds data older than its source stream version
And the new generation {coverage:"covers every stream enumerated at cutover"|"is discarded and read by no query"}
And no command or external effect ran during the rebuild
And the active generation {cutover:"switches in one write and can roll back"|"switches in one write and refuses a rollback"|"stays the old one"}
And writes {writes:"never stopped"|"reopen only after verification"|"reopen after the abort"}
```

## Verification — reviewed

- A reviewer confirms that every batch function states its bound and that the bounds sit below the F13 ceilings with the 1 second timeout in mind.
- A reviewer confirms that no rebuild function calls a context operation, schedules an action or writes anything but read-model rows, the generation row, the progress row, the gate and the gate's audit records.
- A reviewer confirms that the version compare in `applyProjection` is the only thing that prevents a stale overwrite and that L2-5's example asserts it against a concurrent live command.
- A reviewer confirms that a batch patches the generation row only in the mutation that ends its pass, and that no command or query over a read model reads the progress row.
- A reviewer confirms that every entry that changes a generation calls `assertOperator` first and writes the operator on the row, and that no rebuild function reads a grant or `ctx.auth`.
- A reviewer confirms that the gate is read inside every writer's mutation, not cached, that every batch reads it through `gateAllows` and parks its generation instead of throwing, that `startGeneration` closes one entry per source of a paused view and nothing else, and that the write-pause examples assert a refusal of a source writer while closed, the fold of the history view against the journal, and a reopen only after verification.
- A reviewer confirms that no registry function, batch or query takes a tenant scope for a generation, that every batch takes its tenant from `nextTenant` and names it on its context call, and that L2-5's example seeds more than one tenant and asserts both are covered at cutover.
- A reviewer confirms that a history target's `sources` name exactly the context and stream type pairs the view's bindings name, so `startGeneration` closes every writer of its sources, and that `rollbackGeneration` refuses every generation with `pauseRequired`.
- A reviewer confirms that `resumeChain` is the only code path that reschedules a stranded generation and that the restore's `finishRestoreRun` calls it for every generation its inventory lists in `building` or `verifying`.
- A reviewer confirms that `fillTenants` and `fillTenantsBatch` write only tenant rows and the `tenantFill` row, read a grant only through `by_principal` to find the next tenant, insert a tenant row only after a point read finds none, and that `startGeneration` refuses an empty tenant list beside a grant and a fill in its pass `fill`, and `fillTenants` a generation in flight.
- A reviewer confirms that no function writes a retired generation, that `rollbackGeneration` is the only transition out of `retired` besides purge, and that L2-5's example asserts that the reopened generation is `verified`, holds a row for a subject created since its retirement and none for a subject deleted since, before it is active.
