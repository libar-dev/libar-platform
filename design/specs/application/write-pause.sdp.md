# Write pause

Story · Detail: full · Traces: D4, D9, D19, Law 6, F1, F9, F12, F13, Sc L2-6, Sc L2-8, E-8, E-42, E-43, E-48.

The write pause is the maintenance gate every writer in a scope reads inside its own mutation. It exists for the rebuild of a read model that depends on history across several streams, where a consistent cut is needed, and the restore procedure holds the same door closed for every scope through the environment, because the backup archive replaces the gate document, until its checks pass. A closed gate turns every write in scope into a transient refusal, retryable and never stored; a background batch scheduled before the close reads the closed gate when it starts, and a batch of a superseded chain is refused by its generation's fence. The rebuild closes the gate for its own scope in the mutation that registers its generation, an operator entry closes a tenant or the whole deployment, and operator entries resume and abort. Nothing reopens the gate by itself. Optimistic concurrency makes the close a consistent cut, so the gate has one closed state and no drain.

## Intent

- outcome: Pin the maintenance gate document, the writer check every mutation in scope makes, the fencing of background writers, and the operator entries that close, resume and read the gate (D9, E-8)
- value: One document read per command gives the rebuild its consistent cut and the restore its closed door, with no lock protocol and no queue (D9, D1)
- risk: Every use case reads the gate document, one point read per command, and a gate change makes every concurrent command re-run once under optimistic concurrency (F1, E-8)
- risk: This contract states no acceptable length for a write pause; before a paused rebuild starts, its length is estimated as its backfill batches times the time of one batch plus its verify batches times the time of one batch, with the batch time taken from the first paused rebuild measured on the native backend, and whether that length is the trigger for an online history rebuild is ruled with that number and not before it (D9, D18)
- assumption: Mutations are serializable under optimistic concurrency, so a writer that read the gate as open cannot commit after a close that committed first (F1)
- assumption: A mutation reads a deployment's environment variable through `process.env`, and a change of the variable is seen by the next function run without a deploy, which `observedRestoreDoorWithoutDeploy` shows on the pinned local backend and no run has shown on a hosted deployment (E-42, F12)

### Open questions

- [non-blocking] Extension E-8: the doc names a maintenance gate every writer reads, fencing or draining of background writers, and operator resume and abort; the option taken here is one gate document per deployment holding the closed scopes, each in one `closed` state, with no fence of its own and no drain interval, because optimistic concurrency serializes every writer's gate read against the close and the generation row's fence already fences a rebuild's batches, and a refusal answered with `writePaused`, the transient code the outcome boundary reserves for this contract under its E-35, which this contract confirms; the scope a paused rebuild closes is the paused view's sources, one `source:` entry per context and stream type its bindings name, because a consistent cut must hold every writer of those streams and a use case that writes a source stream without maintaining the view would otherwise pass the gate, which is why the command declaration names what it writes under E-38 and the pipeline proves the list at its step 9; an operator entry closes only a tenant or `all`, the coarser and always safe scopes, and no scope names a read model, because nothing would close it (E-8, E-38, D9, D4, F1)

## Contract

- There is one gate document per deployment, read through `assertWritable`, which throws, by the command pipeline at its step 7 and by the grant helpers `insertGrant` and `revokeGrant` of `spec:command.actor-and-scope` before they write, and by every background batch at the start of its mutation through `gateAllows`, which answers and lets the batch park, never cached across mutations; the background readers are the rebuild's backfill, verify and purge batches, its tenant fill's `fillTenantsBatch`, and the journal's baseline driver of `spec:context.journal`, which writes a source stream and reschedules itself when refused; the only mutations that skip the read are the gate's own entries, the rebuild's `fillTenants`, which reads the restore door alone and is refused while it is closed, and the restore procedure's `startRestoreRun`, its check batches, its pending-work inventory and `finishRestoreRun`, which write only the `restoreRuns` record and the generation rows the accepted branch resumes, with their progress rows, while the restore door is closed, as `spec:application.restore` states; every command that reaches step 7 reads the gate; a duplicate answered from its receipt does not, because its answer writes nothing (D9, D6, E-8, E-25, E-37, E-42)
- A scope is `all`, one tenant, or one source stream type of one context; the gate holds the set of closed scopes, each with a reason, the generation it serves if any, and the operator who closed it (E-8, E-48, D9)
- A writer in a closed scope refuses before any write with the transient refusal `writePaused`, whose message carries the scope and the reason; nothing is stored, no operation ID is minted, and the same request key succeeds once the scope is open (D9, D4, Law 6)
- A use case is in scope when `all` is closed, when its tenant is closed, or when a stream type its declaration's `writes` names is closed (E-8, E-38, D9)
- The restore door is read before the gate document: while the deployment's `MAINTENANCE_MODE` environment variable is exactly `restore`, every gate read answers closed with the scope `all` and the reason `restore` and reads no document; any other value, and an unset variable, leave the answer to the gate document (D19, F12, Sc L2-8, E-42)
- A deployment with no gate document is open: the gate read never writes, and the first close inserts the document (E-8, D9)
- [extension] A rebuild that needs a consistent cut closes the sources of the paused view, one `source:` scope per context and stream type its bindings name, so every writer of those streams is held whether or not it maintains the view; the closed entries name the generation, and `abortGeneration` and the switch's resume reopen every entry that names it (E-8, E-38, D9, Sc L2-6)
- [extension] The rebuild a scope was closed for is the one background writer allowed through it: a gate read that states a generation passes a closed entry only when the entry names a generation and names that one, so an entry with no generation admits no one, and a gate read that states no generation passes no closed entry (E-8, D9)
- Background writers are fenced, not drained: a batch scheduled before the close reads the closed gate when it starts and refuses, a batch running when the close commits loses the optimistic-concurrency race on the gate document and re-runs into the refusal, a batch that committed first wrote before the cut, and a batch of a superseded chain returns without writing because the generation row's fence differs from its argument (D9, E-8, F1)
- The gate has one `closed` state per scope and no draining state, drain interval or confirmation step, because the serialization above already gives the consistent cut and a second state would only add an operator duty (E-8, F1)
- `startGeneration` closes one entry per source of a paused view and records its own generation on each in the mutation that inserts the generation row, so every entry that names a generation names a row that exists (D9, E-8)
- [extension] The operator entries are `closeGate` and `resumeGate` for the scope `all` and for a tenant scope, and `getGate` and `getGateAudit` to read; each follows the operator entry contract of `spec:command.actor-and-scope`, and a source scope is closed and reopened only by the rebuild (E-8, E-48, D19)
- Abort marks the generation aborted and resumes its scopes in one mutation (D9, Sc L2-6)
- [extension] A source scope closes only for a generation `startGeneration` registers: `rollbackGeneration` of `spec:application.rebuild` refuses a retired generation with `pauseRequired`, because no function would close its sources while live commands fold onto rows that missed the events since its retirement, so a history view returns to earlier rules only through a new generation, whose start closes its sources again (E-8, D9, Sc L2-6)
- The restore procedure cannot use the gate document, because the backup archive replaces it; the restore door keeps every writer out through the environment, which survives a restore because backups exclude environment variables; the restore procedure's own mutations, which write only `restoreRuns` and the generation rows the accepted branch resumes with their progress rows, are the one exemption, and that workflow states it (D19, F12, Sc L2-8, E-42)
- [extension] A closed entry the backup archive brings back is as closed as one written live: an entry that names a generation stays closed while the restore's pending-work step resumes that generation, and reopens only when that generation is switched or an operator aborts it, and a tenant or `all` entry stays closed until an operator resumes it, so the gate never reopens by itself through a restore either (E-8, E-42, F12, D19)
- [extension] Gate changes are treated as mandatory audit: every close and every resume inserts one record through `writeOperatorAudit` of `spec:operations.baseline-operations` inside the same mutation and fails closed, so a gate change whose audit insert fails changes nothing: the gate document is as it was and no record exists; the doc fails closed only for mandatory business or security audit and does not name gate changes among them (E-8, E-43, D19)
- A local reaction refused by the gate is delayed, not counted: the obligation wrapper reschedules the same attempt without incrementing its attempt count, as `spec:obligations.local-reaction-wrapper` rules, so a pause never turns pending work into needs attention (D13, D9, E-51)

## Design

The gate is one document so that a command pays one point read. Scopes are strings so that the same document serves tenants, source stream types and the whole deployment without a table per kind. The refusal is a `ConvexError` whose data is the outcome boundary's `TransientData`. The table is `gateTables`, a schema fragment the library exports, and `GateDataModel` is its data model; every composition that registers a command spreads it into its schema, because step 7 reads it. The library exports the four operator entries as registered internal functions, built with `internalMutationGeneric` and `internalQueryGeneric` of `convex/server`, and a composition's `gate` module re-exports them, so they are reached as `internal.gate.closeGate`, `internal.gate.resumeGate`, `internal.gate.getGate` and `internal.gate.getGateAudit`. Every refusal of an operator entry is a plain `Error` with the message given.

- validatorClosedEntry: `const closedEntryValidator = v.object({ scopeKey: v.string(), reason: v.string(), generationId: v.optional(v.id("generations")), changedAt: v.number(), changedBy: v.string() })` where `changedBy` is the stated operator and `changedAt` the closing mutation's `Date.now()` (E-8, E-48)
- tableMaintenanceGates: `maintenanceGates: defineTable({ key: v.literal("gates"), closed: v.array(closedEntryValidator), updatedAt: v.number() }).index("by_key", ["key"])` holding at most one document, whose `closed` lists the entries in the order they were closed (E-8, D9)
- indexGatesByKeyUse: the one point read every writer makes, `.withIndex("by_key", (q) => q.eq("key", "gates")).unique()`; an absent document reads as no closed scope (E-8, D9)
- typeScopeKey: `type ScopeKey = "all" | string` where a tenant scope is `"tenant:" + tenantId` and a source scope is `"source:" + contextId + ":" + streamType`, built only by `scopesOfUseCase`, `startGeneration`, the rebuild's batches, the journal's baseline driver and the operator entries (E-8, E-38, D11)
- fnGateAllows: `gateAllows(ctx: { db: GenericDatabaseReader<GateDataModel> }, scopes: readonly ScopeKey[], allowGeneration?: Id<"generations">): Promise<{ allowed: true } | { allowed: false; scopeKey: ScopeKey; reason: string }>` the one gate read: it first reads `process.env.MAINTENANCE_MODE` and answers `{ allowed: false, scopeKey: "all", reason: "restore" }` without reading the document when the value is `restore`; otherwise it reads the gate document once and answers not allowed with the `scopeKey` and `reason` of the first entry of `closed`, in array order, whose `scopeKey` is one of `scopes` and which is not exempt, and allowed when there is none; an entry is exempt only when `allowGeneration` is given, the entry has a `generationId`, and the two are equal; it writes nothing (E-8, E-42, D9, F9)
- fnAssertWritable: `assertWritable(ctx: { db: GenericDatabaseReader<GateDataModel> }, scopes: readonly ScopeKey[]): Promise<void>` calling `gateAllows` with no generation and, when the answer is not allowed, throwing through the boundary's `refuseTransient({ code: "writePaused", message: "write paused for " + scopeKey + ": " + reason })`; the command pipeline's step 7 calls it before it mints the operation, and `insertGrant` and `revokeGrant` of `spec:command.actor-and-scope` call it with `scopesOfUseCase(grant.tenantId, [])` before their first read; nothing else does (E-8, D9, E-35, E-37)
- errorCodeWritePaused: `writePaused`, the transient code the outcome boundary reserves; the refusal's data is exactly `{ kind: "transient", code: "writePaused", message }` with no `retryAfterMs`, where `message` is `"write paused for all: restore"` under the restore door and `"write paused for tenant:" + tenantId + ": " + reason` for a closed tenant; a transient refusal, never a stored rejection, so no receipt, event, read-model row or audit record exists for the refused command (D4, Law 6, E-35)
- restoreDoor: `gateAllows` runs in the parent and reads `process.env.MAINTENANCE_MODE` before the gate document; only the exact value `restore` closes the door, so the restore procedure keeps writers out even though the backup archive replaced the gate, and every rebuild batch parks until the accepted branch resumes it; the restore procedure's own six mutations call neither `gateAllows` nor `assertWritable`; no component reads the variable (E-42, D19, F11)
- fnScopesOfUseCase: `scopesOfUseCase(tenantId: string, writes: readonly SourceRef[]): ScopeKey[]` returning `"all"`, the tenant scope and one source scope per `SourceRef` of the declaration's `writes`, in that order, so a command is held by a closed deployment, by its closed tenant and by a paused rebuild of any view whose sources it writes (E-8, E-38, D9)
- fnCloseScope: `closeScope(ctx: MutationCtx, scopeKey: ScopeKey, reason: string, operator: string, generationId?: Id<"generations">): Promise<void>` throwing `"The scope " + scopeKey + " is already closed"` when `closed` holds an entry with that `scopeKey` and `"The gate holds 16 closed scopes, its limit"` when it holds `limitClosedScopes` entries; otherwise appending the entry to `closed`, inserting the document when there is none, setting `updatedAt`, and calling `writeOperatorAudit(ctx, { kind: "gate.close", scopeKey, reason, generationId, operator })` in the caller's mutation; called by `closeGate` and by the rebuild's `startGeneration`, which passes the ID of the generation row it has just inserted (E-8, E-43, E-48, D9, D19)
- fnResumeScope: `resumeScope(ctx: MutationCtx, scopeKey: ScopeKey, operator: string): Promise<void>` throwing `"The scope " + scopeKey + " is not closed"` when `closed` holds no entry with that `scopeKey`; otherwise removing the entry, setting `updatedAt`, and calling `writeOperatorAudit(ctx, { kind: "gate.resume", scopeKey, reason: entry.reason, generationId: entry.generationId, operator })` in the caller's mutation, the reason and the generation being those of the entry it removed; called by `resumeGate` and by the rebuild's `abortGeneration` and `switchGeneration` (E-8, E-43, E-48, D9, D19)
- fnCloseGate: `export const closeGate = internalMutation({ args: { scopeKey: v.string(), reason: v.string(), operator: v.string() }, returns: v.null(), handler })` the operator entry to `closeScope` with no generation: it calls `assertOperator`, throws `"closeGate takes the scope all or a tenant scope, and " + scopeKey + " is neither"` unless `scopeKey` is `all` or `tenant:` followed by a tenant ID of 1 to `limitIdLength` bytes, throws `"The reason must be between 1 and 256 bytes"` unless `utf8Length(reason)` is, and then calls `closeScope`; it does not read the tenant list, so a tenant may be closed before its first grant (E-8, E-48, D9, D19)
- fnResumeGate: `export const resumeGate = internalMutation({ args: { scopeKey: v.string(), operator: v.string() }, returns: v.null(), handler })` the operator entry to `resumeScope`: it calls `assertOperator`, makes the scope check of `closeGate` with `resumeGate` in the message, so a source scope is never reopened ahead of its rebuild, and then calls `resumeScope` (E-8, E-48, D9, Sc L2-6)
- fnGetGate: `export const getGate = internalQuery({ args: {}, returns: v.object({ restore: v.boolean(), closed: v.array(closedEntryValidator) }), handler })` answering `restore` true when `MAINTENANCE_MODE` is `restore` and `closed` as the document holds it, empty when there is no document (E-8, E-42, D19)
- fnGetGateAudit: `export const getGateAudit = internalQuery({ args: { scopeKey: v.string(), paginationOpts: paginationOptsValidator }, returns: paginationResultValidator(operatorAuditDoc), handler })` paging the `operatorAudit` records of one scope by `by_scope`, newest first, at most 100 a page, a request for more answered with a page of 100, passing the paginator only the request's `cursor` and the capped `numItems`, so an `endCursor` in the request is ignored and cannot widen a page, where `operatorAuditDoc` is the `operatorAudit` table's document validator with `_id` and `_creationTime` (E-8, E-43, D19)
- occSerialization: a writer's mutation reads the gate document, or the index range that holds none; a close that commits first invalidates that read, the writer re-runs, reads the closed gate and refuses; a writer that commits first wrote before the close, which is the consistent cut; a batch scheduled before the close but started after it reads the closed gate like any writer, so no closing state, drain interval or confirmation is needed, and the one-second mutation timeout plays no part (F1, D9, E-8)
- observedRestoreDoorWithoutDeploy: [extension] on the local backend `precompiled-2026-09-28-5c7cb5b` with `convex` 1.46.0, a change of `MAINTENANCE_MODE` through the admin API's update of environment variables is seen by the next function run with no deploy: set to `restore`, the next command in every tenant, through the public and the internal entry, is refused with `"write paused for all: restore"` and `getGate` answers `restore` true; set to another value, `Restore` among them, the refused request keys apply; `spec:application.write-pause.restore-door-without-deploy` binds it at the native backend tier, and it is read again when the pin moves (E-42, F12)
- limitClosedScopes: at most 16 scopes closed at once, so the gate document stays a few kilobytes and the writer check scans an array in memory (E-8, F13)
- limitGateReason: a reason is 1 to 256 bytes of UTF-8, so the refusal's message stays under a kilobyte (E-8, F13)
- limitGateReadsPerCommand: 1 point read per command that reaches step 7, none for a duplicate answered from its receipt, and none while the restore door is closed; the first experiment counts it (E-8, Sc L2-3)

## Verification — reviewed

- A reviewer confirms that `assertWritable` is called by the command pipeline's step 7 for every command that reaches it and by the two grant helpers before they write, that `gateAllows` is called by every background batch before its first write and that the batch parks rather than throws on a refusal, that the two are one read because `assertWritable` is `gateAllows` plus the throw, that the gate's entries and the restore procedure's six mutations are the only exemptions, and that no function caches the gate across mutations.
- A reviewer confirms that `gateAllows` reads the environment before the document, that an entry with no generation is never exempt, and that a gate read with no generation passes no closed entry.
- A reviewer confirms that no function other than `startGeneration` closes a source scope, so every closed entry that names a generation names a row that exists, and that the journal's baseline driver reads the gate with the source scope of the stream type it migrates before every batch.
- A reviewer confirms that `closeScope` and `resumeScope` are the only writers of the gate document, that each inserts its audit record in the same mutation with no catch around it, and that a test whose audit table refuses the record finds the gate unchanged.
- A reviewer confirms that `writePaused` appears in the outcome boundary's closed code list as a transient refusal and is never stored as a rejection.
- A reviewer confirms that the restore workflow sets `MAINTENANCE_MODE` before the backup archive is restored and clears it only after its checks.
