# Generation registry

Story · Detail: full · Traces: D8, D9, D11, D19, F1, F12, F13, Law 6, Law 11, E-8, E-9, E-40, E-42, E-48, E-49.

The registry is two parent tables. The `generations` table records every generation of every read model with its state, its projection version and its fence, and it is the row a command and a query read. The `generationProgress` table holds, per generation, the cursor, the batch size and the counts of the batches that build, verify and purge it, and only a batch and an operator entry read it. A generation is a build of the projection's code, which is the same for every tenant, so one generation row spans every tenant of the deployment and its batches iterate the tenants; there is no generation of one tenant and no rebuild for one tenant. A use case reads the registry once per read model it maintains to learn which generations to write; a query reads it once to learn which generation to read; the rebuild owns the rows. The registry changes only at a transition of a generation, so it is not an application-wide counter in the write path.

## Intent

- outcome: Pin the generations table and its states, the progress row, every transition with who may make it, the per-entity marker document, and the reads a command and a query make against them (D9, E-8)
- value: One table answers which generation is active, which is being built and which is still inside its rollback period, so live update, backfill, queries and operators agree without a second store (D9)
- risk: A registry read sits in every command that maintains a read model, at most two indexed reads per read model; every transition of a generation changes a row those reads cover, so each transition re-runs the commands in flight on that read model once (D9, F1, Sc L2-3)
- risk: A projection version stays in the code for as long as a generation that records it is written or may be rolled back to (E-9, D9)
- assumption: Mutations are serializable under optimistic concurrency, so a switch and a concurrent command that read the registry serialize (F1)

### Open questions

- [non-blocking] Extension E-8: the doc names a generation registry, a marker and a gate without their shapes, and says to keep the old generation for a rollback period without saying whether live commands keep writing it; the option taken here is the `generations` and `projectionMarkers` tables below with seven states, a rollback period of 7 days, one generation being built per read model at a time, and a retired generation that is kept and not written, so that a rollback reopens it as `verifying`, one verify pass repairs what the writes since its retirement changed, and the ordinary switch makes it active again; a rollback is therefore a verify pass and then a switch of one write, never one write by itself (E-8, D9, Sc L2-5)
- [non-blocking] Extension E-8, reach of a generation: the doc says nothing about tenants and rebuild; one generation per read model spans every tenant, the registry has no tenant dimension, one row is active for all tenants and the batches iterate the tenant list of `spec:command.actor-and-scope`; the registry is operational data of the deployment, so its indexes lead with the read model name and not with `tenantId`, a confirmed deviation from Law 11's index rule of the same kind the obligation module records under E-57, while every table that holds tenant data, the read-model rows and the markers among them, leads with the tenant; a rebuild for one tenant is not offered (E-8, D9, D11, Law 11, E-57)
- [non-blocking] Extension E-42, as it touches the registry: a restore brings back a generation row and its progress row at their checkpoint and drops the scheduled batch that was driving them, so the row's fence at inventory time is the restore's proof that the generation is still stranded, and `resumeChain` bumping it is the proof that it is not (E-42, F12)
- [non-blocking] Extension E-8, the first generation: the doc says how a generation is rebuilt and not how a read model's first generation comes to exist; the option taken here is that a read model is installed through its first rebuild, generation 1 starting as `building` like any other, so a read model added to a deployment that has history serves that history from its first switch and no transition claims coverage it did not build; a command that finds no generation to write fails as a technical failure and a query that finds no active generation fails the same way (E-8, D9, D19)
- [non-blocking] Extension E-40, the checkpoint: the cursor, the batch size and the counts live on the progress row and not on the generation row, because a batch that wrote its checkpoint on the row every command reads would re-run every command in flight on the read model once per batch; the progress row is the one checkpoint of every batch whatever drives it (E-40, F1)
- [non-blocking] Extension E-49, as it touches the registry: on a deployment whose grants predate the tenant list the list is empty while grants exist, and a generation started then visits no tenant; the option taken here is that `startGeneration` refuses then, with a message naming `fillTenants`, the operator entry of `spec:application.rebuild` that fills the list from the grants, and refuses while that fill runs (E-49, E-8, Law 11)

## Contract

- Every generation of a read model has one row keyed by read model name and generation number, and generation numbers increase by one per read model, starting at 1 (E-8, D9)
- A generation is in exactly one of `building`, `verifying`, `verified`, `active`, `retired`, `aborted` or `purged` (E-8, D9)
- At most one generation per read model is `active`, and at most one is in `building`, `verifying` or `verified`; these three states are the in-flight states (E-8, D9)
- The allowed transitions are none to building by `startGeneration`, building to verifying by the backfill batch that ends the enumeration, verifying to verified by the verify batch that ends its pass, verified to active by `switchGeneration`, active to retired by the same `switchGeneration`, retired to verifying by `rollbackGeneration`, building, verifying or verified to aborted by `abortGeneration`, and retired or aborted to purged by the purge batch that ends its pass; no other transition exists, and none leads from nothing to active; `interruptGeneration` and `resumeGeneration` change no state, and `resumeGeneration` continues the pass the progress row names, a started purge of a `retired` or `aborted` generation included, at the batch size the progress row holds, since it takes no batch size (E-8, D9, E-40)
- An operator entry of `spec:application.rebuild` makes the transitions named after it, a scheduled batch makes the other three, and nothing else writes a generation row (E-8, E-48, D19)
- [extension] `startGeneration` refuses, and so makes no transition, while the tenant list of `spec:command.actor-and-scope` holds no row and the `grants` table holds one, with a message that names `fillTenants`, and while the tenant fill of `spec:application.rebuild` is in its pass `fill`, because a generation that walked an empty or half-filled list on a deployment whose grants predate the list would be verified and switched without the rows of the tenants it missed (E-49, E-8, Law 11)
- [extension] A read model's first generation is generation 1 in `building`, started by `startGeneration` like any other, and the read model has an active generation only after that generation is verified and switched; on a deployment with no subject the build is one backfill batch and one verify batch for each tenant of the tenant list, and one of each when the list is empty (E-8, D9)
- A command that maintains a read model writes the active generation and the in-flight generation if one exists; a retired generation is kept unchanged until it is purged and never written, and a rollback reopens it as `verifying` so that live commands write it again while its verify pass repairs it (D9, E-8)
- [extension] Each generation is written with the projection whose version its row records, on the live path and by its batches alike, so the rows of one generation are one truth of one projection version (E-9, E-8, D8)
- A query reads the active generation and nothing else; a query over a read model that has no active generation throws a plain error that names the read model, a technical failure, and never answers an empty page (D9, E-8, Law 6)
- [extension] The generation row carries the state, the projection version, the fence and who started and last changed it, and nothing a batch writes on its healthy path except the state that the batch ending a pass sets; the progress row carries the cursor, the batch size and the counts, the batch size set by `startGeneration` and never changed after, so every pass of the generation, a resumed one and its purge included, runs at it, a purge batch capped further by `limitPurgeBatch` of `spec:application.rebuild`, and a batch writes it in the same mutation as its rows, so the progress row is the checkpoint (E-40, D9, F1)
- [extension] A generation spans every tenant of the deployment and the registry row names none; the tenant is named on every read-model row and marker, on every context call a batch makes, and in the batch cursor, so no read or write of tenant data runs with an absent tenant as a wildcard, and no generation can be switched for one tenant alone (E-8, D11, Law 11)
- An aggregate read model keeps one marker per entity per generation with the contribution last recorded and the source versions it was computed from, and every aggregate write reads and writes the marker in the same mutation as the aggregate row; the marker's `sourceVersions` are compared like a row's, so a DTO older than the marker never adjusts the sum (D9, E-8, E-9)
- [extension] A generation whose progress row is in the pass `backfill`, `verify` or `purge` has at most one scheduled batch driving it, identified by the row's fence; a restore brings the rows back at their checkpoint and drops that batch with every pending scheduled function, so the generation is stranded until `resumeChain` bumps the fence and reschedules from the saved cursor, which the restore procedure's pending-work inventory and accepted branch drive for every such generation in `building` or `verifying`, and which the operator drives with `resumeGeneration` for a purge the restore stranded, because a purge belongs to a `retired` or `aborted` generation the inventory does not read (E-42, E-8, F12, D19)
- The registry is read, never incremented, in the command path; it is not an application-wide counter (D2, E-8)
- Registry, progress and marker rows are operational data owned by the parent; they are never written by a context (D2, E-8)
- [extension] A command whose declared read model has no generation to write fails as a technical failure, a plain error that names the read model, so a command never commits without its read model (E-8, D8, Law 6)
- [extension] The operator a generation row records is the string the operator entry was given, as `spec:command.actor-and-scope` rules it: `startedBy` from `startGeneration` and `changedBy` from the last operator entry that changed the row (E-48, D19)

## Design

Tables live in the parent's `schema.ts`, spread from the library's `readModelTables`. `streamVersionValidator` is the kernel's validator for `StreamVersion`. The registry has no `tenantId` because every generation spans all tenants; the marker table is tenant data and leads with the tenant. Every refusal below is a plain `Error` with the message given.

- validatorGenerationState: `const generationStateValidator = v.union(v.literal("building"), v.literal("verifying"), v.literal("verified"), v.literal("active"), v.literal("retired"), v.literal("aborted"), v.literal("purged"))` (E-8, D9)
- tableGenerations: `generations: defineTable({ readModel: v.string(), generation: v.number(), projectionVersion: v.number(), state: generationStateValidator, pauseRequired: v.boolean(), fence: v.number(), startedAt: v.number(), startedBy: v.string(), changedAt: v.number(), changedBy: v.string(), switchedAt: v.optional(v.number()), retiredAt: v.optional(v.number()), retireAfter: v.optional(v.number()) })` where `changedAt` and `changedBy` are the time and the operator of the last operator entry that changed the row, `switchedAt` is when the generation last became active, and `retiredAt` and `retireAfter` are set while it is `retired` and absent otherwise (E-8, E-48, D9, F13)
- indexGenerationsByReadModel: `.index("by_read_model", ["readModel", "generation"])` (E-8)
- indexGenerationsByReadModelUse: the next generation number at `startGeneration`, read as the last row in descending order, and the operator listing `getGenerations` (E-8, D9)
- indexGenerationsByReadModelState: `.index("by_read_model_state", ["readModel", "state"])` (E-8)
- indexGenerationsByReadModelStateUse: `generationsToWrite` in every command that maintains the read model, `activeGeneration` in every query over it, and the in-flight check of `startGeneration`, `switchGeneration` and `rollbackGeneration` (D9, E-8)
- validatorBatchCursor: `const batchCursorValidator = v.object({ tenantId: v.string(), pageCursor: v.union(v.string(), v.null()), streamId: v.optional(v.string()), eventCursor: v.optional(v.union(v.string(), v.null())) })` the position of a pass, the tenant being iterated and the `paginator` cursor within it, `null` at the start of a tenant; `streamId` and `eventCursor` are set only by the batches of a history view (E-8, E-40, Law 11)
- validatorProgressPass: `const progressPassValidator = v.union(v.literal("backfill"), v.literal("verify"), v.literal("purge"), v.literal("idle"))` naming the pass a batch chain is driving, `idle` when none is (E-40)
- tableGenerationProgress: `generationProgress: defineTable({ generationId: v.id("generations"), pass: progressPassValidator, batchSize: v.number(), cursor: v.union(batchCursorValidator, v.null()), batchesDone: v.number(), rowsWritten: v.number(), rowsSkipped: v.number(), misses: v.number(), rowsPurged: v.number(), lastError: v.optional(v.string()), updatedAt: v.number() })` one row per generation, inserted by `startGeneration` in the mutation that inserts the generation row; `cursor` is the position in the pass that `pass` names and `null` before that pass has read its first tenant; `batchesDone` counts every batch of the generation that reached its checkpoint, the batch that ends a pass included and a parked batch not, `rowsWritten` the rows a backfill batch inserted, updated or deleted, `rowsSkipped` the items a backfill or verify batch left as they were, `misses` the rows the current verify pass inserted, updated or deleted, and `rowsPurged` the rows a purge deleted (E-40, D9, F13)
- indexProgressByGeneration: `.index("by_generation", ["generationId"])` (E-40)
- indexProgressByGenerationUse: the one read a batch and an operator entry make to find a generation's progress row; no command and no query over a read model reads the table (E-40, F1)
- tableProjectionMarkers: `projectionMarkers: defineTable({ tenantId: v.string(), readModel: v.string(), generation: v.number(), entityKey: v.string(), aggregateKey: v.string(), contribution: v.number(), sourceVersions: v.array(streamVersionValidator) })` (E-8, D9, Law 11)
- indexMarkersByEntity: `.index("by_entity", ["tenantId", "readModel", "generation", "entityKey"])` (E-8)
- indexMarkersByEntityUse: point read by `applyAggregate` before every aggregate write (D9, E-8)
- typeRegistryReader: `type RegistryReader<DataModel extends ReadModelDataModel = ReadModelDataModel> = { db: GenericDatabaseReader<DataModel> }` and `type RegistryWriter<DataModel extends ReadModelDataModel = ReadModelDataModel> = { db: GenericDatabaseWriter<DataModel> }`, the part of a ctx the registry's helpers use, where `ReadModelDataModel` is the data model of `readModelTables`, the schema fragment that holds `generations`, `generationProgress`, `projectionMarkers` and the tenant fill's `tenantFill` row of `spec:application.rebuild`; every helper that takes them is generic over the composition's data model, because a database reader is not covariant in its data model (E-8)
- typeWritableGeneration: `type WritableGeneration = { role: "active" | "building" | "verifying"; generation: number; projectionVersion: number }` where the role is `active` for the state `active`, `building` for the state `building`, and `verifying` for the states `verifying` and `verified` (E-8, E-9, D9)
- fnGenerationsToWrite: `generationsToWrite<DataModel extends ReadModelDataModel>(ctx: RegistryReader<DataModel>, readModel: string): Promise<WritableGeneration[]>` making at most two indexed reads, the ranges of `by_read_model_state` from `active` to `building` and from `verified` to `verifying`, throwing `"Read model " + readModel + " has " + a + " active generations and " + b + " in building, verifying or verified"` when they hold two active generations or two in-flight ones, and returning one entry per generation a command writes, the active generation first when there is one, then the in-flight one, and an empty list when the read model has neither; the answer is the same for every tenant (E-8, D9)
- fnActiveGeneration: `activeGeneration<DataModel extends ReadModelDataModel>(ctx: RegistryReader<DataModel>, readModel: string): Promise<number | undefined>` making one indexed read and answering `undefined` when the read model has no active generation, which a query over the read model then turns into the plain error `"The read model " + readModel + " has no active generation"`; the answer is the same for every tenant, and the query narrows the rows it reads by its own `tenantId` argument (E-8, D9, Law 11)
- errorNoGenerationToWrite: the pipeline's step 9 throws `commandType + " writes the read model " + readModel + ", which has no generation to write"` when `generationsToWrite` answers an empty list, which is the case before `startGeneration` and after the only generation was aborted (E-8, D8, Law 6)
- markerVersionCompare: `applyAggregate` treats the marker's `sourceVersions` as a row's: a marker whose versions are not older than the input's makes the write `skipped-newer` and leaves the sum alone, so a stale DTO on either path never adjusts an aggregate twice or backwards (E-9, E-8, D9, F1)
- transitionCost: a transition patches one generation row, or two in the one write of a switch that retires an active generation, a single mutation, and every command in flight on the read model that read the registry before it re-runs once; a batch writes a generation row only in the mutation that ends its pass, so a build costs the commands one such re-run at the end of the backfill and one at the end of the verify pass, plus one per operator entry, `startGeneration` and `switchGeneration` among them (E-40, F1, D9)
- limitRegistryReadsPerCommand: at most 2 indexed reads per read model per command, because the pipeline's step 9 calls `generationsToWrite` once per read model name however many bindings name it, and one per query (E-8, F13)
- limitRollbackPeriod: 7 days by default, 604,800,000 ms; `switchGeneration` takes an override between 0 and 2,592,000,000 ms, and `rollbackGeneration` is refused once `retireAfter` has passed because the rows may be purged (E-8, D9)
- limitMarkerCount: one marker per entity per generation; a read model with N entities costs N markers per generation (E-8, F13)

## Verification — reviewed

- A reviewer confirms that every transition in the rebuild workflow is one of the transitions listed here, that no function sets a state outside them, and that no function inserts a generation in a state other than `building`.
- A reviewer confirms that `generationsToWrite` and `activeGeneration` are the only readers of the registry in the command and query paths, that neither writes it, and that neither reads `generationProgress`.
- A reviewer confirms that no batch patches a generation row except in the mutation that ends its pass.
- A reviewer confirms that the marker table's index leads with the tenant, that `applyAggregate` reads it before every aggregate write, and that it compares the marker's `sourceVersions` before adjusting the sum.
- A reviewer confirms that no field, index or function of the registry carries a tenant, that every batch cursor names one, and that the restore's inventory reads `by_read_model_state` for the three in-flight states and nothing else.
