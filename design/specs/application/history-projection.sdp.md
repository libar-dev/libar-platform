# History projection

Story · Detail: full · Traces: D2, D8, D9, D18, Law 6, Law 10, F1, F13, Sc L2-6, E-7, E-9, E-25, E-40, E-46.

A history projection is the form of a read model whose row depends on history across several streams: it folds events into the prior row, where a per-entity projection builds a row from one DTO. The contract pins the `HistoryProjection` shape and `applyHistoryProjection`, the one helper that folds and writes such a row, shared by the command pipeline's step 9 and the rebuild's history batches; a fold that gives one row whatever the order across streams and however the events are split between calls; a row that no fold deletes, which keeps its subject's ended state; baselines dropped before `keyOf`; the `sourceVersions` that keep an event from being folded twice; and the order allocation history of the example domain, with its table, its rules and the bound on what one call reads and writes.

## Intent

- outcome: Pin the history form of a projection, which folds the events of several streams into one row that the live path and the backfill write alike (E-9, D8, D9)

### Open questions

- [non-blocking] Extension E-9, the history fold: D2 orders events only within a stream, and the two paths feed one history row in different orders, the live path command by command and the backfill stream by stream; the option taken here is a fold that gives one row whatever the order across streams and however its events are split between calls, a row no fold deletes, which keeps its subject's ended state, and baselines dropped before `keyOf`, so a view whose meaning needs the order across streams waits for the ordered consumer of D18 (E-9, D2, D9, D18, E-25)
- [non-blocking] Extension E-9, the history form's one version: a `HistoryProjection` declares one version, so a deploy that changes it leaves the active generation, which records the earlier version, unwritable, and every command whose events feed the view fails as a technical failure until a generation of the new version is switched; the option taken here is that one version, because a view rebuilt under the pause is never written by two versions at once, and a list of versions like the `projections` of a `ReadModel` is the form a view takes when its sources must stay writable across such a deploy (E-9, D8, D9, Law 6)

## Contract

- [extension] A history projection folds events into a row: `keyOf` maps each event to the row it belongs to or to none, and `project` folds the events of one key, each stream's in stream-version order and the streams interleaved in any order, into the prior row; it is deterministic in the prior row and the events, reads nothing else, and is the one form a read model that depends on history across several streams may take, which is why such a read model rebuilds only under the write pause (E-9, D8, D9, Law 10)
- [extension] A history projection's fold gives the same row whatever the order in which the events of different streams arrive and however they are split between calls: from one prior row, the events of one key folded in one call or in several, with the streams interleaved in any way that keeps each stream's events in version order, give equal rows; D2 orders events only within a stream, and the live path feeds a row command by command while the backfill feeds it stream by stream, so a view whose meaning depends on the order across streams is not a history projection and waits for the ordered consumer of D18 (E-9, D2, D8, D18)
- [extension] `project` never answers `null`: a history row, once written, keeps its subject's ended state, such as a cancelled order, and leaves its table only when its generation is purged, so its `sourceVersions`, the fold's one memory, outlive the subject's end, and an event that arrives after it, such as `AllocationReleased` after `OrderCancelled`, folds into the row and never makes a new one (E-9, D9)
- [extension] `applyHistoryProjection` drops every event of the reserved type `baseline` before `keyOf`, on both paths: a baseline holds a stream's migrated state and no fact a view folds, and a migration that changes what a source's earlier events mean to the view is a new projection version and so a new generation, never a rewrite of rows in place (E-9, E-25, D9)
- [extension] A history row's `sourceVersions` hold, per source stream, the highest event version folded into it; `applyHistoryProjection` drops every event whose version is not above the recorded version for its stream and skips the write when none remain, so a live update and a backfill page never fold one event twice, and the live path never meets a non-active generation of a history view, because its generation in flight exists only while its source scopes are closed and `rollbackGeneration` of `spec:application.rebuild` refuses to reopen a retired one (E-9, D9, F1)
- [extension] A history projection is bound once per source stream type on the command declaration; the pipeline's step 9 feeds it, once per command, the events of every `streams` entry its bindings match, and the backfill feeds it each source's history, so a history row has one projection and several bindings; a `Projection` or an `AggregateProjection` takes one entry's DTO, so a read model of those forms derives each row from one source stream (E-9, E-7, D8)

## Design

The shapes are TypeScript in the parent. `EventEnvelope` is the envelope `spec:context.event-envelope` pins, which the adapter's `streams` entry carries on the live path and the context's `history` query on the backfill. `ApplyMode`, `ApplyResult`, `WritableGeneration`, `projectionOf`, `rowConventions` and the `by_key` index are those of `spec:application.projection-contract`, which this form shares with the per-entity form, and `MutationCtx` is Convex's mutation context. The example domain's rules read `HistoryEvent`, the part of `EventEnvelope` they need, and live in `example/domain/orderAllocationHistory.ts`.

- typeHistoryProjection: `interface HistoryProjection<Row> { name: string; version: number; table: string; rowBudgetBytes?: number; keyOf(tenantId: string, event: EventEnvelope): string | null; project(tenantId: string, prior: Row | null, events: EventEnvelope[]): Row }` where `EventEnvelope` is the envelope of `spec:context.event-envelope`, `null` from `keyOf` means the event is not this view's, `prior` is `null` before the key's first event, `events` are the events of one key not yet folded into `prior`, each stream's in version order and the streams interleaved in any order, `project` answers a row and never `null`, and `rowBudgetBytes` is 16 KiB when absent; a history row is a bounded summary of history, never a list that grows with it, so `rowBudgetBytes` binds it like any row (E-9, D8, D9, F13)
- fnApplyHistoryProjection: `applyHistoryProjection<Row>(ctx: MutationCtx, projection: HistoryProjection<Row>, input: { tenantId: string; events: EventEnvelope[]; mode: ApplyMode; generations: readonly WritableGeneration[] }): Promise<{ key: string; results: ApplyResult[] }[]>` dropping the events of type `baseline`, grouping the rest by `keyOf` in the order given and leaving out those whose key is `null`, and per key and generation reading the row by `by_key`, dropping every event whose `streamVersion` is not above the row's recorded version for the event's stream, named by the envelope's `tenantId`, `contextId`, `streamType` and `streamId`, answering `skipped-newer` when none remain, and otherwise writing `project(tenantId, prior, remaining)` with `sourceVersions` raised to the highest version folded per stream and sorted by `contextId`, then `streamType`, then `streamId`, strings compared by UTF-16 code units, so the row is one value whatever the order the streams arrived in, and answering `inserted` or `updated`, never `deleted`, in the same mutation; `mode` is read by nothing, and a generation given whose `projectionVersion` is not the projection's `version` makes it throw the plain `Error` of `projectionOf` before it reads a row, a technical failure (E-9, D8, D9, F1, Law 6)
- tableOrderAllocationHistory: `orderAllocationHistory: defineTable({ ...rowConventions, orderId: v.string(), placedAt: v.optional(v.number()), cancelledAt: v.optional(v.number()), allocations: v.array(v.object({ stockItemId: v.string(), quantity: v.number(), allocatedAt: v.number(), releasedAt: v.optional(v.number()) })) }).index("by_key", ["tenantId", "generation", "key"])` the history-dependent cross-stream view of the example domain, the `HistoryProjection` named `orderAllocationHistory` over the table of that name, keyed by order ID and folded from `OrderPlaced` and `OrderCancelled` in Orders and `StockAllocated` and `AllocationReleased` in Inventory, with one entry of `allocations` per stock item the order allocated on and `sourceVersions` holding the order stream and every stock stream folded, so a row holds at most 100 entries and 101 versions; `getConvexSize` measures the largest such row, at 256-byte tenant and order IDs and 100 stock item IDs of 64 bytes, every allocation released, at 55,803 bytes, so the view declares `rowBudgetBytes` 65,536, the ceiling; it is bound once per source stream type, rebuilds only under the write pause, and Sc L2-6 builds it (E-9, E-46, D9, F13, Sc L2-6)
- typeOrderAllocationHistoryFields: `type OrderAllocationHistoryFields = { orderId: string; placedAt?: number; cancelledAt?: number; allocations: OrderAllocation[] }` where `type OrderAllocation = { stockItemId: string; quantity: number; allocatedAt: number; releasedAt?: number }`, the projected fields of the order allocation history, in `example/domain/orderAllocationHistory.ts` (E-9, E-46, Sc L2-6)
- fnOrderAllocationHistoryKeyOf: `orderAllocationHistoryKeyOf(tenantId: string, event: HistoryEvent): string | null` in `example/domain/orderAllocationHistory.ts`, answering the stream ID of an `OrderPlaced` or an `OrderCancelled`, the payload's `orderId` of a `StockAllocated` or an `AllocationReleased`, and `null` for every other event, where `type HistoryEvent = { streamId: string; eventType: string; recordedAt: number; occurredAt?: number; payload: unknown }` is the part of `EventEnvelope` the rules read, so the example's pure domain code imports no context library (E-9, E-46, Sc L2-6)
- fnProjectOrderAllocationHistory: `projectOrderAllocationHistory(tenantId: string, prior: OrderAllocationHistoryFields | null, events: readonly HistoryEvent[]): OrderAllocationHistoryFields` in the same file, folding the events one by one into `prior`, or, when `prior` is `null`, into `{ orderId, allocations: [] }` with the key of the first event that has one, and throwing the plain `Error` `"The order allocation history needs a prior row or an event of an order"` when there is neither; the view's `HistoryProjection` holds this function and `orderAllocationHistoryKeyOf` as its `project` and `keyOf` (E-9, E-46, Sc L2-6)
- orderAllocationHistoryFold: each field is written by the events of one stream, each event's time being its `occurredAt`, or its `recordedAt` when absent: `OrderPlaced` sets `placedAt` and `OrderCancelled` sets `cancelledAt`; `StockAllocated` on a stock item sets that stock item's entry of `allocations` to the payload's `quantity` and the time as `allocatedAt`, with no `releasedAt`; `AllocationReleased` sets `releasedAt` on that entry and changes nothing when the order has none on that stock item; every other event changes nothing; `allocations` is kept sorted by stock item ID, compared by UTF-16 code units; so the fold gives one row whatever the order across streams, a stock event before `OrderPlaced` included, and a pure test folds one order's events in every interleaving of its three streams and every split into calls and finds one row (E-9, D2, Sc L2-6)
- limitHistoryFold: on the live path step 9 calls `applyHistoryProjection` once per history read model per command, so it reads and writes at most one row per distinct key among the command's events in each generation, each at most `rowBudgetBytes`, and a `PlaceOrder` of 100 lines, whose 101 `streams` entries key to one order, reads and writes the order allocation history's one row once; on the backfill it takes one `history` page of at most the progress row's `batchSize` events, as the rebuild's `limitHistoryBatch` bounds it, so one batch reads at most that many events plus as many rows (F13, E-9, E-40)

## Verification — reviewed

- A reviewer confirms that every `HistoryProjection` is rebuilt with `pauseRequired` on its generations, that `applyHistoryProjection` drops baselines before `keyOf` and already-folded events by the row's `sourceVersions` before it calls `project`, that no history projection's `project` answers `null`, and that the L2-6 examples assert the fold against the journal.
