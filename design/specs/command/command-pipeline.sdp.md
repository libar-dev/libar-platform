# The command pipeline

Layer 1 · Detail: full · Traces: D1, D4, D6, D7, D8, D10, D11, D12, D13, Law 1, Law 2, Law 4, Law 5, Law 6, Law 9, Law 11, F1, F2, F3, F11, F13, Sc L1-2, E-8, E-30, E-31, E-32, E-33, E-38, E-54.

The command pipeline is the one top-level mutation every command and every use case runs through in the parent deployment. It owns the order of the steps between a caller's request and the committed outcome: parse against the canonical schema, authenticate, establish the tenant scope, authorize, look up the receipt, admit new intent, execute the contexts as sub-transactions, update the essential read models, insert the receipt, and return the outcome with the operation ID and the affected stream versions. Its boundary is the mutation: everything inside commits or rolls back together, and the only failure signal inside it is a throw. The pipeline writes receipts and parent read models; it never writes a context's tables, which only the context's own sanctioned operations touch.

The pipeline is one code path with two registered entries per command. The public entry is the `mutation` a Convex client calls; it reads `ctx.auth`, assigns the `public` namespace and relies on the client's own retry unless the caller supplies a request key. The internal entry is the `internalMutation` that HTTP actions, actions, workers, workflow steps and agents call from server code; it takes a server-established actor and namespace as arguments and requires a request key, because those callers sit outside the client guarantee. Both entries are produced from the same declaration by the composition helper in `spec:command.command-declaration`. A use case that calls two contexts runs through the same pipeline with one receipt and one outcome; how the parent composes the context calls is Package D's `parent-use-cases`.

## Intent

- actor: A caller that submits a command to the parent: a Convex client on behalf of a human, an HTTP action or webhook, a worker, a workflow step or an agent; and the platform maintainer who owns the one mutation every command runs through (D1, D6)
- problem: A failure injected after the state write, after the journal append or before the receipt must leave nothing of the command behind; if the steps ran in separate transactions, or if the parent caught a component's throw and continued, a partial command would commit and a later retry would run against half an outcome (Sc L1-2, Law 2)
- outcome: Every command runs as one top-level mutation whose steps run in a fixed order, and a failure at any step is a throw that rolls back the whole mutation, component sub-transactions included (D1, D7, F2)
- value: Correctness of a command needs no saga, outbox, command bus or lock protocol; the transaction is the unit of failure, and a new command adds a declaration, not infrastructure (D1, Thesis)
- risk: One mutation carries every step, so its cost is one grants read, one receipt read, one gate read, one registry read per maintained read model, one component sub-transaction per context, the read-model writes, one receipt insert, one audit record where the declaration asks for it and one diagnostic line, all under the 1-second mutation timeout and the per-transaction limits (D1, D19, F13, E-8, E-43)
- risk: Every read of context data from the parent is a component call whose cost Probe 3 measures; if it breaks the budgets, the shape of the context call changes, not the order of the steps (D2, Probe 3, OQ1)
- assumption: Mutations are serializable under optimistic concurrency, and component calls commit or roll back with the calling mutation (F1, F2)
- assumption: `ctx.runMutation` inside a mutation gives partial rollback and the parent can catch and continue; the pipeline relies on it only by never catching on the public path (F3)
- assumption: A `ConvexError` thrown inside a context operation reaches the pipeline's outermost catch with its `data` intact, which `rejectionRelay` rests on; this is F14, which Probe 2 showed on the pinned backend (F14, Probe 2)

### Open questions

- [non-blocking] Extension E-30: the doc names the outcome, the operation ID and the affected stream versions as what a command returns, but not a wire shape; the shape here is a union discriminated by `replayed`, whose executed member carries the declaration's result and whose replayed member carries `result` null because a receipt stores no result, so the entry's returns validator admits a replay as a value; affected IDs are application IDs, never private document IDs (E-30, D2, D6, D8)
- [non-blocking] Extension E-31: the doc says an operation's ID ties together everything one request caused but not how it is minted, and it says a derived command carries causation and an event's `causedBy` may be a triggering event without saying how that cause reaches the pipeline; here the pipeline mints the operation ID once per top-level mutation with `crypto.randomUUID()` before the first context call, a duplicate returns the operation ID stored on the receipt, and the internal entry takes an optional `causedBy` argument that step 7 copies onto the `OperationRef` when present, so a reaction that issues a derived command passes `causedBy` of kind `event` naming its publication event and the envelope's `event` variant has exactly one producer, while an entry called without it mints `causedBy` of kind `command` from the declaration's name; the obligation and attempt behind a derived command are found through its receipt, whose request key is the obligation's effect key, and never through the envelope (E-31, E-54, D2, D13, Vocab: operation)
- [non-blocking] Extension E-32: the doc places rate admission for new intent after the duplicate check and makes a rate or capacity refusal a retryable error, but names no admission mechanism; here admission is an optional per-command policy in the declaration, absent by default, evaluated inside the mutation so that a refusal that throws leaves no consumption behind; the flip side is that a consumption the policy writes commits only with the command, so the policy counts committed intent and cannot bound refused or unauthorized traffic, and a product that must bound refused traffic needs the dispatcher form of D7, where the parent survives the body's rejection (E-32, D4, D6, D7)
- [non-blocking] Extension E-33: the doc lists the callers that need receipts and leaves UI commands to the client guarantee; here a public caller may still supply a request key to opt into a receipt, which Probe 1 showed a caller of `ConvexHttpClient` needs when it retries, and the internal entry always requires one (E-33, D6, Probe 1)
- [non-blocking] Probe 4 showed on the pinned backend that the transaction limits are one budget across the parent and its component sub-transactions, so the per-command bounds are checked against one budget; `ctx.runMutation` accepts a `transactionLimits` option, the design passes none on a context call, and whether a call should reserve room with it for the work after it stays open (Probe 4, F13, S3)
- [non-blocking] Extension E-9: the doc says essential read models are updated inside the command and does not say from what or in what order; here step 9 writes a per-entity read model from the DTO of each matching `streams` entry, never from the events, checks `writes` first, then that each bound read model has a generation to write, then the count of the rows it writes against `limitReadModelWritesPerCommand`, each failure a plain error, and the library helpers that step 9 calls are generic over the application's data model; the owner has not ruled on any of it (E-9, E-7, E-8, E-45, D8, D9)
- [non-blocking] Extension E-34: step 1 bounds every text field a caller sets beside the input, the tenant ID, the request key, the correlation ID, the actor's fields and the fields of `causedBy`, in UTF-8 bytes as `limitCallText` lists them, as rejection `invalidInput`, and treats a declaration name above `limitIdLength` as a defect, a plain error, because these fields become fields of the receipt row or of every event's envelope; the doc says events stay small and names no number; the owner has not ruled (E-34, D6, D12, D19)

## Workflow

- rule: A business operation runs as one top-level mutation; the steps below never split across transactions (D1)
- rule: Failure handling inside the mutation is a throw; the pipeline never catches to continue, its one catch at the handler's outermost level only rethrows in the boundary's wire shape, and it never converts a technical failure into a rejection (D1, D7, Law 6)
- rule: Authorization precedes execution and precedes the disclosure of any stored outcome (Law 5, D11)
- rule: The receipt lookup precedes admission, so a valid retry is never refused for capacity (D6, Sc L1-9)
- rule: Only the parent reads `ctx.auth`; every context receives the server-established actor and tenant scope as arguments (D11, F11)
- rule: Every command names its tenant in its arguments; an absent tenant fails the argument validator and is never a wildcard (Law 11, D11)
- rule: The public entry assigns the `public` namespace; the internal entry takes a namespace from trusted server code only, so a client cannot claim a worker, agent or system namespace (D6, D11, Sc L1-7)
- rule: The pipeline writes receipts and parent read models and never a context's tables; business writes go only through the context's sanctioned operations (Law 1, D2)
- rule: Read models updated in the pipeline are essential read models written from state that the same transaction committed; no invariant is checked against them (D8, Law 9)
- rule: The mutation returns the outcome, the operation ID and the affected stream versions, so a client can compare what it reads against what it wrote (D4, D8, D2)
- rule: [extension] Admission counts committed intent only: a consumption the policy writes rolls back with any later throw of the mutation, a rejection included, and an unauthorized call never reaches admission because step 4 precedes step 6; a policy that must bound refused traffic runs under the conditional dispatcher of `spec:command.outcome-boundary`, where the body is the nested mutation and the parent survives its rejection, never through a nested write inside this pipeline, whose writes commit only with the parent (E-32, D7, F3, Law 5)
- Step 1, parse: the entry's `args` validators run before the handler and refuse a request that does not fit the command's one canonical schema; after the public entry's step 2, which authenticates before the checks that follow, the handler checks every text field the caller set beside the input against its bound in UTF-8 bytes, in the order `limitCallText` lists them, throwing rejection `invalidInput` with `details` `{ field, length, limit }` for the first that is longer than its bound, then checks the declaration's name against `limitIdLength`, throwing a plain error for a name longer than it, because these fields become fields of the receipt row or of every event's envelope, then checks the declaration's `bounds`, throwing rejection `operationTooLarge` with the bound and the offered size when the input's items, the elements of its top-level arrays, exceed `bounds.maxItems` or its size measured with `getConvexSize` exceeds `bounds.maxBytes`, and runs the declaration's refinement over the validated input and, when it returns a value, throws rejection `invalidInput` carrying that value's `message` and `details` through `reject` of `spec:command.outcome-boundary` with the declaration's name as `commandType`, all before any read, so no executor body checks an input bound of its own (D12, D4, D10, E-34, E-38)
- Step 2, authenticate: the public entry calls `establishActor` of `spec:command.actor-and-scope`, which reads `ctx.auth.getUserIdentity()` once, after Convex's argument validators and before step 1's key, bound and refinement checks, and throws rejection `unauthenticated` on `null`; the internal entry accepts the `actor` argument its trusted caller established and performs no authentication of its own (D11, F11)
- Step 3, establish scope: the `tenantId` argument is the tenant scope for every read and write that follows; the pipeline resolves the actor's membership in that tenant through the grants read of step 4 and never infers a tenant from the identity (Law 11, D11)
- Step 4, authorize: the pipeline reads the actor's grants for the tenant inside the transaction and evaluates the declaration's permission policy against actor, tenant scope and input; a denial throws rejection `forbidden` with `details` `{ reason }`, the reason `authorize` gave, before any execution and before any receipt is read (Law 5, D11, D12)
- Step 5, receipt lookup: for a receipted call the pipeline builds the key from tenant, namespace, command type and request key and reads the `receipts` table by its key index in the same transaction; no receipt means new intent, a receipt whose `contractVersion` differs from the declaration's throws rejection `unsupportedContractVersion` before any fingerprint is compared, a receipt with the same fingerprint means a duplicate and the pipeline returns the stored thin outcome with `replayed` true and `result` null, a receipt with a different fingerprint throws rejection `idempotencyConflict`, and neither rejection carries details or anything else of the stored receipt (D6, Law 4, Law 5, Sc L1-3, Sc L1-5, E-5)
- Step 5, disclosure: a duplicate's stored outcome is returned only because step 4 ran for this call, so a caller whose authorization was revoked after the original run receives `forbidden` and learns nothing (D6, Law 5, Sc L1-8)
- Step 6, admit: for new intent only, the pipeline evaluates the declaration's admission policy; a refusal throws transient `rateLimited` or `capacity`, nothing is stored, and the same intent may be retried (D6, D4, Sc L1-9)
- Step 7, gate and mint the operation: the pipeline reads the maintenance gate once through `assertWritable(ctx, scopesOfUseCase(tenantId, (decl.readModels ?? []).map((r) => r.readModel.name), decl.writes))` of `spec:application.write-pause`, which refuses with the transient `writePaused` while a scope of this command is closed, the tenant, a read model it maintains or a stream type it writes, or the deployment is in restore, then mints the whole `OperationRef`, the operation ID, `causedBy` from the call's `causedBy` argument when the internal entry received one and otherwise of kind `command` with the declaration's name, and the caller's optional correlation ID, and passes it to every context call so that events in different streams relate through it (Vocab: operation, D2, D9, D13, E-8, E-26, E-31)
- Step 8, execute: the executor captures the outside facts the decision needs, from parent tables or configuration read in this transaction, and calls each context named by the declaration once through `ctx.runMutation` on the component's sanctioned operation, `components.<context>.operations.<name>`, with tenant scope, actor, the operation reference, the command's input as lists and the captured facts; each call is an isolated sub-transaction that commits with the parent and rolls back on throw; a rejection thrown inside a context rolls its sub-transaction back and propagates to the boundary's outermost rethrow, and the executor returns the kernel's `CommittedOutcome<R>` together with the `streams` entries every context call returned, never a rejection value (F2, F3, D3, D10, D7, E-23)
- Step 9, update read models: the pipeline first checks that every `streams` entry the executor returned names a context and stream type in the declaration's `writes`, throwing a plain error, a defect and a technical failure, when one does not, so the list the gate of step 7 was derived from is proven on the first native run; then, for every binding, it reads the generations to write through `generationsToWrite`, throws a plain error that names the command and the read model when there is none, and calls `applyProjection` of `spec:application.projection-contract` for each matching entry with the entry's DTO and version and the list unchanged, in the live-created mode when the entry's `created` flag is set and the live-updated mode otherwise, or `applyAggregate` or `applyHistoryProjection` for a binding of those forms, in the same transaction; it counts the rows those calls insert, replace or delete, a row in each generation once, and after each entry is applied throws a plain error when they pass `limitReadModelWritesPerCommand`; the executor writes no read-model table itself (D8, D9, D12, Law 9, E-7, E-8, E-9, E-23, E-45)
- Step 10, insert the receipt and the audit record: for a receipted call the pipeline inserts the thin receipt, outcome kind, operation ID, affected IDs derived from the stream versions, and the stream versions, in the same transaction as the lookup of step 5, so two concurrent identical requests serialize under optimistic concurrency and only one effect commits; for a declaration that sets `audit` it then calls `writeAudit` of `spec:operations.baseline-operations`, whose failure throws and rolls the command back (D6, D19, F1, Sc L1-3, E-43)
- Step 11, return: the mutation emits one diagnostic record through `emitDiagnostic` inside a try and catch that swallows every error, then returns the outcome kind, the result DTO, the operation ID, the affected IDs, the stream versions and `replayed` false (D4, D8, D2, D19, E-43)
- At any step, a throw leaves the mutation uncommitted: the state and journal writes of every context sub-transaction, the read-model writes and the receipt are all rolled back, and nothing is stored as a business outcome (Law 2, D7, F2, Sc L1-2)

## Design

The transaction boundary is the top-level mutation. Inside it, the parent's own code runs as plain helpers with no nested `ctx.runMutation`, because a helper's writes roll back with the mutation and a nested call costs more than a helper. The only sub-transactions are the component calls of step 8, one per context, because a component can only be reached through `ctx.runMutation` or `ctx.runQuery` and each such call is isolated from the others and commits with the caller. The pipeline never catches a component's throw to continue; its outermost `normalizeThrown` only rethrows, so that a context's bare kernel `Rejection` and the pipeline's own rejections share one wire shape, and a context's code that is neither a platform code nor in the declaration's `rejections` becomes a technical failure. The nested-mutation form that D7 keeps for a worker wrapper or a refusal record lives in the obligation module and in the conditional dispatcher of `spec:command.outcome-boundary`, not here.

The pipeline depends on three contracts it does not own: the context component's operation mutations, one per sanctioned operation, and their returned DTO, versions and `streams`, the receipt table and its key index, and the actor, scope and grants shapes. It cites Package B's operations at the point the step sequence calls them and states nothing about the adapter's inner steps. Four steps call helpers that Layer 2 Specs pin, the gate of step 7, the projections and the generation registry of step 9, and the audit and diagnostic of steps 10 and 11; each is a no-op in a deployment that has no read model, no closed gate and no audited declaration, so a Layer 1 application runs the pipeline before Layer 2 exists, and the graph edges run from those Specs toward this one, never the reverse.

- transactionBoundary: one top-level mutation per command; each context call is a component sub-transaction through `ctx.runMutation`; no nested `runMutation` on the parent's own code on the happy path (D1, F2, F3)
- convexSurface: per command, one public `mutation` export for Convex clients and one `internalMutation` export for server-side callers, both from the composition helper; the parent registers no other function per command, and the conditional dispatcher of `spec:command.outcome-boundary` runs the internal entry as its nested body rather than a body of its own (D12, D6, D7)
- fnPublicEntry: `export const placeOrder = mutation({ args: { tenantId: v.string(), requestKey: v.optional(v.string()), correlationId: v.optional(v.string()), input: placeOrderInputValidator }, returns: commandResponseValidator(placeOrderDeclaration.output), handler })` (D12, Law 11, E-33, E-30, E-31)
- fnInternalEntry: `export const placeOrderInternal = internalMutation({ args: { tenantId: v.string(), namespace: callerNamespaceValidator, actor: actorValidator, requestKey: v.string(), correlationId: v.optional(v.string()), causedBy: v.optional(causedByValidator), input: placeOrderInputValidator }, returns: commandResponseValidator(placeOrderDeclaration.output), handler })` where `causedByValidator` is the envelope's from `spec:context.event-envelope` (D6, D11, D13, E-33, E-30, E-31)
- fnRunPipeline: `runPipeline<I, R>(ctx: MutationCtx, decl: CommandDeclaration<I, R>, call: PipelineCall<I>): Promise<CommandResponse<R>>` runs steps 1 to 11 for either entry (D1, D12)
- typePipelineCall: `type PipelineCall<I> = { tenantId: string; namespace: CallerNamespace; actor: Actor; requestKey?: string; correlationId?: string; causedBy?: CausedBy; input: I }` where the public entry fills `namespace` with `"public"` and `actor` from step 2 and never sets `causedBy`, `correlationId` is diagnostic grouping the caller may supply and the fingerprint excludes, and `causedBy` is the cause a trusted caller of the internal entry states, which the fingerprint also excludes because a retried reaction carries the same request key with the same cause (D11, D2, D13, E-33, E-31, E-36)
- typeCommandResponse: `type CommandResponse<R> = { kind: "applied" | "businessFailure"; operationId: string; affected: AffectedRef[]; versions: StreamVersion[] } & ({ replayed: false; result: R } | { replayed: true; result: null })`, a union discriminated by `replayed` so that `result` is null exactly when the answer is a replay, where `StreamVersion` is the kernel's `{ tenantId, contextId, streamType, streamId, version }` from `spec:kernel.outcome-model`, never redefined here (D4, D8, D2, D6, E-30)
- typeAffectedRef: the kernel's `AffectedRef`, `{ contextId, streamType, streamId }` from `spec:kernel.outcome-model`, an application ID and never a private document ID; reused here, never redefined (D2, E-21, E-30)
- affectedDerivation: `affected = versions.map(({ contextId, streamType, streamId }) => ({ contextId, streamType, streamId }))` computed once after step 8 from the versions the executor returned, for every call, receipted or not, and stored on the receipt and the response, so the affected list has one source and no step invents it (D6, D2, E-21, E-30)
- validatorCommandResponse: `const commandResponseValidator = <R>(output: Validator<R, "required", string>) => v.union(v.object({ kind: outcomeKindValidator, result: output, operationId: v.string(), affected: v.array(affectedRefValidator), versions: v.array(streamVersionValidator), replayed: v.literal(false) }), v.object({ kind: outcomeKindValidator, result: v.null(), operationId: v.string(), affected: v.array(affectedRefValidator), versions: v.array(streamVersionValidator), replayed: v.literal(true) }))` where `outcomeKindValidator = v.union(v.literal("applied"), v.literal("businessFailure"))`, the composition helper passes the declaration's `output`, and `streamVersionValidator` is the kernel's; Convex validates the return value and would throw on a replay if the executed member alone were declared, which is why the replayed member is part of the closed type (D4, D12, D6, E-30)
- operationRef: `operation = { operationId: crypto.randomUUID(), causedBy: call.causedBy ?? { kind: "command", commandType: decl.name }, ...(call.correlationId === undefined ? {} : { correlationId: call.correlationId }) }` minted once per top-level mutation at step 7, before the first context call, passed to the executor and by it to every context call unchanged, stored on every event and its ID on the receipt; a duplicate returns the receipt's `operationId`; a reaction passes `causedBy: { kind: "event", tenantId, contextId, eventId }` naming its obligation's source event, as `spec:obligations.fan-out-and-chains` pins, and that is the one producer of the envelope's `event` variant (Vocab: operation, D2, D13, E-26, E-31, E-54)
- ctxAuthUse: `ctx.auth.getUserIdentity()` is called once, in the public entry at step 2, and its `tokenIdentifier`, `subject` and `issuer` become the actor's identity; no component function reads `ctx.auth`, by this design's rule (D11, F11)
- gateRead: `assertWritable` of `spec:application.write-pause` runs at step 7 with the scopes `scopesOfUseCase` derives from the tenant, the declaration's read models and the declaration's `writes`, the context and stream type pairs the executor may write, one point read per command after the environment's restore door; a refusal is the transient `writePaused` and nothing is stored (D9, D4, E-8, E-35, E-38, E-42)
- factsCapture: the executor is the one place that captures outside facts, such as an accepted price list, a currency or a policy version, from parent tables or configuration inside this transaction, and passes them as `facts` on each context call; they reach the decider through its decision context, never through `input`, so the fingerprint of step 5 excludes them (D3, E-22, E-36)
- contextCall: `await ctx.runMutation(components.inventory.operations.allocate, { tenantId, actor, operation, input: { orderId, lines }, facts })`, one call per context named by the declaration, lists in and the operation outcome out, the DTO with the versions and one `streams` entry per planned stream with its DTO, version, created flag and the events the call appended; the `args` shape is the one `spec:context.context-component` fixes, `operation` is the `OperationRef` of `spec:context.event-envelope` minted at step 7, and the return is the `OperationOutcome` of `spec:context.persistence-adapter` (D10, F2, E-22, E-23, E-26)
- contextCallIsolation: each component call is a sub-transaction isolated from the other calls; a throw inside it rolls that sub-transaction back, and uncaught it rolls the parent back, so the parent never observes a half-applied context (F2, F3, S2)
- rejectionRelay: a `ConvexError` carrying the kernel's `Rejection` thrown inside a component reaches the pipeline with its data intact under F14, which Probe 2 showed on the pinned backend; `normalizeThrown(error, decl.name, decl.rejections)` at the handler's outermost level rethrows it as the boundary's `RejectionData` when its code is a platform code or one the declaration's `rejections` names, and as a plain error otherwise; the fallback for a refuted F14, contexts returning the rejection as a value, is not needed (F14, Probe 2, D7)
- readModelWrites: parent-owned read-model tables written by the pipeline at step 9, one `applyProjection`, `applyAggregate` or `applyHistoryProjection` call per matching `streams` entry per binding the declaration lists, with the list `generationsToWrite` returns, each generation with its role; the executor holds the DTOs and the appended events only long enough to return them and writes no read-model table, so the declaration's list is the one wiring fact for read models (D8, D9, D12, E-7, E-9)
- writesCheck: `decl.writes` is proven at step 9 against the `streams` entries the executor returned, in memory and with no extra read; an entry outside the list throws a plain error, so a declaration whose `writes` understates its executor fails its first native run rather than passing a closed source scope at step 7 (E-8, E-38, Law 6)
- fnWriteReadModels: `writeReadModels<DataModel extends ReadModelDataModel>(ctx: RegistryReader<DataModel> & RowWriter<DataModel>, commandType: string, bindings: readonly ReadModelBinding[], input: { tenantId: string; streams: readonly StreamDto[] }): Promise<number>`, the read-model half of step 9 and the one function of the read-model library the pipeline calls, returning the number of entries it fed; the pipeline passes its own ctx, which at run time is the parent's and holds the registry and the read model's table (D8, E-7, E-9)
- helperGenerics: [extension] every library helper that takes the parent's own ctx or reads one of the parent's tables, `writeReadModels`, `activeGeneration` and `authorizeQuery` among them, is generic over the parent's data model, because a database reader is not covariant in its data model under the repository's compiler settings, so a helper typed with the library's tables alone refuses the parent's ctx (E-7, E-9, D11)
- auditWrite: `writeAudit` of `spec:operations.baseline-operations` at step 10 for a declaration whose `audit` field is set, inside the transaction and after the receipt insert; its failure throws and the command rolls back (D19, E-43, Sc ALL-1)
- diagnosticEmit: `emitDiagnostic` of `spec:operations.baseline-operations` at step 11, after every business write and inside a try and catch that swallows every error, so no diagnostic failure reaches the mutation (D19, E-43, Sc ALL-1)
- receiptWrites: the `receipts` table of `spec:command.receipt-table`, read at step 5 by `by_key` and inserted at step 10 in the same mutation (D6)
- admissionHook: `admission?: (ctx: MutationCtx, call: PipelineCall<I>) => Promise<{ admitted: true } | { admitted: false; code: "rateLimited" | "capacity"; retryAfterMs?: number }>` on the declaration, absent by default; a refusal throws the transient error and any consumption it wrote rolls back with the throw, as it does with every later throw of the same mutation, so an admitted call that is then rejected leaves no consumption either (D6, D4, E-32)
- subTransactionLimits: `ctx.runMutation` accepts `{ transactionLimits }` per call; the limits are shared across the boundary, as Probe 4 showed; the design passes no `transactionLimits` on a context call, and whether a call should reserve room for the work after it is an open question (S3, Probe 4, F13)
- limitMutationTimeout: the whole pipeline runs under the 1-second query and mutation timeout; every per-command bound in a declaration is chosen so that one command's reads and writes finish well inside it (F13)
- limitTransaction: 16 MiB read, 16 MiB written, 32,000 documents scanned, 4,096 index ranges read, 16,000 documents written per transaction; the per-command `bounds` in the declaration, such as the maximum order lines, are ceilings chosen against these, and the largest order is a product decision (F13, D10, OQ3)
- limitContextCalls: one `ctx.runMutation` per context named by the declaration per command; O(N) business work inside a call is fine, O(N) calls is not (D10)
- limitTooLarge: an input that exceeds the declaration's `bounds`, `maxItems` items or `maxBytes` bytes measured with `getConvexSize`, throws rejection `operationTooLarge` at step 1, the one checkpoint for the input bound in the corpus; a context's adapter keeps its own `maxStreams` and byte bound and the smaller bites first; the pipeline never splits an input, because splitting silently changes the contract (D10, D4, E-38)
- fnUtf8Length: `utf8Length(value: string): number` returns the number of bytes in the UTF-8 encoding of the string, which equals `getConvexSize(value) - 2`; every text bound of step 1 and of the persistence adapter's step 1 is measured with it, and the command library and the context library both export it (F13, E-34)
- limitCallText: the text fields a caller sets beside the input and their bounds in UTF-8 bytes, in the order step 1 checks them, each written as the path that `field` carries in the rejection's `details`: `tenantId` 256, `requestKey` 256, `correlationId` 256, `actor.id` 512, `actor.issuer` 256, `actor.onBehalfOf.id` 512, `actor.delegationRef` 256, `causedBy.commandType` 256, `causedBy.tenantId` 256, `causedBy.contextId` 256, `causedBy.eventId` 256, `causedBy.migrationName` 256; an absent field is not checked, a field exactly at its bound passes, and a field one byte longer is rejection `invalidInput` with `details` `{ field, length, limit }`, `length` being the field's UTF-8 byte count and `limit` its bound; the check runs in `runPipeline` for both entries, so the public entry's actor is the one step 2 established and an identity whose `tokenIdentifier` is longer than 512 bytes is rejected with `field` equal to `"actor.id"`; 256 is the exported `limitIdLength` and 512 the exported `limitActorIdLength`; these bounds and the stream ID's are what `limitEnvelopeBytes` of `spec:context.event-envelope` is derived from (D2, D11, D19, F13, E-34, E-12)
- errorPath: every throw at any step leaves the mutation uncommitted; the four outcomes and the error data are mapped at `spec:command.outcome-boundary` (D4, D7)
- injectionPointOrder: the three injection points of Sc L1-2 keep the doc's order, after the state write, after the journal append, before the receipt insert, and the examples number them in that order; the adapter appends the events at its step 8 before it saves the state at its step 9, so the ordinals are not the order of execution (Sc L1-2)
