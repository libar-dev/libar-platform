# The native harness

Feature · Detail: extension · Traces: Acceptance scenarios (tiers, evidence), S13, Sc L2-9, D11, E-13, E-15, E-59.

The doc says that native tests prove component and nested-mutation behavior, scheduling, contention and deployment, that the kernel's fixture app is separate from the example app, that test-only functions never ship and that every test owns its disposable backend. It does not say how a test obtains an identity, what the fixture app contains, how a fault enters a run, what a test may read or what it controls. This Spec carries those rules as two extensions, E-13 and E-15, and a third, E-59, for a native run on a hosted deployment. Every rule here is the corpus's provisional reading until the owner rules, except the local reading of Sc L2-9 in the first rule, which is settled. The doc's own rules on tiers and evidence stay in `spec:platform.acceptance-contract`.

## Intent

- outcome: A native test runs on a backend it owns, as an ordinary caller, on a named composition, and asserts only what a client or the harness's admin access can read (Acceptance scenarios)
- value: Every native test of the platform runs on this harness, so a harness that is more privileged or more lenient than production lowers the worth of every native pass (Sc L2-9)
- risk: One backend per test costs a process start, a deploy and a teardown per test, and a harness that leaks a process or a port fails tests that did nothing wrong (Acceptance scenarios)
- assumption: Native tests run against a local Convex backend as S13 describes; the testing guide S13 links obtains a test's identity through the backend's admin key acting as that identity, which this harness does not use for a caller under test (S13, E-13)

### Open questions

- [non-blocking] Extension E-13: the doc says native acceptance runs with production authority and a disposable backend per test and does not say how a test obtains a signed identity, which a production issuer cannot mint for a throwaway backend; the option taken here is a fixture issuer: a composition that runs natively reads its issuer, application ID and key set from the deployment's environment variables, the harness sets the key set to a data URI whose private key it holds, and each caller under test is an ordinary client carrying a token the harness signs; the option first taken, the backend's admin key acting as an identity, was dropped because such a caller passes Convex's visibility check for internal functions, which `spec:platform.native-harness.admin-key-acting-as-identity-reaches-internal-function` shows; this reading reaches into production, because running the production composition natively with no changed file means the example application's `auth.config.ts` is a `customJwt` provider whose trust root is whatever the deployment's environment names, and a provider that fetches its keys from an issuer's own endpoint cannot be run on a disposable backend this way; the owner rules on both halves, the test identity and the production provider (E-13, S13, Sc L2-9, D11)
- [non-blocking] Extension E-15: the doc does not say what the fixture app contains, how a fault enters a run, what a test may observe, or what a test controls on a backend that offers no clock and no scheduler switch; the option taken here is the rules below; two of them read the doc for the owner: the production-configuration run of Sc L2-9 is taken as the scenarios routed to the production composition, where the corpus earlier asked for the full Layer 0 to 2 suite on a release build, and evidence records that back a pass claim are kept in the repository; whether the durations Layer 3 pins become configuration, so that a test can outwait them, is left to Layer 3; and because the Convex CLI reads `convex.json` and `package.json` from its working directory, a composition is a name, a project directory and a functions directory, the production composition's project directory is `example/` with a `package.json` that links to the repository's one, and both compositions' generated files are committed; the owner has not ruled on the layout (E-15, Acceptance scenarios, Sc L2-9)
- [non-blocking] Extension E-15: the design takes the fixture action `nonUiCaller:send`, which any authenticated client of the fixture composition may call to run any fixture command's internal entry under any namespace and actor kind, as the fixture's stand-in for trusted server code, kept out of the production composition; it is a provisional reading the owner rules, because within the fixture composition it lets a client do what `spec:command.tenancy-and-authority` refuses a client (E-15, D11, Sc L1-7)
- [non-blocking] Extension E-59: the doc's native tier is a test on a real backend, S13 names a local one, and Sc L2-9 is read as the local observation; the doc does not say whether a native test runs on a hosted deployment, where alone Probe 3 can read function-call quota and where F12 and F16 keep parts that only documentation states; the option taken here: the same harness, run record and compositions run natively on one hosted development deployment in a Convex team and project of their own, selected by process variables under a test configuration of its own, one run at a time, from a workflow whose failure fails no other check, with one development deploy key limited to the actions `deployKeyActions` lists; the alternatives were each developer's own deployment, which still needs one more key for the continuous integration, a preview deployment per run, which on the Free and Starter plans expires by default five days after it is created, before F16's seven-day window, and a fresh development deployment per run, which needs a project key, a credential the docs give total control over a project; the team, the project, the plan and the key are the owner's to provide (E-59, Sc L2-9, F4, F12, F16, Probe 3, Probe 7)

## Rule

- [extension] Sc L2-9 is read as the local observation: the production composition on the pinned local backend, with the same code path, schema, concurrency and authority model a release has, the authority model being the grants, namespaces, entry points and actor mapping, and Convex's own visibility check on every call a caller under test makes; no native pass claims parity with a hosted deployment (E-13, S13, Sc L2-9)
- [extension] A caller under test is an ordinary client that carries a token signed by the fixture issuer, or no token (E-13)
- [extension] A composition that runs natively reads its issuer, its application ID and its key set from the deployment's environment variables, and the harness sets the key set to a data URI that holds the fixture issuer's public key (E-13, S13)
- [extension] No caller under test carries the admin key, alone or acting as an identity, because a call made with it passes Convex's visibility check (E-13)
- [extension] The fixture issuer is the identity source of a native run and its one named difference from production; it is recorded as the identity source and is not an adjusted configuration (E-13, Sc L2-9)
- [extension] The harness uses the admin key to deploy, to generate code, to set and read environment variables, to read stored data and the function log, to run fixture functions, and to call a composition's internal functions that admin access reaches, its grant mutation and its operator entries (E-15, E-48)
- [extension] On the local backend, every Convex CLI call the harness makes names the backend it started on the command line and gets an environment of its own, so that no variable of the caller's shell and no dotenv file selects another deployment (E-15)
- [extension] No generated secret, the instance secret or the admin key, reaches an error message, test output or a record (E-15)
- [extension] A native run on a hosted deployment uses the same harness, run record and compositions as one on the local backend and names the hosted deployment as the backend it ran on; it claims no parity with a release under Sc L2-9, passes no scenario row, and shows only what the local backend cannot: the deploy key's authority, the deployment's acceptance of a composition, its reachability, its report of its own usage and what it keeps between runs (E-59, Sc L2-9)
- [extension] Only `npm run test:hosted` selects a hosted deployment, by the deployment URL and the deploy key in two process variables; no other variable, no dotenv file and no login selects it, `npm run test:all` cannot select it, and a run on the local backend reads neither variable (E-59)
- [extension] The harness refuses a native run on a hosted deployment whose deploy key does not begin `dev:`, whose deployment URL is not `https://`, the deployment name the key carries and `.convex.cloud`, with or without one region between the name and `.convex.cloud` as the CLI prints it (`https://<name>.<region>.convex.cloud`), or whose composition's project directory holds a `.env` or `.env.local` file, so a developer's own `.env.local` at the repository root refuses it; a refusal names the variable or the file and never a value (E-59)
- [extension] A native run on a hosted deployment starts no local backend: `fixtureBackend` and `productionBackend` refuse inside it (E-59)
- [extension] The deploy key enters the harness as one process variable and reaches a Convex CLI child only as `CONVEX_DEPLOY_KEY` in the environment the harness gives that child, never as an argument; the harness's HTTP and socket clients carry it in a header or an authentication message, never in a URL (E-59, E-15)
- [extension] No form of the deploy key, the whole key, its part after the `|` or either of them URL-encoded, reaches an error message, test output, a record or an artifact of the continuous integration; every member of the admin access to a hosted deployment and every CLI child replaces those forms in what it throws before it throws, where the response is first seen, and the record is redacted again as a whole before it is written (E-59, E-15)
- [extension] The hosted deployment keeps its data between runs, so the record of a native run on it states a kept dataset, `kept from earlier runs`, and an example on it asserts only on what its own run wrote or on what a table of the run's temporary copy says an earlier run planted (E-59)
- [extension] Native runs on the hosted deployment run one at a time, which the harness cannot enforce across machines, so the record names whether the continuous integration or a developer ran it; a failed native run on the hosted deployment fails no check of a commit's continuous integration (E-59)
- [extension] The record of a native run on a hosted deployment holds the deployment's usage readings before and after the run, with the time of each, and no example asserts a cost from them; a difference of two readings is the run's own only when no other run on the deployment overlapped it, and is unestablished when that cannot be shown; the plan it names is the stated plan, and the backend version is what the deployment reports or `null`, never mapped to a release (E-59)
- [extension] An assertion about authority, identity or visibility is made through an ordinary client (E-15, E-13)
- [extension] A native scenario runs on one of two compositions, the fixture composition or the production composition, and its example names which (E-15)
- [extension] The fixture composition mounts the shared libraries beside fixture contexts and fixture functions; the production composition is the example application with no test-only function registered (E-15, Acceptance scenarios)
- [extension] A scenario runs on the production composition unless it needs a fixture-only state or operation, a fault or a fixture function (E-15)
- [extension] The production-configuration run of Sc L2-9 is the scenarios routed to the production composition, deployed with no test-only function and no adjusted configuration (E-15, Sc L2-9)
- [extension] A scenario on the fixture composition is native evidence for its own row; it runs the shared libraries with their own tables and the same authority model, beside fixture contexts whose state is the fixture's own (E-15, First experiment)
- [extension] The shared libraries carry no test hook: they read no flag and take no callback that exists only for a test (E-15)
- [extension] A fault inside a function, a throw at a chosen point or a part that fails, enters a native run only through something the fixture composition supplies: a fixture context's declaration, a fixture read model, a fixture function, or a dependency the libraries take from every composition (E-15)
- [extension] A fault outside the functions, a killed backend, a closed client or a lost response, comes from the harness's controls (E-15)
- [extension] A native assertion reads only what a client or the harness's admin access can read: a returned value, the data of a thrown error, stored documents and the function log (E-15)
- [extension] A table read or a function log read that may be incomplete fails (E-15)
- [extension] What a command read and wrote, in documents and bytes, is taken from the `usageStats` of its top-level completion record, never from a function that exists for a test (E-15, First experiment)
- [extension] Where a scenario asserts that something did not run, the test shows the refusal's own error, shows that nothing the thing writes is stored, and shows on the same deployment that the thing exists and runs, through a control that an ordinary client sends where a client may call the thing and that is sent with admin access otherwise; where no error tells a refusal from a failure, the fixture composition supplies a part that fails the call if it runs (E-15)
- [extension] An error text, a count or a wait that an example of this harness binds is what the pinned backend release answers; another answer on a new release is a finding to rule on, and the example is rebound, not the test repaired to keep the old value (E-15)
- [extension] The native tier controls a run through four things: the backend process, its clients, the deployment's environment variables and, on the fixture composition, fixture functions (E-15)
- [extension] The harness starts a local backend on fresh storage, stops it, kills it, and restarts it on the same storage (E-15, S13)
- [extension] The harness registers the cleanup of a backend before the start of that backend can stall; a run that ends or is interrupted kills every backend process it started and removes every backend directory (E-15)
- [extension] Before the harness signals a process it reads from the process table the instance name and the storage path it gave that backend, and it signals no process that does not show both; a backend whose process it cannot inspect keeps its directory and its ownership record, and the run fails naming it (E-15)
- [extension] A client under test may close, and may lose a response (E-15)
- [extension] The native tier cannot move the backend's clock and cannot switch its scheduler off (E-15, S13)
- [extension] A scenario that needs time to pass waits in real time or shortens a duration that its owning Spec makes configuration, and a run with a shortened duration is adjusted configuration (E-15, Acceptance scenarios)
- [extension] A native run's record names a local backend that ran by the hash of its executable and, when that hash is the pinned one, by its release; it names the identity source, and the commit with whether the tree was clean (E-15, Acceptance scenarios)
- [extension] A run's record takes its facts from the backends that ran, and a measurement is stored on the test that recorded it (E-15, Acceptance scenarios)
- [extension] A claim that a tier passed cites the commit and the run of the continuous integration on it, whose record was made on a clean tree at that commit (E-15, Acceptance scenarios)

## Design

The harness is plain test support with no Convex function in it. The entries whose keys start with `fn` or `type` are the signatures native tests are built on; the code under `harness/` holds the rest. The entries whose keys start with `observed` are readings of the backend release the repository pins, `precompiled-2026-09-28-5c7cb5b`, with `convex` 1.46.0. They are not rules, and they are read again when the pin moves.

- backend: [extension] the disposable backend is the `convex-local-backend` binary of one pinned release, checked against a recorded hash; the harness starts it on local ports with fresh storage, a generated instance secret and the admin key the binary derives from it, sets the environment variables, runs the Convex CLI in the composition's project directory to deploy it, and at the end of the test stops the process and removes the storage (E-15, S13)
- identity: [extension] a caller is a `ConvexHttpClient` or a `ConvexClient` whose `setAuth` carries a token the harness signs; `auth.config.ts` declares one `customJwt` provider whose `issuer`, `applicationID` and `jwks` are environment variables; the token carries `iss`, `aud`, `sub`, `iat` and `exp` and no other claim, so `ctx.auth.getUserIdentity()` in a public entry returns the identity those claims yield, and `establishActor`, the grants read and the namespace rules run unchanged as long as they read nothing a provider adds beyond them (E-13, S13, D11)
- adminReads: [extension] the harness reads a table of the app or of a component, and the function log's completion records, with the admin key; a table read returns every document with every Convex value intact or fails, never a sample, and is several queries, not one snapshot; a log read returns every completion record after a point the test marks or fails, and a mark taken before a restart cannot be read after it; a completion record carries at least `identifier`, `componentPath`, `requestId`, `executionTime` in seconds, `cachedResult`, `error` and `logLines` as an array of strings (E-15)
- typeFixtureIssuer: [extension] `interface FixtureIssuer { issuer: string; applicationID: string; jwks: string; token(subject: string): Promise<string> }` (E-13)
- typeBackend: [extension] `interface Backend { url: string; adminKey: string; issuer: FixtureIssuer; admin: AdminAccess; stop(): Promise<void>; kill(): Promise<void>; restart(): Promise<void>; dispose(): Promise<void>; facts(): BackendFacts }`; `stop` and `kill` keep the storage; `dispose` alone removes it and is final, so a disposed backend cannot be started again; `adminKey` is there for the one example that shows why no caller carries it (E-15)
- typeAdminAccess: [extension] `interface AdminAccess { deploy(): Promise<void>; deployTemporary(directory: string, signal?: AbortSignal): Promise<{ command: string[]; stdout: string; stderr: string }>; codegen(): Promise<void>; setEnvironment(variables: Record<string, string>): Promise<void>; environment(): Promise<Record<string, string>>; run(name: string, args?: Record<string, Value>, options?: { component?: string }): Promise<Value>; readTable(table: string, options?: { component?: string; pageSize?: number }): Promise<Record<string, Value>[]>; writeTable(table: string, write: { insert: Record<string, Value> } | { patch: string; fields: Record<string, Value> } | { delete: string }, options?: { component?: string }): Promise<void>; logMark(): Promise<LogMark>; completionsSince(mark: LogMark, until: (records: readonly CompletionRecord[]) => boolean, timeoutMs?: number): Promise<CompletionRecord[]>; exportBackupArchive(path: string): Promise<void>; importBackupArchive(path: string): Promise<void> }` holds every use of the admin key and takes no identity; the two backup archive members run the Convex CLI's export of a backup archive and its import with replacement against this backend, and a test uses them and never the admin key itself; `deployTemporary` deploys a temporary copy, stops its deploy child when the caller's signal or the backend's own aborts, returns its redacted command and clears the plain composition claim (E-15)
- fnOrdinaryClient: [extension] `ordinaryClient(url: string, options?: { token?: string; fetch?: typeof fetch }): ConvexHttpClient` (E-13)
- fnOrdinarySocketClient: [extension] `ordinarySocketClient(url: string, options?: { token?: string; webSocket?: typeof WebSocket }): ConvexClient` (E-13)
- fnCountingFetch: [extension] `countingFetch(options: { loseResponses: boolean }): { fetch: typeof fetch; requests(): number }` delivers each request and, when it loses responses, throws after the backend has answered (E-15)
- fnHeldWebSocket: [extension] `heldWebSocket(): { WebSocket: typeof WebSocket; holdResponses(): void; pauseConnections(): void; release(): void }`; a socket that closes drops the responses it held (E-15)
- fnWatchQuery: [extension] `watchQuery<Query extends FunctionReference<"query">>(client: ConvexClient, query: Query, args: FunctionArgs<Query>): { values: readonly FunctionReturnType<Query>[]; error: Error | undefined; until(matches: (value: FunctionReturnType<Query>) => boolean, description: string, timeoutMs?: number): Promise<FunctionReturnType<Query>>; stop(): void }` (E-15)
- fnFixtureBackend: [extension] `fixtureBackend(options?: { issuer?: string; executable?: Executable; parentDirectory?: string; deploy?: boolean }): Promise<Backend>` starts a backend, deploys the fixture composition unless `deploy` is `false`, and removes the backend when the test finishes, however it finishes; the executable and parent directory options let the harness's own tests exercise the same cleanup path (E-15, E-13)
- fnProductionBackend: [extension] `productionBackend(options?: { issuer?: string; deploy?: boolean }): Promise<Backend>` starts a backend, deploys the production composition unless `deploy` is `false`, and removes the backend when the test finishes, however it finishes (E-15, E-13)
- fnMeasure: [extension] `measure(name: string, value: JsonValue): void` stores a measurement on the running test (E-15)
- typeBackendFacts: [extension] `interface BackendFacts { composition: "fixture" | "production" | null; installedLayers: string[]; target: "local backend" | "hosted deployment"; executable: { release: string | null; sha256: string; source: "cache" | "CONVEX_BACKEND_BINARY" } | null; identitySource: { kind: "fixture issuer"; issuer: string }; environment: string[]; dataset: "empty at start" | "kept from earlier runs" }` says `null` for the composition after `deployTemporary`, so a record never claims the plain composition for a backend running a copy; the test that deployed the copy records what it added as a measurement; on a hosted deployment `executable` is `null` and `dataset` is kept from earlier runs, and `environment` names the variables this run set, never a value (E-15, E-13, E-59)
- typeNativeTestEntry: [extension] `interface NativeTestEntry { project: "types" | "pure" | "simulator" | "native" | "hosted"; name: string; file: string; result: "passed" | "failed" | "skipped"; durationMs: number | null; errors: string[]; backends: BackendFacts[]; measurements: { name: string; value: JsonValue }[] }`; a run that includes the native project records every test it ran, of every project, each under the project that ran it, and `hosted` is the project of a test that ran on a hosted deployment (E-15, E-59)
- typeNativeRunRecord: [extension] `interface NativeRunRecord { tier: "native"; target: "local backend" | "hosted deployment"; commit: string; clean: boolean; command: string; startedAt: string; finishedAt: string; result: "passed" | "failed" | "interrupted"; versions: Record<string, string>; tests: NativeTestEntry[]; unhandledErrors: string[]; hosted: HostedRunFacts | null }`; it holds no field for adjusted configuration, and a run that adjusts configuration is the trigger that adds one; a record with no `target` reads as one of the local backend, and `target` is recorded apart from `tier`, because a hosted deployment is a target of the native backend tier and not a tier of its own (E-15, Acceptance scenarios, E-59)
- typeHostedRunFacts: [extension] `interface HostedRunFacts { deployment: string; keyName: string; statedPlan: string; ranBy: "continuous integration" | "developer"; cliVersion: string; backendVersion: string | null; usageBefore: HostedUsage | null; usageAfter: HostedUsage | null; windowCrossed: boolean; deploys: { composition: "fixture" | "production" | null; wallMs: number }[] }`; `deployment` is the name the key carries; `keyName` and `statedPlan` are what the owner states in two variables that hold no secret, `HOSTED_DEPLOY_KEY_NAME` and `HOSTED_PLAN`, because the deployment reports its team, project and type and no plan; `backendVersion` is the answer of `/instance_version` or `null`, and `executable` stays `null`, because no mapping from that answer to a release is established; `windowCrossed` is true when a UTC day boundary falls between the two readings (E-59)
- typeHostedUsage: [extension] `interface HostedUsage { readAt: string; seedStatus: string | null; response: JsonValue }` holds the deployment's answer to `GET /api/v1/get_current_usage`, its current UTC day and calendar month, as `convex deployment usage --json` reads it; the endpoint is beta, may understate usage and promises no time by which a call is counted, so a difference of two answers is recorded in the plan's units, never in money, and is the run's own only when no other run on the deployment overlapped it (E-59)
- typeHostedTarget: [extension] `interface HostedTarget { url: string; deployment: string; keyName: string; statedPlan: string }`; the deploy key is no member, because the harness's admin access holds it and a test never reads it (E-59)
- fnHostedTarget: [extension] `hostedTarget(variables: Readonly<Record<string, string | undefined>>): HostedTarget` reads `HOSTED_DEPLOYMENT_URL`, `HOSTED_DEPLOY_KEY`, `HOSTED_DEPLOY_KEY_NAME` and `HOSTED_PLAN` and refuses as the rules say (E-59)
- typeHostedAccess: [extension] `interface HostedAccess extends AdminAccess { usage(): Promise<HostedUsage>; instanceVersion(): Promise<string | null> }` is the admin access to a hosted deployment, which holds the deploy key and a fresh home; `usage` reads `GET /api/v1/get_current_usage` with the key, and `instanceVersion` is the answer of `/instance_version` or `null` (E-59)
- fnHostedBackend: [extension] `hostedBackend(options?: { composition?: "fixture" | "production"; issuer?: string; deploy?: boolean }): Promise<Backend & { admin: HostedAccess }>` sets the fixture issuer's variables, deploys the composition unless `deploy` is `false`, records the wall time of each deploy on the running test, which the record gathers into `deploys`, and, when the test finishes, closes its clients; `stop`, `kill` and `restart` refuse, `dispose` removes nothing on the deployment, and reading `adminKey` throws (E-59, E-13)
- hostedSelection: [extension] a CLI call of a native run on a hosted deployment runs in the composition's project directory with the environment `PATH`, `HOME` set to a fresh directory, `TMPDIR` and `CONVEX_DEPLOY_KEY`, and no `--url` or `--admin-key`; `convex` 1.46.0 resolves a development deployment's deploy key to its URL and uses the key itself as the deployment's credential, in `node_modules/convex/src/cli/lib/deploymentSelection.ts` lines 714 to 749, and sends it as `Authorization: Convex` in `node_modules/convex/src/cli/lib/utils/utils.ts` lines 1373 to 1389; the local path keeps its arguments (E-59)
- deployKeyActions: [extension] the deploy key allows exactly `deployment:deploy`, `deployment:env:view`, `deployment:env:write`, `deployment:data:view`, `deployment:data:write`, `deployment:functions:runInternalQueries`, `deployment:functions:runInternalMutations`, `deployment:functions:runInternalActions`, `deployment:logs:view`, `deployment:usage:view`, `deployment:backups:view`, `deployment:backups:create`, `deployment:backups:download` and `deployment:backups:import`, the actions the routes of `AdminAccess` and the CLI's export and import check in the upstream backend at `5c7cb5b`, and not `deployment:functions:actAsUser`, pause, usage limits, integrations or the audit log (E-59)
- hostedRedaction: [extension] the secrets of a native run on a hosted deployment are the four forms of the deploy key, given to every child, every buffer and the reporter; the admin access built over a hosted deployment catches every rejection of its members, the HTTP client's raw response text and its `Invalid response` text among them, a fetch that rejects and a call that aborts, and rethrows it with those forms replaced; its HTTP and socket clients take a logger that replaces them; a CLI child's output is redacted on success as on failure and on an abort; the reporter redacts the serialized record before it writes it; the import upload token, the export download token, application data and the fixture issuer's private key are not among these secrets and are named as not covered, not scrubbed as if they were (E-59, E-15)
- hostedConfiguration: [extension] `npm run test:hosted` runs `vitest run --config vitest.hosted.config.ts`, whose one project, `hosted`, runs one driver file under `tests/hosted/` with its own global setup and the evidence reporter; the driver runs four examples in order: Probe 7's retention example before any deploy or import, Probe 7's replacement in place, the production composition's acceptance, and Probe 3's quota half; the first, second and fourth run on one temporary copy of the fixture composition that adds the modules under `tests/hosted/`, and the fourth leaves that copy deployed for the next run; when the deployment holds no earlier planting, the first run deploys the copy before the retention example and records that it read nothing; `npm run test:all` never includes it (E-59)
- hostedSchedule: [extension] the workflow `.github/workflows/hosted.yml` runs on `workflow_dispatch` and on a schedule at 03:00 UTC on Monday and Thursday; GitHub runs a schedule from the default branch, and the job runs in a GitHub environment named `hosted` that holds the key and admits the default branch only, so a dispatch from another branch gets no key; in one concurrency group that cancels no running job; it uploads the record as the artifact `hosted-evidence` only after `scripts/hosted-record-check.mjs`, reading the key from its own environment, finds no form of it in the record or the captured log, and no other workflow waits on it; until the workflow is on the default branch, the owner's machine runs `npm run test:hosted` with the variables in its shell, and its record names a developer as the one who ran it (E-59)
- hostedRedactionTest: [extension] one pure test with no network plants a key in the form of a development deploy key, gives the hosted admin access an injected fetch and a stub socket and runs a stub CLI script, each of which echoes the key in all four forms on every path, calls every member so that each fails, captures `process.stdout` and `process.stderr` and the reporter's output, writes a record into a temporary directory, and fails when any form appears in any of them (E-59)
- hostedProbeCopy: [extension] the temporary copy of the fixture composition that the hosted driver deploys adds, from `tests/hosted/planting.ts` and the local in-place example's own scheduler module, the table `plantedSchedules` of planting records, one for each schedule a run planted in the parent, with its scheduler ID, the state and `completedTime` the run saw, the `startedAt` of the run that planted it and the count of backup archive imports since, the module `planting` that plants one succeeded, one failed and one canceled schedule and writes their planting records, and the scheduler references and reactions of the local in-place example in the parent and in the fixture contexts `depot` and `yard`; Probe 3's parent mutation is the fixture's own `readCost:viaMutation`, whose helper and component paths read the same document; the fixture composition itself gains nothing, as `probe7Narrowed` of `spec:facts.probe-plan` requires, and a later run knows a schedule's age after its scheduler row is gone (E-59)
